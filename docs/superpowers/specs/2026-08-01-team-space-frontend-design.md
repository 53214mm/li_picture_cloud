# 第 15 轮：团队空间前端业务闭环设计

## 1. 为什么要做这一轮

后端已经能创建团队空间、保存团队成员、计算空间权限，也已经具备图片协同编辑能力，但前端目前只展示“创建私有空间”，空间首页也只取用户创建的第一个空间。因此，普通用户无法通过页面完成下面这条完整路径：

> 创建团队空间 → 邀请成员 → 分配角色 → 进入团队空间 → 上传图片 → 有编辑权限的成员协同编辑。

本轮的目标是补齐这条业务链，而不是重做整站视觉。全局布局、排版、色彩和组件风格统一放到第 17 轮；本轮只增加必要的页面结构和局部样式，并尽量沿用现有视觉语言。

## 2. 成功标准

完成后，一个刚接触项目的用户应当可以只通过页面完成以下操作：

1. 创建私有空间或团队空间，并清楚知道二者区别。
2. 在“我的空间”中分别看到私有空间、自己创建的团队空间和自己加入的团队空间。
3. 在团队空间中看到自己的角色和当前可执行的操作。
4. 团队管理员可以按用户 ID 添加成员、修改角色、移除成员。
5. 查看者只能查看；编辑者可以上传、编辑和参与图片协同；团队管理员还可以管理成员。
6. 创建者成员记录不能被删除或降级，成员不能重复加入同一个团队。
7. 无权限、重复成员、成员不存在、网络失败等情况有明确中文提示，不出现“点击后没反应”。

## 3. 本轮范围

### 3.1 包含

- 创建空间时选择“私有空间”或“团队空间”。
- 空间入口按归属和类型分组。
- 团队空间角色、权限和成员管理界面。
- 补全 `spaceUser` 前端 API。
- 团队图片的上传、编辑、协同入口按后端权限显示。
- 后端补充成员唯一性和创建者保护规则。
- 前后端自动化测试、构建检查和小白向使用文档。

### 3.2 不包含

- 整站导航、栅格、字体、配色、阴影和响应式规则的重新设计；该工作属于第 17 轮。
- 通过用户名、手机号或模糊搜索邀请成员。本轮使用稳定且已有后端支持的“用户 ID”添加方式。
- 邀请链接、邮件通知、待接受邀请等复杂邀请流程。
- 新增团队数量规则。沿用后端现状：每位用户最多创建一个私有空间和一个团队空间，但可以加入多个其他团队。
- 改写现有 WebSocket/Redis 协同协议。本轮只把已有协同能力正确接入团队空间业务入口。

## 4. 采用的方案

采用“在现有页面上渐进补齐”的方案，而不是新建一套独立的团队工作台。

选择它的原因：

- 私有空间和团队空间共享图片列表、容量统计、图片详情等大部分能力，复用现有页面能减少重复代码。
- 后端已经用 `spaceType` 和权限集合表达差异，前端只需根据数据切换功能。
- 第 17 轮还要统一重做视觉；现在另建复杂布局会造成二次返工。

未采用的方案：

- **单独建设团队空间后台**：隔离清晰，但会重复图片列表和空间详情，当前阶段成本过高。
- **只在现有页面塞一个团队开关**：改动最少，但用户仍然找不到已加入团队，成员管理也没有自然入口，无法形成业务闭环。

## 5. 页面与交互设计

### 5.1 创建空间页

在表单顶部增加两个类型选项：

- **私有空间**：仅创建者使用，适合个人图片管理。
- **团队空间**：支持成员、角色和协同编辑。

默认选中私有空间，避免改变老用户的使用习惯。提交时始终显式传递 `spaceType`：私有空间为 `0`，团队空间为 `1`，不依赖后端默认值。空间级别继续使用现有规则。

创建成功后跳转到新空间详情页。若后端返回“每个用户每类空间仅能有一个”，前端直接显示该业务提示，并提供返回“我的空间”的入口。

### 5.2 我的空间页

页面按三个区域展示：

1. **我的私有空间**：当前用户创建、类型为私有的空间。
2. **我创建的团队空间**：当前用户创建、类型为团队的空间。
3. **我加入的团队空间**：来自“我的团队成员关系”接口，并排除自己创建的团队，避免同一个空间显示两次。

每张空间卡片展示空间名称、类型、级别、使用量。团队卡片额外展示当前角色：查看者、编辑者或管理员。某个区域没有数据时显示解释性空状态，例如“你还没有加入其他团队”，而不是留下空白。

数据来源分为两路：

- 用户创建的空间：空间分页接口，按当前用户 ID 查询。
- 用户加入的团队：`POST /spaceUser/list/my`。

两路请求互不覆盖；其中一路失败时保留另一路结果，并在失败区域显示重试按钮。

### 5.3 空间详情页

进入空间后先请求空间信息，再请求当前用户对该空间的权限集合。前端不再用“是不是创建者”猜测功能权限，而是以服务端返回的权限为准。

权限与界面能力的对应关系固定为：

| 权限 | 页面能力 |
| --- | --- |
| `picture:view` | 查看团队图片和图片详情 |
| `picture:upload` | 上传图片、批量上传 |
| `picture:edit` | 编辑图片、进入协同编辑 |
| `picture:delete` | 删除图片 |
| `spaceUser:manage` | 查看并管理成员面板 |

如果用户打开了没有权限的团队空间，页面显示“你不是该团队成员或暂无访问权限”，不渲染图片操作按钮。平台管理员和空间创建者仍由后端授权逻辑处理，前端只消费最终权限集合。

团队空间标题旁展示“团队空间”和当前角色标签。私有空间保持现有功能，不出现成员管理入口。

### 5.4 成员管理

只有拥有 `spaceUser:manage` 权限的用户能看到“成员管理”按钮。点击后打开成员抽屉或面板，避免把空间详情页继续拉长。

成员列表包含头像、昵称、用户 ID、角色和操作。管理员可以：

- 输入用户 ID，并选择查看者、编辑者或管理员后添加成员。
- 修改已有成员角色。
- 移除成员。

创建者一行带“创建者”标记，其角色固定为管理员；修改和删除按钮禁用，并说明“团队必须始终保留创建者管理员”。当前操作者不能通过界面移除自己，减少误操作；如确实需要退出团队，后续应设计独立的“退出团队”流程，不复用管理员删除操作。

所有危险操作都显示确认框。操作成功后重新加载成员列表；失败时保留当前列表并显示后端返回的具体原因。

### 5.5 图片协同入口

团队图片详情继续复用现有图片编辑弹窗和协同客户端。满足以下条件时显示“协同编辑”：

- 图片属于团队空间；
- 当前用户拥有 `picture:edit` 权限。

点击后进入已有的 WebSocket/Redis 协同流程。查看者只接收普通页面数据，不建立编辑会话，也不显示旋转、缩放等编辑操作。私有空间仍可使用原有单人编辑，不强行引入“协同”概念。

## 6. 前端模块边界

为避免继续把 `SpaceDetailView.vue` 堆成一个巨型文件，本轮拆出以下职责：

- `api/spaceUser.js`：成员增删改查、我的成员关系、空间权限请求。
- `constants/space.js`：空间类型、成员角色和中文元信息。
- `utils/spaceAccess.js`：空间分组、去重、权限判断等纯函数，便于单元测试。
- `components/space/SpaceCard.vue`：统一展示空间卡片。
- `components/space/SpaceMemberPanel.vue`：成员列表与管理交互。
- 现有页面负责加载数据、组织状态和处理路由，不重复实现角色规则。

这些模块都只依赖明确的输入：卡片接收空间展示数据；成员面板接收空间 ID、创建者 ID 和管理权限；权限工具接收后端权限字符串集合。以后第 17 轮换视觉时，可以替换组件样式而不用重写业务逻辑。

## 7. 后端业务约束补强

前端禁用按钮不能代替后端校验，因此同步增加两条服务端规则：

1. 同一个 `spaceId + userId` 只能有一条有效成员记录。添加前进行业务校验；数据库已有唯一索引则保留它作为并发情况下的最后防线。
2. 团队空间创建者对应的管理员成员记录不能被删除，也不能被修改为其他角色。

成员增删改仍然经过现有 `spaceUser:manage` 权限注解。所有校验失败统一抛出可读的业务异常，由全局异常处理器转换成前端能展示的响应。

本轮不会把这些规则只写在 Controller，因为规则属于团队成员业务，应放在 Service/领域边界，保证将来从其他入口调用时仍然生效。

## 8. 数据流（小白版）

以“管理员添加编辑者”为例：

1. 页面先向后端询问“我在这个空间有哪些权限”。
2. 后端根据空间创建者、平台管理员身份或团队成员角色返回权限字符串。
3. 页面发现包含 `spaceUser:manage`，才显示成员管理按钮。
4. 管理员填写用户 ID 并选择“编辑者”。
5. 前端把 `spaceId`、`userId`、`spaceRole=editor` 发送给后端。
6. 后端再次检查操作者权限，并检查用户、空间和重复成员。
7. 保存成功后，前端刷新成员列表。
8. 新成员进入团队空间时，后端返回编辑权限，页面才显示上传和协同编辑入口。

关键原则是：**前端负责友好展示，后端负责最终裁决**。即使有人绕过页面直接调用接口，也不能获得不属于自己的能力。

## 9. 异常与边界情况

- 未登录：沿用统一请求拦截，跳转登录页。
- 空间不存在：显示明确的空状态并提供返回空间首页按钮。
- 不是团队成员：不泄露成员列表和编辑入口。
- 重复添加：提示“该用户已在团队中”。
- 用户 ID 不存在：提示“用户不存在”。
- 创建者被修改或删除：后端拒绝，前端也禁用相应按钮。
- 两个管理员同时操作：以后端最终结果为准，失败的一方刷新列表。
- 接口部分失败：各区域独立显示错误，不让整页白屏。
- 已加入团队返回重复数据：按空间 ID 去重，自己创建的团队只归入“我创建的团队空间”。
- 权限加载期间：操作按钮保持禁用，避免权限尚未确定时短暂闪现。

## 10. 测试与验收

### 10.1 前端自动化测试

为纯业务工具补充 Node 单元测试，至少覆盖：

- 私有、我创建的团队、我加入的团队正确分组。
- 重复团队去重。
- `spaceType` 和角色元信息映射。
- 查看者、编辑者、管理员对应按钮能力。
- 未加载权限时默认拒绝操作。

前端还要通过：

- ESLint；
- 单元测试；
- Vite 生产构建；
- bundle 大小检查；
- 依赖安全审计。

### 10.2 后端自动化测试

至少覆盖：

- 创建团队空间后，创建者成员角色为管理员。
- 重复添加同一成员被拒绝。
- 创建者成员记录不能删除。
- 创建者不能被降为编辑者或查看者。
- 非管理员不能管理成员。
- 各角色返回的权限集合符合配置。

后端运行完整 Maven 测试和打包；Redis 专项测试继续使用既有验证方式，避免本轮破坏协同能力。

### 10.3 人工验收路径

文档给出两个测试账号的操作步骤：账号 A 创建团队并邀请账号 B 为编辑者；账号 B 进入团队、上传图片并打开协同编辑；账号 A 同时编辑同一图片，双方都能看到旋转、缩放和操作提示；随后将 B 改为查看者，B 刷新后不再看到编辑入口。

## 11. 文档与提交策略

本轮文档面向第一次接触项目的人，包含：

- 团队空间是什么；
- 三种角色分别能做什么；
- 如何创建团队、查找用户 ID、添加成员；
- 如何用两个账号验证协同编辑；
- 常见报错及处理方法；
- 本轮涉及的接口和关键代码入口。

实现按可独立回退的主题拆分提交：

1. 设计与实施计划文档。
2. 成员规则和接口测试。
3. 前端空间类型、列表分组和 API。
4. 成员管理与权限驱动的操作入口。
5. 验收文档和最终验证修正。

每个稳定提交都推送到远程仓库；不会把用户本地的 `application.yaml` 配置改动混入提交。

- **第 17 轮：全局前端视觉改版**。重新设计导航、页面宽度、栅格、字体层级、色彩、卡片、表格、表单、空状态和移动端适配。该轮先出视觉方向和页面清单，再统一实施，避免本轮边做业务边反复改样式。
