# 伙伴图片观察基础层设计

## 1. 本阶段目标

把伙伴喂养从“仅按图片 ID 选择固定档案”升级为“读取真实图片元数据后生成确定性营养”，同时建立视觉模型接入所需的稳定边界。

本阶段不接入外部视觉模型，不产生长期记忆，不开放用户 Token，也不改变已有经验、等级和幂等规则。即使没有任何 AI 密钥，伙伴仍能从图片尺寸、格式、大小以及图库文字元数据中获得可解释的基础营养。

## 2. 核心决策

### 2.1 观察与成长分离

```text
授权图片
   ↓（每次喂养重新校验权限）
PictureObservationProvider
   ↓ 只提供受控观察
PictureNutritionAnalyzer
   ↓ 生成候选营养
Companion / CompanionBalance
   ↓ 决定经验、等级、性格和技能的最终变化
GrowthRecord
```

外部模型未来只能替换观察 Provider 或营养 Adapter，不能直接写伙伴属性、等级、权限或额度。

### 2.2 三种信息必须明确区分

- `DEMO_DETERMINISTIC`：只按图片 ID 选择固定档案，不读取图片信息。
- `METADATA_DETERMINISTIC`：读取尺寸、格式、大小和用户填写的图库元数据，不读取图片像素。
- 后续视觉模式：读取图片像素，必须记录 Provider、模型、置信度和内容理解状态。

前端必须显示当前模式。元数据模式仍然是 `contentUnderstood=false`，不能用“AI 已看懂图片”之类的文案。

### 2.3 Provider 不返回原始敏感内容

本阶段的 `PictureObservation` 只携带完成成长计算所需的归一化事实，例如“是否有描述”“尺寸是否完整”，不把原始 URL、用户文字或 COS 凭据带入伙伴领域。

真实视觉阶段优先由后端读取受控字节或生成短期签名 URL；不能把永久 COS 密钥、内部对象路径或任意用户 URL直接交给模型厂商。

## 3. 配置与降级

配置项为 `app.companion.nutrition-mode`：

- 本地默认 `METADATA_DETERMINISTIC`；
- 测试与浏览器 E2E 固定 `DEMO_DETERMINISTIC`，保证断言稳定；
- 生产环境必须显式配置，且伙伴总开关仍默认关闭。

未来视觉 Provider 不可用时，是否降级到元数据模式必须由显式策略决定，并在当次成长记录中保存实际使用的模式；禁止静默把失败的视觉分析伪装成成功理解。

## 4. 本阶段验收

1. 同一图片元数据始终得到相同营养，不依赖随机数和当前时间。
2. 图片不存在时不创建成长记录，源图片也不会被修改。
3. 元数据模式最多产生受平衡规则约束的小幅性格变化和技能经验。
4. 主页与成长记录都能区分演示模式和元数据模式。
5. Demo、元数据两个实现通过配置互斥注册，现有 E2E 不依赖外部 AI。

## 5. 下一小步

在这个边界稳定后，实现一个 `imageInput=true` 的视觉 Provider。首个实现应输出结构化观察候选、Provider/模型标识与置信度；DeepSeek 继续只承担文本、推理和工具调用，`gpt-image-2` 继续只承担图片生成/编辑，二者都不冒充视觉理解模型。

视觉模式需要在现有 run 上区分“请求的分析策略”和“实际使用的来源”。显式降级时由分析结果携带实际 mode、Provider、模型、置信度与理解状态，再将实际来源写入成长记录；不能沿用全局 Analyzer 模式冒充当次结果。多个 Provider 应通过按 key 注册的 registry 选择，避免增加实现后出现 Spring Bean 歧义。图片像素或临时 URL 外发前还必须再次校验权限和资源版本。
