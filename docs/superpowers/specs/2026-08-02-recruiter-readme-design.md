# LiPictureCloud 招聘者导向 README 设计

## 目标

为仓库根目录补充一份中文 README，使招聘者或面试官能在 3 分钟内理解项目定位、业务闭环、候选人的技术投入和可深入追问的工程难点。

README 同时为开发者保留最短可用的本地启动与 Docker 部署入口，但不替代已有的详细教程。

## 目标读者

主要读者是国内 Java 后端岗位的招聘者和面试官。次要读者是希望运行或审阅代码的开发者。

## 写作原则

1. 先讲业务价值和个人技术工作，再列技术栈。
2. 所有功能和技术亮点必须能够在当前代码、测试或文档中找到依据。
3. 使用可被面试追问的具体设计取舍，不写无法证明的性能数字。
4. 中文为主，框架、协议和基础设施名称保留英文。
5. 展示线上地址 `https://lipicturecloud.com`，明确不提供公共测试账号。
6. 不写入密码、Token、云厂商密钥、服务器登录信息或其他秘密。
7. 根 README 保持可扫描性，详细操作链接到 `docs/`。

## 内容结构

### 1. 首屏

- 项目名称和一句话定位。
- 线上体验地址及账号说明。
- 技术栈/构建状态徽章。
- 3 至 5 条能快速建立项目印象的核心能力。

### 2. 项目简介与业务能力

按用户可感知的业务组织，而不是按 Controller 罗列接口：

- 公共图库与图片管理。
- 个人空间和团队空间。
- 团队成员角色、权限与协同编辑。
- AI 对话、生图和图片入库。
- 图库统计分析。
- 管理员审核与治理能力。

### 3. 技术架构

使用 Mermaid 绘制从浏览器、Nginx、Vue、Spring Boot 到 MySQL、Redis、COS 和外部 AI 服务的组件关系。

技术栈按后端、数据与中间件、前端、工程与部署分类，避免无层次地堆砌依赖名称。

### 4. 核心技术难点

选择能够体现 Java 后端能力且可从代码验证的主题：

- HTTP 与 WebSocket 共用团队空间授权语义。
- 查看者接收协同事件、编辑者提交操作的读写分离。
- Redis Session、缓存和协同状态的职责边界。
- AI MCP 工具回调按当前用户隔离，保证生成图片归属正确。
- ShardingSphere 静态/动态分表策略及可关闭设计。
- 生产配置外部化、健康检查、容器资源限制和 Nginx 网关。

每项使用“问题—设计—结果”的简短格式，不声明未经基准测试验证的性能收益。

### 5. 工程质量

- 自动化测试与 GitHub Actions。
- Maven Wrapper 和前端 Node 测试。
- Docker 多阶段构建与 Compose 编排。
- 生产环境种子模板和密钥外部化。
- 详细的分轮治理和部署教程。

测试数量等易变化数据不写死；如需展示，使用可复现命令代替。

### 6. 快速开始

提供本地运行所需的 Java、Node.js、MySQL、Redis 环境，以及后端和前端的最短启动命令。配置使用环境变量占位符，不提供真实值。

Docker 部分只保留复制 `.env`、填写配置和启动 Compose 的入口，并链接生产部署教程。

### 7. 项目结构与文档导航

说明后端、前端、部署模板、SQL 和文档目录的用途，并链接：

- 团队空间教程。
- 密码与 AI 安全教程。
- 用户种子教程。
- OpenCloudOS Docker 部署教程。
- 未决问题文档。

### 8. 已知边界

如实说明线上环境不提供公共测试账号，外部 AI、COS 等能力依赖用户自行配置合法凭证。对仍属演进方向的 DDD 改造等内容，只能列为后续规划，不能作为已完成功能。

## 不纳入本次范围

- 不制作新的产品截图或演示视频。
- 不重写现有部署教程。
- 不生成虚假的覆盖率、QPS、并发量或节省比例。
- 不公开生产账号、服务器详情和第三方服务密钥。
- 不修改业务代码、前端样式或部署配置。

## 验收标准

1. 仓库根目录存在 `README.md`。
2. 招聘者能在首屏明确项目定位、线上地址和主要技术亮点。
3. README 中的功能、依赖、命令和文档链接均能在仓库中验证。
4. Mermaid 架构图语法完整，GitHub 可直接渲染。
5. 本地与 Docker 启动命令不包含真实秘密。
6. 所有相对链接指向实际存在的文件。
7. README 对已完成能力和后续规划有明确区分。
