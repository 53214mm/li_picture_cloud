# 用户与管理员种子脚本设计

## 1. 背景与目标

项目已经将登录密码从 MD5 收口为 BCrypt，并固定使用 strength 12。新环境初始化时仍缺少一套清晰、安全的用户种子方案，因此本次增加两份用途严格分离的 SQL：

- 本地开发脚本：下载项目后可以直接执行，快速获得一个普通用户和一个管理员。
- 生产环境模板：只提供结构和操作说明，不携带任何可以直接登录生产环境的固定密码。

本次只增加初始化 SQL、自动化校验和小白友好的使用说明，不修改注册、登录、权限校验或数据库表结构。

## 2. 方案选择

### 2.1 采用方案：开发脚本与生产模板分离

选择两份独立文件，避免开发便利性与生产安全性互相冲突：

1. `sql/dev_seed_users.sql` 是可以直接运行的开发数据。
2. `sql/prod_seed_users_template.sql` 是不可直接使用的生产模板。

没有采用“同一份脚本通过变量切换环境”的方案。数据库本身无法可靠判断当前连接是否属于生产环境，一旦变量配置错误，就可能把公开的开发密码写入生产数据库。文件级隔离更直观，也更适合初学者审查。

### 2.2 没有采用的方案

- 只提供固定账号脚本：操作最简单，但容易被误用于生产。
- 只提供 BCrypt 占位模板：最安全，但本地开发者仍要自行生成密文，降低开箱体验。

## 3. 本地开发脚本

文件：`sql/dev_seed_users.sql`

固定开发账号如下：

| 角色 | 账号 | 临时密码 | 昵称 |
| --- | --- | --- | --- |
| 普通用户 | `user_seed` | `LocalUser123!` | 本地测试用户 |
| 管理员 | `admin_seed` | `LocalAdmin123!` | 本地测试管理员 |

密码列只写入由项目同款 `BCryptPasswordEncoder(12)` 生成的 BCrypt 密文。明文密码仅出现在开发脚本注释和开发说明中，用来告诉开发者如何登录；脚本明确标注“禁止生产使用”。

插入使用 `INSERT IGNORE`：

- 第一次执行时创建两个账号。
- 再次执行时，由 `uk_userAccount` 唯一索引阻止重复数据。
- 如果同名账号已经存在，不覆盖其密码、昵称、角色或删除状态。

脚本末尾提供只读取 `userAccount`、`userName`、`userRole` 和 `isDelete` 的检查语句，不查询或打印密码密文。

## 4. 生产环境安全模板

文件：`sql/prod_seed_users_template.sql`

模板遵循以下约束：

1. 不包含固定明文密码。
2. 不包含能够直接登录的默认 BCrypt 密文。
3. 示例插入语句默认保持注释状态。
4. BCrypt 占位符使用明显的 `REPLACE_WITH_BCRYPT_12_HASH`，提醒操作者替换。
5. 操作者必须在可信环境生成 strength 12 的 BCrypt 密文，完成替换、复核账号后，才可以取消注释执行。
6. 使用 `INSERT IGNORE`，避免模板误覆盖生产环境中的同名账号。
7. 文档要求首次登录后立即修改临时密码，并按现有安全迁移指南轮换 Session 命名空间，使旧会话失效。

生产模板同时给出普通用户和管理员示例。实际部署可以只启用管理员插入语句，普通用户继续通过注册接口创建。

## 5. 自动化校验

新增一个后端测试，读取两份 SQL 并校验以下行为：

- 开发脚本包含 `user_seed` 和 `admin_seed`，角色分别为 `user` 和 `admin`。
- 两个开发密码密文符合 BCrypt 格式，cost 为 12。
- 使用项目的 `PasswordHashService` 验证密文与文档中的临时密码匹配。
- 开发脚本采用 `INSERT IGNORE`，且验收查询不选择 `userPassword`。
- 生产模板包含明确的替换占位符和注释插入示例。
- 生产模板不包含开发账号、开发明文密码或开发 BCrypt 密文。

测试采用读取真实 SQL 文件的方式，不复制一份 SQL 到测试代码中，从而保证验证的是最终交付物。

## 6. 使用说明

同步增加一份面向初学者的说明，解释：

- 应该先执行 `sql/user.sql` 创建用户表，再执行开发种子脚本。
- 如何确认两个账号已经创建。
- 为什么不能把开发脚本用于生产。
- 如何生成生产 BCrypt 密文、替换占位符并安全执行模板。
- 遇到同名账号未变化时，`INSERT IGNORE` 的行为是什么。
- 初始化完成后如何处理临时密码和历史会话。

## 7. 验收标准

本功能完成时必须满足：

1. 两份 SQL 的用途从文件名和文件头注释即可分辨。
2. 本地脚本可在现有 MySQL 用户表上直接执行并创建两个不同角色的账号。
3. 本地脚本可以重复执行，且不会覆盖同名账号。
4. 本地密码能够通过当前项目的 BCrypt 登录校验。
5. 生产模板没有开箱即用的公共密码。
6. 自动化测试、完整 Maven 验证均通过。
7. 所有提交都排除开发者本地的 `src/main/resources/application.yaml` 修改。

## 8. 范围外事项

以下内容不在本次改动范围内：

- 自动随 Spring Boot 启动执行种子 SQL。
- 引入 Flyway 或 Liquibase。
- 修改用户表结构。
- 开发账号自动创建个人空间或团队空间。
- 自动删除或重置已存在的同名账号。
