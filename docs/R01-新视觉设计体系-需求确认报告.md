## 2. 当前视觉问题

### 2.1 信息层级：靠"边框+色块"分层，不靠"空间+字体"分层

每个面板都用同样强度的 2px 黑边框主张自己的存在，结果是**所有模块的视觉权重相等**——Stats、Chat、成长时间线在首屏争夺同样的注意力（`CompanionView.vue:114-131`）。层级靠红黄蓝色块（hero 蓝底、营养横幅黄底、Stats 黄头 `CompanionStats.vue:97`）而非位置、尺寸、留白来区分，用户视线没有落点。

### 2.2 密度：面板密度高，但"信息密度"低

情绪五轴 = 5 个数字 + 5 根条，关系五轴同样（`CompanionMoodPanel.vue:22-24`、`CompanionRelationshipPanel.vue:21`）——用户首先看到 `Mood=72`、`信任=63` 这类**读数**，而不是"伙伴现在怎么样"。这是仪表盘思维：把后端字段直接可视化，缺少一层"状态 → 可感知表达"的转译。

### 2.3 Layout：纵向堆叠的"管理后台"

伙伴页 11 个面板单列/双列混排后一路向下滚动（`CompanionView.vue:330-331`），是典型的"功能面板不断纵向堆叠"。页面没有空间结构——没有"伙伴在哪里""我在哪里"的位置感，只有模块清单。内容页（Gallery/MySpace/SpaceManage）的 `container + 页头` 模式本身健康，但与首页 hero 驱动、SpaceAnalyze 自定义宽度并存，节奏不统一（`src/views/SpaceAnalyzeView.vue:229`）。

### 2.4 卡片使用：卡片套卡片、边框套边框

SpaceDetail 上传面板 = 2px 黑边面板内嵌 2px 黑边 tabs 内嵌 2px 虚线 drop-zone（`src/views/SpaceDetailView.vue:575-579`）；MySpace 的 2px 黑边卡片内嵌一个紫色圆角 AI 面板（`src/views/MySpaceView.vue:151`）——两种视觉语言直接互嵌，是全站风格断裂最刺眼的点。

### 2.5 Typography：只有"大"和"小"，没有"语气"

标题体系 = 900 字重 + 紧字距 + 大写 kicker（`HeroSection.vue:82-89`、`CompanionView.vue:337`），这是海报语言，适合 landing 的一次性冲击；但当它同时用于错误面板、工具页标题、时间线 eyebrow 时，整个产品始终处于"喊话"状态，与"安静、陪伴"的产品情绪相反。中文排印没有专门处理（无中文字体栈、uppercase 对中文无效导致中英 kicker 观感不一）。

### 2.6 Navigation：功能完备，但它是"后台菜单"不是"空间导览"

导航分组（浏览/工作空间/管理/账户，`src/constants/navigation.js`）按**权限与功能**组织：上传、空间管理、图库分析、模型控制中心、配方工坊、喂养日志……这是管理后台的菜单逻辑。"我的伙伴"只是 8 个工作空间条目之一（`navigation.js:20`）——产品的第二主角在导航里没有任何特殊位置。

### 2.7 图像占比：图库页合格，其余页面图片近乎缺席

Gallery/PictureList 网格本身不错（`auto-fill,minmax(280px,1fr)`、4:3、懒加载、hover 上浮+硬阴影，`src/views/GalleryView.vue:238-271`）。但伙伴页——产品叙事的核心——图片只有喂养选择器的 12 张缩略图和 Story 面板 80×60 小图（`CompanionPicturePicker.vue:16-25`、`CompanionStoryPanel.vue:14-21`）；首页图片集中在第二屏马赛克区（`HomeView.vue:104-125`）。"图片优先"目前只在图库页成立。

### 2.8 组件语言：三套体系并存

1. **瑞士粗野主体系**（主流）：2px 黑边、直角、三原色、大写按钮；
2. **紫色 SaaS 体系**：`AiAgentPanel` 全套 `#8b5cf6/#6366f1`、8–16px 圆角、渐变（`AiAgentPanel.vue:241-306`）；
3. **圆角工具系**：`SpaceAnalyzeView` 全页 6/8px 圆角 + ECharts 紫橙（`SpaceAnalyzeView.vue:233-252`）。
另有进度条四种规格（12px 蓝/9px 红/.6rem 蓝绿/渐变轨道）、时间线两套样式、badge 三种规格、标签四种样式、遮罩透明度五档（详见第 3.3 节）。

### 2.9 动效：SaaS hover 级别，没有"生命感"预留

全部动效 = `transition: all 0.2s` 级别的属性过渡（`src/style.css:72`）。没有入场编排、没有环境/持续动效、没有状态驱动的动画概念。伙伴"活着"这件事在当前 UI 中没有任何动效表达——hero 同心圆是静态的（`CompanionView.vue:346-350`）。好的一面：`prefers-reduced-motion` 全局兜底已存在（`src/style.css:136-145`）。

### 2.10 Companion 页面结构：后端是数字生命，前端是 CRUD 面板

面板顺序（Stats→Feeding→Mood→Relationship→Chat→Proposal→Memory→Story→Emoji→Fusion→Growth）是**后端能力的目录式排列**，不是用户与伙伴相处的心智顺序。用户进入页面先看到等级 chip 和经验进度条（`CompanionStats.vue:9,105-106`），而不是"伙伴此刻的状态与存在"。后端已有生命阶段（光点/幼体/伙伴，`src/constants/companion.js:1-5`）、情绪五轴、性格五轴、记忆状态机，但前端没有任何"生命实体"的承接层——这正是 R01 要解决的核心矛盾。

## 3. 可保留资产

### 3.1 可以保留（进入 2.0 的资产）

- **无色相的克制骨架**：白/灰 + 单强调的思路本身是对的，三原色中 `--blue` 的"蓝"可作为新 accent 的调色起点。
- **Gallery/PictureList 网格机制**：auto-fill 响应式列、4:3、懒加载、键盘 focus 红 outline、`@media(hover:none)` 禁用 hover（`src/components/PictureList.vue:192-297`）——交互机制保留，视觉重制。
- **移动端 Drawer 导航的交互骨架**：焦点管理（打开聚焦关闭按钮、ESC 关闭、焦点还原）、body 滚动锁定、safe-area 适配（`NavBar.vue:101-143, 181-203`）——这套 a11y 行为直接复用，仅换皮。
- **弹窗→底部抽屉的移动端降级模式**（`PictureDetailView.vue:514-516` 等四处一致）。
- **全局触控与降级规范**：44px 触控高度（`style.css:121-124`）、`prefers-reduced-motion` 兜底（`style.css:136-145`）、focus-visible 3px 高可见焦点环（`style.css:44-47`，颜色随新令牌调整）。
- **页头模式**（h1 2rem/700/-0.04em 十页一致）——说明"页面级排版规范"可以被全站接受，新体系保留这一致性传统，只更新规格。
- **CompanionMessageBubble 的复用思想**："伙伴说话"气泡贯穿 Mood/Growth/Memory/Proposal（`CompanionMoodPanel.vue:14` 等）——这是"伙伴之声"的雏形，R12 可在此基础上实体化。
- **生命阶段/情绪/性格的领域语言**（`src/constants/companion.js`）：光点/幼体/伙伴、五轴情绪、五轴性格——新视觉的"状态协议"直接映射这些既有词汇，不需要发明新概念。

### 3.2 应该淘汰（与 2.0 方向冲突）

- 2px 黑色硬边框作为默认表面样式（69 处）——图片优先体系里边框必须退到 hairline 或消失。
- 高饱和三原色并置（`--red/--yellow/--blue` 同屏使用：hero 三色条 `HeroSection.vue:38-43`、黄营养横幅 `CompanionView.vue:351`、Stats 黄头）——图片应是唯一高饱和内容。
- hover 硬投影 `6px/8px 8px 0 var(--black)`——替换为柔和弥散阴影。
- 大写按钮与 kicker 作为全站默认语气（对中文无效且持续"喊话"）。
- 仪表盘式首屏（情绪/关系 10 根读数轴作为第一表达）——数据退入详情层，首屏让给状态与实体。
- 原生 `alert()/confirm()/prompt()`（`PictureDetailView.vue:307,369`、`SpaceManageView.vue:208,213` 等）——迁移范围内替换为统一浮层。
- 面板目录式堆叠的伙伴页结构（R09 重构对象）。

### 3.3 明显不一致（需在迁移中统一，不分对错只列事实）

1. 绿色两套：`#1A7A2E`（表单/审核）vs `#075d2a/#24633d/#2d7a4b/#4aa16d`（伙伴/网关/工坊）。
2. `var(--gray-300)` 被引用但从未定义（`ModelGatewayView.vue:637` 等 6 处）——现存 bug。
3. `.btn-sm` 三种尺寸并存（`GalleryView.vue:212` vs `MySpaceView.vue:152` vs `ShareModal.vue:129`）；`RecipeWorkshopView.vue:603` 覆写 `.btn-danger` 与全局冲突。
4. 容器宽度三派：1440 / 1400 / 64rem。
5. 断点七档并存：900/820/767/760/640/560/480 + 全局 1023。
6. 圆角：直角（全站）vs 6/8px（SpaceAnalyze）vs 8–16px（AiAgentPanel）。
7. 进度条四种规格；时间线两套；badge 三种；标签四种；遮罩透明度五档（0.45/0.5/0.55/0.6/0.92）。

## 4. 三套视觉方向

> 三套方向在**整体视觉思想**上不同：A 是"空间"（界面为墙），B 是"环境"（界面为暗室），C 是"世界"（界面为居所）。配套草图见 `docs/design-exploration/`。

### 方向 A · 雾屿纸境 — 安静的个人数字空间

- **核心关键词**：美术馆的墙、暖纸、克制、呼吸感、图片是唯一色彩
- **思想**：UI 退后成为装裱图片的墙与说明签；所有颜色让给图片；伙伴是住在这片安静里的住客，用光与微动效感知，不用数据感知
- **主背景**：暖纸白 `#F6F4EF`（非纯白，柔和、不刺眼、衬图）
- **主色与强调色**：暖墨 `#211E1A` 文字；单一强调"雾蓝" `#47618C`（旧 `--blue` 的去饱和延续）；语义色全部低饱和化（陶红 `#B4482F`、苔绿 `#4E7A5B`、蜜蜡 `#9A7418`）
- **字体气质**：无衬线正文（Inter + PingFang/YaHei 中文栈）+ 衬线展示字体（Noto Serif SC，仅 landing/大标题，可选）；字重收敛到 400/500/600，弃用 900 海报体
- **圆角**：小圆角 6/10/16px——柔化边缘但不"圆润可爱"
- **阴影**：低透明弥散阴影（双层：近处 2px/6px + 远处 12px/28px），无硬投影
- **表面材质**：纸面 + 1px 暖灰 hairline；分组靠留白与细线，不靠描边卡片
- **导航方式**：顶部细导航（hairline 底边），无粗边框；移动端保留现有 Drawer 交互骨架换皮
- **图片展示方式**：museum wall——统一 gutter、4:5/3:2 节奏、图片下方细字说明签；hover 仅上浮 4px + 柔影
- **Companion 如何融入**：伙伴是"空间里的住客"——Shell 中有固定栖居位（见 7.2 三级存在模型），其状态用呼吸光晕、姿态、一句话表达；数据收进详情层（Popover/Drawer）
- **动效语言**：240–420ms 缓出（entrance `cubic-bezier(.16,1,.3,1)`）；伙伴专属"环境动效"通道（呼吸 3–4s、眨眼 ~5s）；其余界面动画少而短
- **优点**：与"安静/克制/图片优先/精致"四个关键词完全对齐；迁移成本最低（白底→纸底是替换而非重写）；管理/表单页天然兼容；对比度易达标
- **风险**：执行不到位会显"空"而非"安静"；惊艳感依赖排印与留白功力；需要严格控制"再加点颜色"的冲动
- **契合点**：产品 = 图片资产 + 生命伙伴。纸境让图片资产成为视觉主体，让伙伴成为唯一"会动"的元素——动效预算集中给生命，而不是撒给按钮

### 方向 B · 暗房 — 沉浸式影像世界

- **核心关键词**：暗室、灯箱、显影、沉浸、图片是唯一光源
- **思想**：界面沉入黑暗，图片如灯箱发光；UI 是暗房工具，出现时轻、退去时隐；伙伴是暗室里一枚活着的光
- **主背景**：暖黑 `#131110` / 抬升面 `#1C1917`
- **主色与强调色**：纸白 `#EDE8DF` 文字；强调"显影琥珀" `#E3B04B`；hairline `rgba(255,255,255,.09)`
- **字体气质**：同 Inter 但更轻字重（300/400）+ 宽字距，影院字幕感
- **圆角**：极小 2–4px 或直角，冷峻画廊感
- **阴影**：不用投影，只用光晕（glow）与暗部层次
- **表面材质**：哑光黑面 + 发光边缘；无卡片感
- **导航方式**：浮动极简导航，随滚动隐去；全屏看图是一等公民
- **图片展示方式**：full-bleed 主视觉 + 横向胶片卷；图片承载全部色彩
- **Companion 如何融入**：伙伴 = 暗室中的光点/萤光体，与 LIFE_STAGE 第一阶"光点"（`constants/companion.js:2`）天然同构；情绪 = 光的色温与律动
- **动效语言**：显影式渐显（blur+brightness develop 1.6s）、光晕呼吸 4.2s、视差
- **优点**：沉浸感与图片表现力最强；"数字生命"叙事张力最大；差异化极高
- **风险**：管理/表单/表格/审核页深色化成本高；长时间管理操作易疲劳；与"日常陪伴的居家感"气质偏冷；摄影用户对深色界面下的色彩判断敏感
- **契合点**：与"沉浸、图片优先"满分契合，与"安静"契合，但"生命伙伴的日常感"需要额外经营

### 方向 C · 生息之间 — 数字生命空间 UI

- **核心关键词**：居所、空间层、环境色、有身体的伙伴、拖拽即交互
- **思想**：界面不是页面堆叠而是伙伴的家——图片是空间陈设，UI 是空间中的层（Drawer/Popover/浮层），环境色从图片提取，操作发生在空间里
- **主背景**：晨雾灰 `#EFEDE7` + 图片提取的环境色光晕（随用户图片变化）
- **主色与强调色**：墨绿灰 `#262A27` 文字；强调"苔绿" `#5F7A5E` + 暖木 `#D9A06B` 辅色
- **字体气质**：人文无衬线，圆润排印，弱字距
- **圆角**：12–20px 有机大圆角（非对称有机形用于伙伴身体）
- **阴影**：多层空间阴影（近景/中景/远景三档纵深），无描边
- **表面材质**：半透明暖白层叠（空间层，非装饰性毛玻璃——**明确排除紫色渐变毛玻璃 SaaS 路线**）
- **导航方式**：空间式导航——底部"房间切换"Dock（客厅/图库墙/庭院/我的），页面即房间
- **图片展示方式**：画布式自由布局（微旋转、错落、可拖拽），图片是墙上/桌上的陈设
- **Companion 如何融入**：伙伴是空间的**主人**——有身体的 2D Avatar 常驻居所，在空间中等待、靠近、反应；喂养 = 把图片拖到它面前；这是 R05–R10 最自然的土壤
- **动效语言**：弹簧物理曲线（`cubic-bezier(.34,1.56,.64,1)`）、空间漂浮、环境色漂移 24s、视差层
- **优点**：数字生命感最强、差异化最大；R05–R12 几乎无需二次设计即可落入
- **风险**：实现复杂度最高（自由布局 × 响应式 × 降级）；容易滑向过度游戏化；管理后台类页面与"房间"隐喻格格不入；移动端画布布局需要单独的降级设计（R13 压力最大）
- **契合点**：与"数字生命感、空间感"满分契合，但"克制、安静"需要极强的自我约束

## 5. 推荐方向

**推荐：以方向 A「雾屿纸境」作为 LiPictureCloud 2.0 全局视觉体系的基底，完整吸收方向 C 的"伙伴存在模型"，并为方向 B 预留"暗房模式"主题位。**

理由（对照产品定位与约束，非审美偏好）：

1. **图片优先的可执行性**：A 的"颜色全部让给图片"直接服务图片资产管理主业；B 虽然图片表现力更强，但管理/表单/审核/表格等占产品一半体量的页面深色化成本高，且这些页面在 R02–R15 中并不重构——选 B 意味着长期双体系割裂。
2. **数字生命感的正确载体**：生命感不来自视觉风格的"酷"，而来自"界面中唯一活着的东西是伙伴"。A 把全站动效压到最低、把环境动效预算集中给伙伴——**对比产生生命**。C 的方向本身正确，但作为全局默认对 R13（响应式与降级）压力过大，因此将 C 的空间/拖拽/实体思想收编进伙伴域（Companion Room、Feeding、Shell 存在位），而不是让全站变成画布。
3. **渐进迁移的现实约束**：现有体系是白底直角，A 是"替换令牌"级别的迁移（换底色、去边框、换阴影），B/C 是"重写布局"级别。R01 的原则是不一次性重写前端，A 唯一满足。
4. **B 不浪费**：令牌层按"主题可切换"设计（语义令牌 → 浅色默认主题 + 暗房主题预留），R04 图库的"沉浸看图模式"与未来 Companion Room 夜间模式可启用暗房主题，作为**模式**而非全局默认。

### 7.2 关键问题：伙伴如何作为"有身体的实体"存在于整个 UI，而不是右下角客服机器人？

**模型：伙伴是空间的常住居民，不是悬浮的工具入口。** 具体为三级存在（Presence Tiers）：

- **T1 · 居所（Habitat）**：`/companion` 是伙伴的房间（R09）。这里有它的全身 Avatar、它的环境光、它的物品（它喜欢的图片）。用户来这里"看它"，而不是"管理它"。数据仪表盘退入房间内的详情层（Popover/Drawer）。
- **T2 · 陪伴（Shell Presence）**：App Shell 中有它的**固定栖居位**——导航行内的活体端点（桌面）/ 底导 dock 的生命位（移动），而不是 `position:fixed; right:24px; bottom:24px` 的悬浮球。它与 T1 使用**同一套 Avatar 渲染资产、同一种姿态语言**，只是等比缩小——用户感知到的是"它在那里"，不是"那里有个图标"。
- **T3 · 在场（Contextual Appearance）**：在与它相关的时刻出现在原位——图库选中图片时，接收位出现它的期待姿态；拖拽图片经过时它跟随注视；喂养结果在原处发生（它消化、反应），而不是弹 toast。

**与客服机器人的五条设计约束区别**（写入验收标准）：

1. **有住所**：T1 居所是默认归宿，Shell 存在位指向居所；客服机器人没有家，只有 launcher。
2. **同一身体**：T1/T2/T3 渲染同一 Avatar 资产（等比缩放），禁止另造 icon 版"伙伴入口"。
3. **状态由内而发**：它的外观由 R06 状态协议（生命阶段/情绪/饥饿）驱动，不是未读红点驱动的"找你有事"。
4. **交互以"给予"为主**：首要动作是递图片/看望，对话是其中一种相处，而不是打开会话窗。
5. **沉默权**：它可以只是待着（呼吸、眨眼、看向图片），不必须说话——客服机器人以开口为存在方式，伙伴以存在为存在方式。

## 11. 本阶段结论

1. **现状诊断成立**：当前前端是执行一致的瑞士粗野主义"管理后台"体系（2px 黑边 ×69、三原色、直角、无阴影、hover 硬投影），与"图片资产管理 + 数字生命伙伴"的产品方向存在**结构性冲突**——冲突核心不是配色，而是"面板目录式布局 + 数据仪表盘表达"没有给"图片主体"与"生命实体"留位置。
2. **R01 提案**：以方向 A「雾屿纸境」（暖纸底 + 雾蓝单强调 + hairline + 柔影 + 小圆角 + 双通道动效）为全局基底，吸收方向 C 的伙伴三级存在模型，令牌层为方向 B 暗房模式预留主题位。初版令牌见第 6 节，落地边界见第 8 节，验收见第 10 节。
3. **本阶段产物**：本报告 + `docs/design-exploration/`（三套方向草图，独立隔离）。未修改任何正式代码、样式、配置、依赖与 Git 历史。
4. **待确认事项（需要产品方决策，不自行脑补）**：
   - 是否确认方向 A 为深化方向（或选择 B/C）；
   - 衬线展示字体（Noto Serif SC）是否接受作为 landing 可选字体；
   - 容器最大宽度由 1440 收敛至 1200 是否接受（影响全站密度感）；
   - 伙伴 Avatar 的具象程度（抽象光团 ↔ 具象角色）——R05 前需要定调，本报告按"抽象有机形、有眼睛与姿态"的最低实体标准预留。

**R01 阶段到此停止。等待对视觉方向的明确确认后，才进入「模型运行日志-代码生成」阶段；R02–R15 不在本轮启动。**
