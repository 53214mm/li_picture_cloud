# R05 — 角色体系设计（第一阶段已决策）

日期：2026-09-23。这里只定义概念边界与资产组织意图；没有新建表、接口、状态协议或生产渲染器。

正式基线：第一 Species 为绫页 / 纸翼蛾族，Egg / Juvenile / Adult 视觉方向均接受；B/C 冻结。首版采用 Sprite + 静态 / 表情差分 Portrait。Web Adult 保持正常比例，Q 版仅作未来桌宠参考。旧光团直接获得绫页身体，原 Instance 和全部业务数据不变。

## 1. 身份所有权

| 概念 | 拥有什么 | 不拥有什么 |
| --- | --- | --- |
| CompanionSpecies | 官方身份、种族、稳定人格底色、世界文化背景、三阶段视觉基因、资产母版与可用表现 | 用户私有记忆、关系数值、已发生的个人经历 |
| CompanionInstance | 唯一 id、owner、未来 species 关联、用户取名、未来孵化时间、现有生命经验/等级/阶段、Traits、Mood、Relationship、Memory 关联 | 一套独立复制的 Runtime 或新的角色模板 |
| Appearance / Art revision | 服装、皮肤、资产版本、不同设备的表示 | 新的生命、重置成长、另起记忆 |
| Representation | Shell Presence、Home Full-body Sprite、Conversation Portrait、未来 Desktop Pet Chibi | 决定实际生命阶段、业务权限或创建新的 Instance |
| Owned Companion（未来） | 用户拥有的全部独立 Instance 的归属关系 | 当前前台必须同时渲染全部实例 |
| Displayed Companion（未来） | Shell / 首页 / 全局 Presence 当前展示的 Instance 选择关系 | 替换 ownership、合并记忆或重置未展示实例 |

未来概念唯一约束是 `(userId, speciesId)`。Species 的边界是「官方可养成的一种角色模板」，不是现实生物分类法。同物种文化背景下若再发布不同官方角色模板，是否仍算同一 Species 必须在发布规范中明确，不能用新增 skinId 绕过唯一性。

现有领域 `ownerId` 与持久层 `userId` 指向用户，不因此再引入第二套所有者。`Companion.id` 应成为未来 Instance 身份的延续，`lifeExperience` 是现有 EXP 名称。Mood / Relationship / Memories 可以继续通过 companionId 关联，不必塞进同一张大表。

用户命名、孵化时间、Events、Keepsakes 和自主生活 Story 是未来需要表达的能力；目前不能假装都已存在。已有 StoryDraft 是创作能力，与伙伴生平应分开。

## 2. 身份连续性的不可变条件

- 蛋被分配给用户后就属于同一个 Instance；孵化、成熟、换装、艺术升级、浏览器与 Desktop 切换都不能换 id。
- 关系与记忆绑定 Instance，而非 PNG 文件名、皮肤、设备、运行时对象或前端 session。
- 官方形象修订有 artVersion；不能因为升级模型重新计算过去 Feed，也不能回滚用户的成长。
- 同种第二次获得不产生重复实例；具体如何退回/提示/转为其它获取机会属于未来获取流程，本轮不编造补偿货币。
- 「忘记」「纠正」「图片撤权」的规则不因身体有了表情而改变。

## 3. 现有数据的冲突必须显式处理

当前 `UNIQUE(userId)` 比目标 `(userId, speciesId)` 更严格。当前读写按 `findByOwnerId` 选择单个伙伴，聊天、喂养、契约、记忆上下文都依赖这个前提。**多角色上线不是仅增加图片或修改唯一索引。**

未来如实施多实例，需要独立设计与测试：旧数据如何获得 speciesId、原 companionId 保留、所有关联归属、Displayed 选择、接口中的实例授权、幂等键作用域、当前单实例 API 的兼容行为及回滚。第二阶段不改唯一索引，不新建 Species 表或 displayedCompanionId，不改 Chat / Feed 路由；完整迁移不能由 R06～R12 顺手完成。

生命周期还有另一处冲突：`LIGHT → SEEDLING → COMPANION` 是现有等级推导；目标是 `Egg → Juvenile → Adult`，其中 Egg 涉及真实孵化状态。

| 当前事实 | 首版兼容边界 | 禁止的快捷处理 |
| --- | --- | --- |
| 已存在 LIGHT，可能已有聊天和成长 | 直接显示绫页身体，保留真实 lifeStage 与已有交流能力 | 映射为 Egg、重新孵化、认领或身份确认 |
| SEEDLING | 直接显示绫页身体；不凭名称相似自动绑定 Juvenile | 更改历史等级或把视觉替换当成生命周期迁移 |
| COMPANION | 直接显示正常比例绫页身体，真实状态照旧 | 将 Q 版强制解释为降级/幼年 |
| 尚未唤醒 | 继续视为不存在 Instance 的当前事实 | 从空数据假造已有蛋和孵化倒计时 |

明确保留 companionId、owner、lifeExperience、level、lifeStage、Traits、Mood、Relationship、Memory、Feed 历史与 Proposal / Contract 等数据。不得重建伙伴、重算历史 Feed、清空成长或重置记忆。

首发实施计划建议对所有已有单实例使用 Adult 视觉资产，把 `currentStage`（后端原值）与 `visualStage`（本地资源选择）分开；该建议在资产规格验收时核定，不写回 API / DB，也不把业务面板的 LIGHT 文案改成 Adult。不存在或未加载时不能伪造 Instance。原型的 Egg / Juvenile 切换仅供设计预览；未来真正获得新 Species 时才引入 Egg → Hatch → Juvenile → Adult 流程，生命周期领域模型另行设计。

## 4. 两个正交维度

| 生命阶段 | Shell Presence | Home Scene Sprite | Conversation Portrait |
| --- | --- | --- | --- |
| Egg | 具有种族轮廓的静态小卵 | 场景中的卵与固定落点 | 近景卵形，不假装已有成年面孔或成熟台词能力 |
| Juvenile | 简化的未成熟体 | 较简单的服装、尚未展开的生物特征 | 相同未成熟特征的半身，不按现实幼儿年龄叙事 |
| Adult | 绫页使用适合小尺寸的简化 Sprite，保留文字入口，不自动改为桌宠 Q 版 | 正常比例全身 Sprite，预留脚底与动作边界 | 正常比例半身静态 / 表情差分，默认 Neutral |

三阶段视觉方向已全部接受。Q 版是艺术比例，和现实年龄、生命周期无一一对应；不能拿它代替 Juvenile。生产时延续已接受的形态、服装和比例，细节可优化；不恢复先前要求 Juvenile 重画的阻塞条件。

原 A Q 版作为独立桌宠参考留档，不删除原图、不重新命名为幼体，也不作为本轮 Web 主体。保留此参考不意味着已确定桌宠宿主或要制作 Codex 宠物包。

同一角色的 Sprite 和 Portrait 共享：主色块、发型分区、眼色、种族轮廓、一个服装锚点与一个主题纹样。优先保持这些视觉不变量；小尺寸可以删纹理、纽扣与缝线，不能删掉全部非人特征。

## 5. 三个产品表现位置

### Shell

沿现有 Presence 的位置增补安静的小身体。首版计划在现有 40×44 标记容器内验证简化静态 Sprite，保留「伙伴空间」文字、router-link 与至少 44px 可触达区域；224px 桌面侧栏、88px 平板栏及手机底部行为不变。前轮 48 / 64 / 80px 样本仍可辅助美术观察，不直接成为生产槽位尺寸。

Shell 目前没有读取 Companion 业务状态。第一版静态角色作为导航身份标记，不宣称账号已拥有、在线、睡眠或达到某个等级；不为装饰入口新增全局轮询或第二份业务状态。保持侧栏滚动、Drawer 和 Overlay 层级，避免隐藏的重复入口触发无效动画。

Hover / Focus 先使用一致的边界、底色、焦点环；角色的微小反应是以后 R07/R08 的扩展。原型最多只有可暂停的整体呼吸示意，不算合格帧动画，不映射 Mood。没有红点、随机气泡或右下角漂浮客服球。

功能关闭：移除 Presence 并回收布局位置，不请求角色图片或启动播放器。未唤醒 / 状态未知：沿用中性导航语义；Home 保留现有空态、加载和错误处理，不编造睡觉。业务弹层开启：保持 Shell inert，停止可能的动效与指针响应，不越过现有 drawer/modal 层级。

### Home

仅替换 CompanionView 现有光团 Hero，使用绫页正常比例全身及稳定地面接触，预留宽翼包围盒；保留 Stats / Feed / Mood / Relationship / Chat / Proposal / Memory / Story 等面板。最小 Idle 各帧 feet anchor 一致，不制作 Walk / Sit / Sleep，不重做 R09 小屋。

### Conversation

在现有 Chat 中加入正常比例半身构图；窄屏收成小头像/静态缩略图，把文本放前。首版默认 Neutral，可准备 1～2 个差分供验收，但当前没有可信表现状态时不得自动使用；不按“哈哈”等关键词、流式文本或前端猜测切表情。Mood / Interaction Result → Expression 与最终状态集由 R06 / R11 负责，不能通过表情暗示记忆确认或提案执行成功。

## 6. 资产扩展方式（设计意图，不是 R06 协议）

建议将可替换美术资源组织成 `本地角色资源键 → artVersion → visualStage → representation`，每包附许可出处、设计母版、图片大小、裁切范围、feet anchor、安全边距、静态 fallback 和制作工具版本。本地资源键不是 DB speciesId，视觉阶段不是后端 lifeStage 的改名。R05 只验证一个 Idle；动作状态协议由 R06 / R07 决定，不冻结公共 enum。

例如 `lingye / art-v1 / adult / shell` 与 `lingye / art-v1 / adult / portrait` 是同一身份的两个资源视图。调用方通过轻量 CompanionBody / CompanionPortrait / CompanionPresence 表达 representation、currentStage、fallback 与可访问标签，不到处硬编码图片 URL；组件不创建实例、不调用业务写接口。不要提前造 Renderer Framework 或 R06 协议。用户 id 不拼到公共美术路径里；私人图片和未来纪念品继续使用原有授权路径。

| 增长规模 | 表现层应如何扩展 | 仍然要投入什么 |
| --- | --- | --- |
| 第 2 个角色 | 同样的画框、锚点与资源选择机制；添加一套资产和视觉元信息 | 新的原画、三阶段、表情与动作 QA；多实例业务尚须单独实现 |
| 第 5 个角色 | Shell 只加载 Displayed 的小资源；未来 Home 按可见实例加载，未展示不等于未拥有；切换释放绘制资源 | 可用动作清单与静态 fallback，不能全员常驻 GPU |
| 第 10 个角色 | 用资源清单校验、版本控制和制作模板维持一致；缩略图与全尺寸分开 | 系列角色的识别度测试、组合测试、资产许可证与包体预算维护 |

一个可替换渲染适配层能降低将来 Sprite 换 Spine 的业务耦合，但不代表动画资产可以自动转换。美术生产源文件的保留比提前实现庞大的 Runtime 抽象更重要。

## 9. Architecture Notes：未来 Owned 与 Displayed

```text
User
 ├── Owned: CompanionInstance A / 绫页
 ├── Owned: CompanionInstance B
 └── Owned: CompanionInstance C

Displayed Companion ── 选择其中一个已拥有 Instance
                       用于 App Shell / 首页 / 全局 Presence

Companion Home ── 未来可呈现多个 Owned Instance 的存在状态
```

这是产品关系，不是本轮 schema。Displayed Companion ≠ Only Companion。切换展示只改变前台选择，不改变 ownership、growth、memory、relationship 或 life state；不销毁未展示实例。实例间不能共用 / 合并私人记忆。未来 Home 显示多个伙伴或外出状态时，分别读取各实例事实，不受单一 Displayed 选择抹除。

用户引用的《明日方舟》仅用于说明“首页展示一位、生活空间中多位存在”的关系；不复制 UI、美术、文案或角色。B/C 冻结档案也不因此变成已承诺上线的 Species。

第二阶段只有当前一个 Companion：不新增 species 表、speciesId 数据、displayedCompanionId、角色选择器、轮换或多角色 Home。前端将“获得当前实例”与“选择显示资源”分开；未来可替换实例来源，但今天不实现列表、全局选择 store 或公共协议。

未来 Static Expression → Live2D、Frame Sprite → Spine / 其他骨骼动画只替换 Representation 的资源与局部渲染，不更换 Instance。那时再评估许可、模型与资源生命周期；本轮保留轻量组件边界与制作源文件，不安装适配器。

第一阶段决策已完成；第二阶段的工作单元与验收见[实施计划](R05-第二阶段实施计划.md)。本轮只提交文档，然后停止。
