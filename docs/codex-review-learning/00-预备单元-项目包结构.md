# 预备单元 0.0：项目包结构地图

> 基线：`main@11a6182`
>
> 目标：看到一个类的包名时，先判断它大概负责什么、应该依赖谁，再开始读方法。

## 1. 先看全局结论

当前后端不是一种架构从头贯彻到底，而是两种组织方式共存：

```text
传统三层（主要是图库旧功能）
Controller → Service → Mapper → Entity / MySQL

渐进式 DDD（伙伴、部分图片/空间/协同功能）
Controller → Application → Domain ← Infrastructure → Mapper / Entity / MySQL
```

因此，看到 `service` 和 `application` 同时存在并不代表它们是同一层的两个名字：

- `service` 主要承载旧模块的业务实现；
- `application` 目前主要承载伙伴用例的流程编排；
- `domain` 承载不依赖框架的业务规则；
- `infrastructure` 实现数据库、COS、视觉模型等外围能力。

这是一个“从传统分层逐步引入领域边界”的过渡期项目。

## 2. 根包结构

根包是：

```text
com.li.lipicturecloud
├─ controller       HTTP 接口入口
├─ service          传统业务服务接口与实现
├─ application      新式应用用例编排
├─ domain           领域模型、规则与仓储端口
├─ infrastructure   数据库和外部系统适配器
├─ repository       部分领域仓储适配器
├─ mapper           MyBatis 数据访问接口
├─ model            DTO、Entity、VO、Enum
├─ manager          权限、上传、COS 等较底层业务支撑
├─ AI               既有 Spring AI、Agent、RAG 与工具代码
├─ collaboration    WebSocket 协同编辑应用与运行设施
├─ api              第三方 API 封装
├─ annotation/aop   权限、限流等横切逻辑
├─ config            Spring 配置
├─ common            通用响应和分页请求
├─ exception         异常体系
├─ constant          常量
└─ sharding          分片算法
```

## 3. 请求入口：`controller`

代表文件：

- `PictureController`
- `SpaceController`
- `UserController`
- `CompanionController`
- `AIController`

Controller 的理想职责是：

1. 接收 HTTP 参数；
2. 确认登录主体；
3. 做最外层格式校验；
4. 调用一个业务用例；
5. 返回 DTO/VO。

Controller 不应该直接写 SQL、计算复杂业务规则或调用模型供应商。

阅读接口时，从 Controller 开始是为了找到“系统允许外部做什么”，但不能停在这里，因为真正的规则通常不在 Controller。

## 4. 传统业务层：`service` 与 `service.impl`

代表结构：

```text
service/PictureService.java
service/impl/PictureServiceImpl.java

service/SpaceService.java
service/impl/SpaceServiceImpl.java

service/UserService.java
service/impl/UserServiceImpl.java
```

这是常见的 Spring + MyBatis Plus 三层写法：

```text
PictureController
  → PictureService
  → PictureServiceImpl
  → PictureMapper
  → picture 表
```

这里的 `Service` 往往同时承担：

- 用例流程编排；
- 业务规则；
- Entity/VO 转换；
- 数据库调用；
- 有时还包括缓存或外部服务调用。

优点是路径直观、开发速度快；缺点是功能增长后容易出现很大的 `ServiceImpl`，业务规则也更难脱离 Spring 和数据库单独测试。

## 5. 新式应用层：`application`

当前主要是：

```text
application/companion
├─ CompanionLife.java
├─ CompanionLifeService.java
├─ CompanionFeedingCoordinator.java
├─ PictureNutritionAnalyzer.java
├─ FeedPictureCommand.java
├─ FeedReservation.java
└─ view/
```

应用层回答的是：

> 为了完成一次用户用例，应该按什么顺序调用权限、领域规则、仓储和外部能力？

例如 `CompanionLifeService.feed` 负责组织：

```text
查伙伴 → 预留幂等运行 → 检查图片权限 → 分析图片 → 提交成长
```

应用层可以依赖 Spring 事务和领域接口，但不应该包含大量经验计算、状态机不变量等纯业务规则。

`application/companion/view` 存放返回给前端的稳定视图。它们不等同于数据库 Entity。

## 6. 领域层：`domain`

当前已声明六个业务上下文：

| 子包 | 当前代码情况 | 主要含义 |
| --- | --- | --- |
| `domain/companion` | 最完整 | 伙伴、成长、喂养运行、营养与成长事实 |
| `domain/collaboration` | 有领域对象 | 协同会话、版本和操作 |
| `domain/picture` | 小型领域接口 | 图片资产与仓储端口 |
| `domain/space` | 小型领域接口 | 空间成员关系与角色 |
| `domain/identityaccess` | 目前主要是 `CONTEXT.md` | 主体、权限、授权资源概念 |
| `domain/airuntime` | `main` 上主要是 `CONTEXT.md` | 模型、能力、MCP 和费用概念预留 |

领域层应该保存：

- Entity、Aggregate、Value Object；
- 状态机和不变量；
- 领域计算规则；
- 领域需要的 Repository Port；
- 领域术语说明 `CONTEXT.md`。

领域层不应该依赖：

- Spring；
- Servlet/HTTP；
- MyBatis；
- 数据库 Entity；
- COS 或具体模型 SDK。

仓库中有 `DomainDependencyTest` 自动检查这些禁用依赖。这说明“领域层保持纯 Java”不是口头约定，而是有测试保护的架构规则。

## 7. 基础设施层：`infrastructure`

它负责回答：

> 领域和应用层提出的能力，具体怎样通过技术实现？

当前分为两类。

### 7.1 外部能力适配器

`infrastructure/companion` 包括：

- `DashScopeVisionClient`：调用视觉模型；
- `CosAuthorizedPictureContentProvider`：读取授权图片内容；
- `MetadataPictureNutritionAdapter`：根据元数据生成营养；
- `VisualPictureNutritionAdapter`：组合额度、图片字节、视觉模型和降级路径。

### 7.2 持久化适配器

`infrastructure/persistence/companion` 包括：

- `MybatisCompanionRepository`；
- `MybatisFeedingRunRepository`；
- `MybatisGrowthRecordRepository`；
- `MybatisVisionQuotaGuard`。

这些类实现领域层或应用层定义的小接口，再在内部调用 Mapper。

例如：

```text
CompanionRepository                 领域端口
        ↑ implements
MybatisCompanionRepository          基础设施适配器
        ↓
CompanionMapper                     MyBatis 接口
        ↓
companion 表
```

## 8. `repository`、`mapper` 和 `model/entity` 的区别

这三个包很容易混淆。

### `repository`

当前主要有：

- `PictureRepository`
- `repository/mybatis/MybatisPictureRepository`

Repository 表达的是业务需要的持久化语义，例如“按 ID 查授权图片资产”。它可以在内部组合多个 Mapper 或隐藏数据结构。

### `mapper`

Mapper 是 MyBatis 的数据库操作接口，通常与表结构更接近：

- `PictureMapper`
- `UserMapper`
- `SpaceMapper`
- `CompanionMapper`

Mapper 关心的是查询、插入、更新和 SQL 映射，不应该成为 Controller 直接使用的业务 API。

### `model/entity`

Entity 在这个项目中主要表示数据库行，例如用户、图片、空间或伙伴表的持久化结构。

它与 DDD 中的“领域实体”不是同一个概念。为了避免混淆，可以这样记：

```text
model/entity/CompanionEntity  ≈ 数据库长什么样
domain/companion/Companion    ≈ 业务规则认为伙伴是什么
```

## 9. 数据传输包：`model`

`model` 是传统模块共享的数据结构包：

```text
model/dto       接收请求的数据
model/vo        返回页面的数据
model/entity    数据库持久化数据
model/enums     传统模块使用的枚举
```

常见方向是：

```text
HTTP JSON → DTO → Service/Application → Domain/Entity → VO → HTTP JSON
```

不要因为几个对象字段相似就把 DTO、Entity、领域对象和 VO 当成同一种东西。它们变化的原因不同：

- DTO 随接口输入变化；
- Entity 随数据库表变化；
- Domain 随业务规则变化；
- VO/View 随前端展示契约变化。

## 10. `manager`：项目特有的支撑层

`manager` 不是 Spring 或 DDD 的标准层名。当前它主要承载：

- `CosManager`、`FileManager`：文件与 COS 支撑；
- `manager/upload`：不同上传来源；
- `manager/auth`：权限解析、Sa-Token 接入、空间授权。

它可以理解为“尚未完全归入应用层或基础设施层的复合支撑能力”。

阅读时不要仅凭 `manager` 名字判断层次，要看它的输入输出和依赖：

- 如果主要包装 SDK，它更接近 Infrastructure；
- 如果主要组织权限业务流程，它更接近 Application/Domain Service；
- 如果两者都有，说明职责可能需要以后重新划分。

## 11. 独立功能包

### `AI`

这是较早形成的 AI 子系统，包括：

- Agent/ReAct/工具调用；
- Spring AI 应用；
- RAG 与聊天记忆；
- MCP 工具配置；
- AI 工具类。

它目前没有完全遵循新 DDD 包结构，而且 Java 包名使用了大写 `AI`。Java 的惯例是包名全小写，因此这是历史结构，不应作为新增包命名模板。

### `collaboration`

这里包含协同编辑的应用服务、Redis 事件总线、状态存储和 WebSocket 接入；真正不依赖框架的核心规则另放在 `domain/collaboration`。

它是一个“按功能垂直聚合”的包，与伙伴模块的横向 `application/domain/infrastructure` 拆分方式不同。

### `api`

当前主要封装以图搜图的外部网页/API 调用。它更接近第三方客户端层，而不是本项目的 HTTP Controller。

## 12. 横切与公共包

| 包 | 用途 |
| --- | --- |
| `annotation` | `@AuthCheck`、`@RateLimit`、`@SpacePermission` |
| `aop` | 拦截上述注解并执行权限、限流逻辑 |
| `config` | Spring Bean、WebSocket、Redis、COS、MyBatis 等配置 |
| `common` | `BaseResponse`、分页请求、响应工具 |
| `exception` | 错误码、业务异常、全局异常处理 |
| `constant` | 全局常量 |
| `sharding` | ShardingSphere 自定义分片算法 |

这些代码服务多个业务模块，不能承载某一个具体领域的大量业务规则，否则会逐渐变成难以维护的“万能公共层”。

## 13. `resources` 与测试目录

`src/main/resources` 中比较重要的目录：

| 目录 | 用途 |
| --- | --- |
| `mapper` | MyBatis XML SQL 映射 |
| `db/changelog` | Liquibase 数据库迁移 |
| `sharding` | 静态/动态分片配置 |
| `redis` | Redis 脚本或资源 |
| `static` | 静态资源 |
| `biz`、`generator` | AI/生成相关模板和映射资源 |

测试包大体镜像生产包，例如：

```text
src/main/java/.../domain/companion/Companion.java
src/test/java/.../domain/companion/CompanionTest.java
```

此外还有按测试目的组织的包：

- `architecture`：架构依赖规则；
- `migration`：Liquibase 迁移；
- `sharding`：分片配置与路由；
- `deployment`：部署产物契约；
- `infrastructure`：真实适配器或集成测试。

## 14. 两条真实调用链对比

### 传统图片模块

```text
PictureController
→ PictureService
→ PictureServiceImpl
→ PictureMapper
→ Picture Entity / picture 表
```

### DDD 伙伴模块

```text
CompanionController
→ CompanionLife
→ CompanionLifeService
→ Companion / Repository Port
← MybatisCompanionRepository
→ CompanionMapper / CompanionEntity / companion 表
```

两者都能工作。区别不在“类的数量”，而在业务规则是否与框架、数据库结构解耦。

## 15. 当前结构的初步维护性信号

以下是阅读地图时应记住的信号，不是本轮正式缺陷结论：

1. `AI` 使用大写包名，属于历史命名，不宜继续复制；
2. `manager` 含义较宽，需要逐类判断职责；
3. MyBatis Repository 分散在 `repository/mybatis` 和 `infrastructure/persistence`；
4. `collaboration` 与 `companion` 使用了不同的分包策略；
5. `model` 已经较大，未来继续加入跨领域 DTO/Entity 容易成为“大杂烩”；
6. `domain/airuntime` 和 `domain/identityaccess` 在 `main` 上更多是术语占位，不代表领域实现已经完成。

接管项目时不要急着统一所有包。只有当结构确实妨碍理解、测试或变更时，才值得迁移；纯粹为了目录整齐进行大规模移动，收益通常不够。

## 16. 推荐读包顺序

处理一个具体功能时，推荐按以下顺序读：

```text
1. Controller：外部能做什么
2. DTO/Command：输入是什么
3. Application/Service：流程怎么组织
4. Domain：真正的业务规则是什么
5. Repository 接口：业务需要存取什么
6. Infrastructure/Mapper：具体怎样落库或调用外部服务
7. View/VO：最终输出什么
8. Test：作者声称哪些行为必须成立
```

如果是排查 SQL、迁移或第三方 SDK 问题，可以直接从 Infrastructure/Mapper 切入；但审查业务正确性时仍要回到 Domain/Application。

## 17. 知识分级

### 【必须掌握】

- Controller、Service/Application、Domain、Repository、Mapper、Entity 的职责差异；
- DTO、数据库 Entity、领域对象、VO/View 不是同一种对象；
- 传统三层与当前 DDD 路径的真实调用链；
- 从包名建立初步判断，再通过依赖和调用关系验证判断。

### 【需要看懂】

- Port/Adapter 的依赖反转方向；
- `manager`、`collaboration` 等项目特有包不能机械套层次；
- 横切逻辑为什么放在 annotation/AOP/config；
- 架构测试如何禁止领域层依赖 Spring/MyBatis。

### 【暂时知道即可】

- ShardingSphere 分片算法的内部执行方式；
- Spring AOP 代理生成细节；
- MyBatis XML 与 Mapper 代理的内部实现；
- Spring AI Agent/RAG/MCP 的具体运行机制。
