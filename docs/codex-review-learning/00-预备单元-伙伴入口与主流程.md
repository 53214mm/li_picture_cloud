# 预备单元 0.1：伙伴入口与主流程地图

> 基线：`main@11a6182`
>
> 本单元只建立全局地图，不深入证明事务和并发是否完全正确。

## 1. 业务目的

`main` 上的伙伴模块完成了三个最小用例：

1. **查看伙伴**：读取当前伙伴、技能、成长属性和最近成长记录；
2. **唤醒伙伴**：一个用户最多创建一个自己的伙伴；
3. **喂养伙伴**：用户选择一张有权查看的图片，系统把图片转换成“图片营养”，再由领域规则决定伙伴实际成长多少。

这里最重要的边界是：

> 图片分析结果只是成长候选，不能直接修改经验、等级、性格或技能。

真正决定成长结果的是领域对象 `Companion` 和平衡规则 `CompanionBalance`。

## 2. 总调用链

```text
浏览器请求
  ↓
CompanionController                 HTTP、登录用户、请求参数
  ↓
CompanionLife                       应用用例接口
  ↓
CompanionLifeService                权限、幂等、分析流程编排
  ├─ PictureNutritionAnalyzer       把授权图片变成图片营养
  ├─ CompanionFeedingCoordinator    管理短事务与最终提交事务
  │    ├─ Companion.feed(...)       领域规则计算成长
  │    ├─ CompanionRepository       保存伙伴快照
  │    ├─ GrowthRecordRepository    追加成长事实
  │    └─ FeedingRunRepository      保存幂等运行状态
  └─ CompanionViewAssembler         把领域对象转换成前端视图
       ↓
BaseResponse / FeedPictureResult
```

阅读大型项目时，不要一开始就打开所有 Repository 和 Mapper。先锁定公开入口，再沿一条用例向下追踪。

## 3. 入口：`CompanionController`

文件：`src/main/java/com/li/lipicturecloud/controller/CompanionController.java`

它暴露三个接口：

| HTTP 接口 | Controller 方法 | 应用用例 | 结果 |
| --- | --- | --- | --- |
| `GET /companion/me` | `current` | `companionLife.home(...)` | 伙伴主页 |
| `POST /companion/awaken` | `awaken` | `companionLife.awaken(...)` | 新建或已有伙伴主页 |
| `POST /companion/feed` | `feed` | `companionLife.feed(...)` | 本次成长结果 |

Controller 只做四件事：

1. 接收 HTTP 请求；
2. 做最外层参数检查；
3. 从服务端登录会话构造 `AuthorizationSubject`；
4. 调用应用层并包装响应。

它不负责判断图片权限，也不计算经验。这是一个刻意保持很薄的 HTTP 边界。

关键安全点在 `subject(HttpServletRequest)`：主体 ID 来自服务端登录态，而不是请求体中的 `userId`。否则攻击者可以伪造别人的用户 ID 给别人的伙伴喂图。

如果删除 Controller，领域和应用代码仍然存在，但外部 HTTP 客户端无法使用这些用例。

## 4. 应用门面：`CompanionLife`

文件：`src/main/java/com/li/lipicturecloud/application/companion/CompanionLife.java`

```java
public interface CompanionLife {
    CompanionHomeView home(AuthorizationSubject subject);
    CompanionHomeView awaken(AuthorizationSubject subject);
    FeedPictureResult feed(FeedPictureCommand command);
}
```

它描述“伙伴模块允许外部执行哪些应用用例”，而没有暴露数据库 Entity、Mapper 或领域对象内部结构。

当前只有 `CompanionLifeService` 一个实现，因此这个接口不是业务正确性的必需条件；它的实际价值是稳定 Controller 的依赖方向，并方便用替身测试 HTTP 边界。如果以后它始终只有一个实现且没有隔离价值，可以重新判断是否需要保留。

## 5. 应用编排：`CompanionLifeService`

文件：`src/main/java/com/li/lipicturecloud/application/companion/CompanionLifeService.java`

### 5.1 查看主页

```text
home(subject)
  → 开启只读、REPEATABLE_READ 事务
  → findByOwnerId
  → 查询最近 20 条成长记录
  → CompanionViewAssembler 转换视图
```

只读事务不等于“绝对不会写数据库”，它主要向 Spring 和数据库表达这个事务的用途。这里采用 `REPEATABLE_READ`，目的是避免并发喂养时主页分别读到新伙伴快照和旧成长记录，形成“半新半旧”的组合。

### 5.2 唤醒伙伴

```text
awaken(subject)
  → companionRepository.createIfAbsent(userId, balance)
  → home(subject)
```

`createIfAbsent` 表达的是“没有才创建”。真正防止并发创建两个伙伴，还需要数据库唯一约束和仓储实现配合，不能只相信方法名。

### 5.3 喂养伙伴

`feed` 是当前模块的主流程：

```text
校验功能开关、pictureId、idempotencyKey
  ↓
查找当前用户的伙伴
  ↓
reserve：先保存一次 FeedingRun
  ↓
检查当前用户是否仍有 PICTURE_VIEW 权限
  ↓
若是历史成功请求，直接回放旧结果
  ↓
PictureNutritionAnalyzer 分析图片
  ↓
complete：锁伙伴、执行领域成长、保存伙伴、追加记录、完成 run
  ↓
返回 FeedPictureResult
```

注意顺序：即使相同幂等键已经成功过，也必须先重新检查图片权限，再允许回放历史结果。这样图片撤权后，旧请求不能变成越权读取旁路。

如果删除 `CompanionLifeService`，Controller 就必须自己承担权限、幂等、异常归一化和分析编排，HTTP 层会迅速变成难测试的大类。

## 6. 为什么还有 `CompanionFeedingCoordinator`

文件：`src/main/java/com/li/lipicturecloud/application/companion/CompanionFeedingCoordinator.java`

图片分析可能访问 COS 和视觉模型，耗时远大于普通数据库操作。如果从分析开始到结束一直持有数据库事务和行锁，会导致锁等待、连接占用和吞吐下降。

所以流程被拆为：

```text
短事务 reserve
  → 无数据库长事务的图片分析
  → 短事务 complete
```

`reserve`、`reject`、`fail` 使用 `REQUIRES_NEW`，确保运行状态能够独立提交；`complete` 则把伙伴快照、成长记录和 run 完成状态放在同一事务中。

这个拆分增加了一层调用链，但它在这里有明确价值：隔离慢外部调用与数据库事务。下一单元会专门检查它是否真的保证了幂等和原子性。

## 7. 领域核心：`Companion.feed`

文件：`src/main/java/com/li/lipicturecloud/domain/companion/Companion.java`

输入：

- `PictureNutrition`：分析器提出的经验、性格和技能候选；
- `FeedingContext`：是否重复喂养、今日已获得经验、该图片已获得的熟悉度；
- `CompanionBalance`：每日上限、重复收益、等级和阶段规则。

输出：`FeedingGrowth`，其中包含新的伙伴快照和本次实际变化。

领域规则会再次裁剪候选值：

- 重复图片不能重复刷性格和技能；
- 经验受每日上限控制；
- 性格和技能变化受平衡规则限制；
- 等级和生命阶段由累计经验重新推导；
- `revision` 必须递增，用于并发写入保护。

`Companion` 不依赖 Spring、HTTP、MyBatis、COS 或模型 SDK。这意味着领域规则可以用普通 Java 单元测试验证，也不会因为替换数据库或视觉模型而重写。

## 8. Port 与 Adapter

`CompanionRepository` 是领域层定义的 Port：

```java
public interface CompanionRepository {
    Optional<Companion> findByOwnerId(long ownerId);
    Optional<Companion> findByOwnerIdForUpdate(long ownerId);
    Companion createIfAbsent(long ownerId, CompanionBalance balance);
    boolean save(Companion companionAfter, long expectedRevision);
}
```

`MybatisCompanionRepository` 是基础设施层 Adapter，负责把这些业务语义翻译成 MyBatis 和 SQL。

依赖方向是：

```text
应用层 → 领域接口 ← 基础设施实现
```

领域层不知道 MyBatis 的存在。这就是本项目中 Ports and Adapters 的实际含义，不需要先背抽象定义。

## 9. Spring 如何选择图片分析实现

文件：`src/main/java/com/li/lipicturecloud/config/CompanionConfiguration.java`

`CompanionLifeService` 只依赖 `PictureNutritionAnalyzer` 接口。配置类根据 `app.companion.nutrition-policy` 创建互斥 Bean：

| 配置 | 实现 | 是否读取像素/调用模型 |
| --- | --- | --- |
| `DEMO_ONLY` | `DemoPictureNutritionAdapter` | 否 |
| `METADATA_ONLY` | `MetadataPictureNutritionAdapter` | 否，只读取元数据 |
| `VISUAL_WITH_METADATA_FALLBACK` | `VisualPictureNutritionAdapter` | 可以，并允许明确降级 |

这不是为了“使用设计模式而使用”。它让应用流程不需要写一串供应商判断，也让测试可以使用确定性实现。

## 10. 类职责速查

| 类/接口 | 一句话职责 | 删除后的直接影响 |
| --- | --- | --- |
| `CompanionController` | HTTP 入口和登录主体转换 | 外部无法调用伙伴用例 |
| `CompanionLife` | 对外声明应用用例 | Controller 将直接依赖具体服务 |
| `CompanionLifeService` | 权限、幂等、分析的总编排 | 逻辑会泄漏到 Controller 或领域层 |
| `CompanionFeedingCoordinator` | 隔离慢分析与短事务 | 容易出现长事务或提交步骤散落 |
| `PictureNutritionAnalyzer` | 把图片变成成长候选 | 应用层会绑定具体模型/元数据实现 |
| `Companion` | 执行真正的成长规则 | 模型输出可能直接污染状态 |
| `CompanionBalance` | 集中成长数值和平衡版本 | 上限、等级规则会散落各处 |
| Repository Port | 表达领域需要的持久化能力 | 领域/应用层会依赖 MyBatis |
| `CompanionViewAssembler` | 领域对象转前端视图 | Controller 会了解领域内部和展示文案 |

## 10.1 通俗类比：把系统想成“宠物成长中心”

假设用户带着一张照片来到宠物成长中心，想用它喂养自己的伙伴：

| 项目中的类 | 成长中心里的角色 | 它实际做什么 |
| --- | --- | --- |
| `CompanionController` | 前台接待员 | 确认来的人是谁、接收照片编号和请求编号，然后把申请交给内部 |
| `CompanionLife` | 服务项目清单 | 只写明本店提供“查看伙伴、唤醒伙伴、喂养伙伴”，不亲自干活 |
| `CompanionLifeService` | 值班经理 | 安排完整流程：登记、查权限、找营养师、通知结算员 |
| `CompanionFeedingCoordinator` | 登记与结算员 | 给每次喂养编号，防止重复结算，并保证账本、伙伴状态和回执一起成功或一起失败 |
| `PictureNutritionAnalyzer` | 图片营养师 | 看图片或元数据，提出“建议增加多少经验、性格和技能” |
| `Companion` | 伙伴本人及其成长规律 | 根据自己当前状态接受或削减营养，算出真正成长结果 |
| `CompanionBalance` | 成长规则手册 | 规定每日上限、重复喂养收益、等级门槛和属性上限 |
| Repository Port | 仓库业务窗口 | 提供“找伙伴、保存伙伴、追加记录”等业务操作，不关心仓库内部使用什么设备 |
| MyBatis Repository Adapter | 仓库管理员 | 把业务窗口的要求翻译成具体数据库操作 |
| Mapper | 仓库里的数据库操作员 | 直接执行查询、插入和更新 SQL |
| `CompanionViewAssembler` | 成长报告制作员 | 把内部对象整理成前端能展示的等级、技能、文案和成长记录 |

这里最容易混淆的是“服务项目清单”和“值班经理”：

- `CompanionLife` 是接口，只声明**可以做什么**；
- `CompanionLifeService` 是实现类，负责**具体怎么做**。

类似于：

```java
interface 洗衣店服务 {
    衣服 洗衣服(衣服 dirty);
}
```

接口只是承诺提供洗衣服务。真正负责检查衣料、选择程序和启动机器的是实现类。

## 10.2 具体例子：小李用一张旅行照片喂养伙伴

假设请求是：

```text
登录用户：小李，userId = 1001
图片：pictureId = 8888
幂等键：feed_20260826_abcd
```

### 第一步：Controller 接待请求

`CompanionController` 从登录会话确认当前用户是 `1001`，再创建命令：

```text
FeedPictureCommand(
  subject = 用户 1001,
  pictureId = 8888,
  idempotencyKey = feed_20260826_abcd
)
```

如果客户端额外声称 `userId = 2002`，Controller 也不采用，因为真正主体只能来自登录会话。

### 第二步：Service 安排流程

`CompanionLifeService` 依次处理：

```text
伙伴功能是否开启？
→ 小李是否已经唤醒伙伴？
→ 这个幂等键以前是否处理过？
→ 小李现在是否仍有权查看图片 8888？
→ 应该调用哪种图片分析器？
```

它自己不计算最终经验，只负责让正确的人按正确顺序工作。

### 第三步：Coordinator 登记本次喂养

在分析图片前，Coordinator 先创建一条 `FeedingRun`：

```text
runId = 50001
status = PROCESSING
subjectId = 1001
pictureId = 8888
idempotencyKey = feed_20260826_abcd
```

如果浏览器超时后再次发送完全相同的幂等键，系统能够找到 `50001`，而不是再创建一次成长。

### 第四步：Analyzer 提出营养建议

营养师分析旅行照片后，可能给出：

```text
建议生命经验：20
建议好奇：+3
建议创造：+2
建议观察技能：+5
原因：图片包含新的旅行场景
```

这只是候选值，不是最终写入值。模型即使建议经验 `+100000`，也不能直接更新伙伴。

### 第五步：Companion 和 Balance 作最终裁决

假设规则手册规定：

```text
小李的伙伴今天最多还能获得 8 点经验
单次好奇最多增加 2
技能本次最多增加 4
```

那么真正结果可能是：

```text
实际生命经验：+8
实际好奇：+2
实际创造：+2
实际观察技能：+4
```

如果图片 `8888` 以前已经完整喂过，领域规则可能改成：

```text
事件：PICTURE_REVISITED
经验：只增加少量熟悉度
性格：不再增加
技能：不再增加
```

所以职责关系是：

```text
Analyzer：这张图“建议提供”什么
Companion + Balance：伙伴“实际得到”什么
```

### 第六步：Coordinator 原子结算

Coordinator 在一个数据库事务里完成：

```text
更新伙伴快照
+ 追加成长记录
+ 把 FeedingRun 改成 COMPLETED
```

只要其中一步失败，整个结算回滚。这样不会出现“伙伴已经加经验，但请求重试后系统又认为从未成功”的状态。

### 第七步：Assembler 制作前端报告

内部领域对象包含 revision、平衡版本、枚举和各种数值。Assembler 把它整理成前端需要的结果，例如：

```json
{
  "outcome": "GROWN",
  "lifeExperienceDelta": 8,
  "level": 2,
  "reason": "图片包含新的旅行场景"
}
```

它不负责决定经验，只负责翻译和展示。

## 10.3 为什么不把它们全写进一个类

如果全部写进 `CompanionController.feed()`，这个方法将同时负责：

```text
解析 HTTP
+ 登录认证
+ 图片权限
+ 调模型
+ 经验算法
+ SQL
+ 事务
+ 返回文案
```

任何变化都会修改同一个大方法：

- 换视觉供应商要改它；
- 调整等级规则要改它；
- 换数据库要改它；
- 修改接口格式也要改它。

当前拆分的核心价值是让变化尽量局部发生：

| 需求变化 | 主要修改位置 |
| --- | --- |
| HTTP 参数变化 | Controller / DTO |
| 喂养流程变化 | `CompanionLifeService` |
| 事务与幂等变化 | `CompanionFeedingCoordinator` |
| 图片分析方式变化 | `PictureNutritionAnalyzer` 的实现 |
| 经验和等级规则变化 | `Companion` / `CompanionBalance` |
| MySQL 存储变化 | Repository Adapter / Mapper |
| 前端展示字段变化 | View / `CompanionViewAssembler` |

拆分类不是越多越好。如果一个类只是把参数原样传给下一个类，又没有隔离变化、事务、框架或测试边界，它就可能是多余的中间层。本项目中 `Coordinator` 和 Analyzer 接口有明确边界价值；`CompanionLife` 接口是否长期值得保留，则可以随着实现数量和测试方式继续观察。

## 11. 本单元知识分级

### 【必须掌握】

- Controller、Application Service、Domain、Repository 各自负责什么；
- 为什么权限检查属于应用流程，而经验计算属于领域规则；
- 如何从一个 HTTP 接口沿调用链追到真正修改状态的代码；
- 图片营养是候选，`Companion.feed` 才拥有最终裁决权。

### 【需要看懂】

- 构造器注入：对象需要什么依赖，由 Spring 创建时传入；
- `record`：用于表达以数据和值语义为主的领域对象；
- `Optional`：明确表示查询结果可能不存在；
- Port/Adapter：业务依赖小接口，MyBatis 和模型 SDK 放在外围实现；
- `@ConditionalOnProperty`：根据配置决定创建哪个 Bean。

### 【暂时知道即可】

- `TransactionTemplate` 的内部实现；
- Spring AOP 如何生成事务代理；
- MyBatis Plus 如何把条件构造器转换成 SQL；
- 视觉模型响应解析和 COS 字节读取细节。

## 13. 下一单元

下一单元沿着 `feed` 继续深入：

```text
FeedingRun 状态机
→ 幂等键
→ REQUIRES_NEW
→ 行锁
→ revision/CAS
→ complete 的原子提交
→ 失败与重试
```
