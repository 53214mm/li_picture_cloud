# 预备单元 0.2-D：超时重试、旧尝试保护与完整复盘

> 基线：`main@11a6182`
>
> 目标：理解请求“看似卡死”后怎样被接管，以及旧请求突然恢复时为什么不能破坏新请求或重复成长。

## 1. 最危险的不是普通失败，而是结果未知

普通失败容易理解：模型明确返回错误，系统把 run 标记为 `FAILED`。

更麻烦的场景是：

```text
请求 A 已经开始分析
→ 应用进程卡顿、网络中断或模型长时间无响应
→ 数据库仍然是 PROCESSING
→ 客户端不知道 A 还活着还是已经消失
```

如果永远不允许重试，run 会一直卡在 PROCESSING。

如果任何重试都立即抢占，又可能出现 A、B 同时完成并重复成长。

所以系统需要“超时接管 + 旧尝试隔离”。

## 2. 什么情况下允许 restart

`existingReservation` 判断：

```text
run.status == FAILED
或者
run.updatedAt 已经早于 processingTimeout 截止时间
```

可以理解为：

```text
明确失败 → 可以重试
长时间没有更新的 PROCESSING → 视为可能失联，可以尝试接管
正常且未超时的 PROCESSING → 返回 IN_PROGRESS
```

restart 成功后：

```text
status：回到 PROCESSING
attemptCount：+1
revision：+1
updatedAt：更新为重启时间
```

例如：

```text
第一次尝试：attemptCount=1, revision=0
失败：       attemptCount=1, revision=1
第二次重启：attemptCount=2, revision=2
成功：       attemptCount=2, revision=3
```

`attemptCount` 表示这是第几次处理尝试，`revision` 表示运行记录总共发生了多少次受控变化。两者含义不同。

## 3. restart 也必须使用 CAS

假设 B、C 同时发现 A 已超时：

```text
B 尝试：revision 0 → 1
C 也尝试：revision 0 → 1
```

更新条件包含旧 revision，所以只有一个能成功：

```text
B 更新成功，成为新处理者
C 更新影响 0 行，重新读取最新 run
C 看到新的 PROCESSING，返回 IN_PROGRESS
```

因此超时并不等于“所有重试都能开始”，而是只允许一个请求通过 CAS 获得接管资格。

## 4. 为什么重试必须保持同一分析策略

restart 前还会比较：

- `requestedPolicy`；
- `requestedProviderCode`；
- `requestedModelCode`。

例如第一次请求登记的是：

```text
VISUAL_WITH_METADATA_FALLBACK
provider = dashscope
model = qwen-vl-max
```

如果系统配置后来切成纯元数据或另一个模型，同一个幂等键不能悄悄换策略后继续。

原因是同一个幂等请求应该保持稳定语义：

```text
同一个 key
→ 同一张图片
→ 同一种请求策略
→ 同一个预期供应商和模型
```

策略变化时应创建新的业务请求，而不是让旧 key 的含义漂移。

## 5. 经典竞态：A 超时，B 接管，A 又恢复

时间线：

```text
A：持有 run revision 0，正在调用模型
A：长时间无响应

B：发现 run 超时
B：restart CAS 成功
B：数据库 run 变为 revision 1，attemptCount 2

A：旧模型调用突然返回
A：仍然持有旧对象 revision 0
```

此时必须阻止 A：

- 把 run 标记为 COMPLETED；
- 把 run 标记为 FAILED；
- 把 run 标记为 REJECTED；
- 覆盖 B 的新状态。

## 6. 旧 A 尝试 complete 时怎样被阻止

A 进入 `complete` 后可能暂时完成这些步骤：

```text
锁定伙伴
→ 计算成长
→ 更新伙伴
→ 追加成长记录
```

最后更新 run 时，SQL 条件仍要求：

```text
revision = 0
AND status = PROCESSING
```

但数据库已经被 B restart 到 revision 1，所以 A 的 `runRepository.complete` 返回 false。

Coordinator 随即抛出异常。因为伙伴更新、成长记录和 run 完成都处于同一个事务：

```text
A 对伙伴的更新回滚
A 追加的成长记录回滚
A 不能产生任何成长效果
```

这说明 run CAS 不只是保护 run 自己，它还是整个成长事务最后的所有权确认。

## 7. 旧 A 尝试 fail/reject 时怎样被阻止

旧 A 可能不是成功恢复，而是晚到的失败回调：

```text
A 使用 revision 0 调用 fail
数据库已经是 revision 1
更新影响 0 行
```

代码会重新读取当前 run，但不会拿到 revision 1 后再次强写 FAILED。

它只接受一种情况：

```text
别人已经把 run 变成与 A 相同的目标终态
```

例如两个错误处理路径都想标记同一个 revision 为 FAILED，而其中一个已经成功，可以视为幂等完成。

如果当前是：

```text
PROCESSING（由 B 接管）
COMPLETED
或其他不同状态
```

旧 A 会收到“运行状态已变化”，不能继续写。

关键原则：

> CAS 失败后不能简单读取最新 revision 再重试写入，否则旧请求会冒充当前所有者。

## 8. FAILED、REJECTED 与 COMPLETED 的错误语义

### `REJECTED`

用于明确业务拒绝：

```text
图片不存在
图片已撤权
当前用户没有 PICTURE_VIEW
```

典型安全码：

```text
PICTURE_UNAVAILABLE
```

它是终态，不通过同一个 key 自动重试。

### `FAILED`

用于暂时性或基础设施失败：

```text
权限数据库暂时不可用
COS/图片读取失败
视觉模型调用失败
最终数据库提交失败
```

典型安全码：

```text
AUTHORIZATION_CHECK_FAILED
NUTRITION_FAILED
FEED_COMMIT_FAILED
```

它允许同一 key restart。

### `COMPLETED`

成功终态，必须携带：

```text
resultGrowthRecordId
```

之后相同 key 只回放原结果，不再成长。

## 9. 为什么错误信息必须是“安全错误”

run 保存的是：

```text
safeErrorCode
safeErrorMessage
safeErrorTime
```

不应保存或返回：

- API Token；
- 供应商完整响应；
- 图片临时签名 URL；
- SQL 和数据库连接信息；
- Java 堆栈；
- 用户不应看到的内部异常文本。

日志可以记录安全标识：

```text
correlationId
subjectId
pictureId
exceptionType
```

但同样不应记录秘密或完整敏感内容。

## 10. 为什么失败信息在 restart 后仍保留

`FeedingRun.restarted` 保留上一次：

```text
safeErrorCode
safeErrorMessage
safeErrorTime
```

即使第二次最后成功，也能审计：

```text
这次成功前曾经发生过一次什么安全失败
```

这不代表成功结果仍应向用户显示失败。展示层应该根据当前状态决定用户界面，历史错误主要服务审计和排障。

## 11. 回放成功结果为什么还要重新鉴权

假设：

```text
上午：用户有权查看图片 8888，喂养成功
下午：空间管理员撤销用户权限
晚上：用户用旧 key 请求 REPLAY
```

如果系统先回放再鉴权，旧幂等 key 会成为读取该图片派生成长信息的旁路。

当前顺序是：

```text
reserve 找到历史 run
→ 重新检查当前 PICTURE_VIEW
→ 有权限才允许返回 REPLAY
```

幂等保证的是业务效果不重复，不代表可以绕过最新权限状态。

## 12. 从请求到终态的完整流程

```text
POST /companion/feed
  │
  ├─ 校验 pictureId、idempotencyKey、功能开关
  ├─ 查找当前主体的伙伴
  │
  ├─ T1 / reserve(REQUIRES_NEW)
  │    ├─ 新 key：插入 PROCESSING
  │    ├─ COMPLETED：准备 REPLAY
  │    ├─ 未超时 PROCESSING：IN_PROGRESS
  │    ├─ FAILED/超时：CAS restart
  │    └─ REJECTED：保持拒绝
  │
  ├─ 重新检查当前图片权限
  │    └─ 明确无权：T3 / reject(REQUIRES_NEW)
  │
  ├─ 若 REPLAY：读取原 GrowthRecord 后返回
  ├─ 若 IN_PROGRESS/REJECTED：返回对应结果
  │
  ├─ 事务外分析图片
  │    └─ 失败：T3 / fail(REQUIRES_NEW)
  │
  └─ T2 / complete
       ├─ 校验实际 provenance 符合请求策略
       ├─ SELECT companion FOR UPDATE
       ├─ 读取每日经验和重复图片事实
       ├─ Companion.feed 计算成长
       ├─ companion revision CAS
       ├─ INSERT GrowthRecord
       ├─ FeedingRun revision + status CAS
       └─ COMMIT；任一步失败则全部 ROLLBACK
```

## 13. 每层保护各管什么

| 保护层 | 解决的问题 |
| --- | --- |
| 登录主体来自服务端会话 | 防止伪造其他用户 |
| 图片权限检查 | 防止使用未授权图片 |
| idempotencyKey | 识别同一次业务操作 |
| requestFingerprint | 防止一个 key 被复用到另一请求 |
| feed run 数据库唯一键 | 防止并发插入两条相同运行 |
| `FeedingRun` 状态机 | 限制合法状态转移 |
| processing timeout + restart CAS | 允许单个新请求接管失联运行 |
| `FOR UPDATE` | 串行结算同一伙伴 |
| companion revision CAS | 防止过期伙伴快照覆盖新状态 |
| growth record 唯一 feedingRunId | 防止同一运行产生两条成长事实 |
| run revision + status CAS | 最终确认当前尝试仍拥有运行 |
| complete 数据库事务 | 伙伴、成长记录、完成回执同成同败 |
| safe error | 失败可审计但不泄露秘密 |

## 14. 当前设计的价值判断

这套设计比普通 CRUD 复杂，但复杂度来自真实风险：

- 外部模型调用耗时且可能结果未知；
- 浏览器和网关可能重试；
- 多实例应用必须共享幂等状态；
- 同一伙伴的每日上限和重复收益需要串行结算；
- 成长必须可回放、可审计；
- 旧请求恢复后不能破坏新请求。

因此以下设计值得保留：

- 持久化 `FeedingRun`；
- 慢分析夹在两个短事务之间；
- 数据库唯一键；
- 行锁 + revision 第二道防线；
- 追加式 `GrowthRecord`；
- 旧尝试不能拿新 revision 强写终态。

## 15. 需要知道的边界

这些不是本单元正式缺陷结论，但接管时应知道：

### 没有处理心跳

当前超时主要看 `updatedAt`。若一次合法视觉调用确实超过 processing timeout，新的请求可能接管并发起第二次外部调用。

最终成长仍由 revision/事务保护，不会轻易重复提交，但可能产生：

- 两次模型调用；
- 额外费用；
- 两个尝试争抢完成资格。

是否需要心跳、租约或更长超时，要结合真实模型耗时和成本指标判断，不能只为架构完整提前增加复杂度。

### 数据库锁仍可能超时或死锁

一致性保护不等于运行永不失败。当前策略依赖失败回滚和安全重试处理这些情况。

### 幂等键需要客户端正确复用

如果客户端每次网络重试都生成新 key，服务端会把它们视为不同业务操作。前后端必须共同遵守幂等契约。

### 当前测试不等于生产穷尽

已有测试覆盖状态机、CAS、事务要求和若干并发路径，但真实 MySQL、多应用实例、网络中断和极端锁竞争仍需要分阶段验收。

### 【必须掌握】

- FAILED 与 REJECTED 为什么语义不同；
- 超时 restart 为什么也必须通过 revision CAS；
- 旧尝试 complete 失败时为什么伙伴和成长记录会一起回滚；
- CAS 失败后为什么不能读取最新 revision 再强行更新；
- 幂等回放为什么仍要遵守当前权限。

- `attemptCount` 与 `revision` 的区别；
- 同一 key 重试为什么必须保持分析策略、供应商和模型稳定；
- 安全错误与内部异常的边界；
