## 1. 先用做饭来理解“图片营养”

可以把伙伴喂图想成做饭：

```text
图片                  = 原材料
图片分析器            = 厨师
PictureNutrition      = 厨师提交的配餐建议
CompanionBalance      = 营养标准和每日上限
Companion.feed(...)   = 最终结算
GrowthRecord          = 已经吃下去后的正式记录
```

视觉模型不能直接修改伙伴。它最多只能说：

```text
这张图可能比较欢乐；
场景复杂度是 3；
创造性线索是 4；
建议增加一些观察、故事和表情技能经验。
```

系统再把这些观察转换成候选营养，最后由领域规则裁剪：

```text
模型观察
  ↓
VisualObservationCandidate
  ↓ 服务端固定公式
PictureNutrition（候选值）
  ↓ CompanionBalance 与重复图片规则
FeedingGrowth（实际成长）
```

这样设计的意义是：即使供应商返回异常大数值、提示词以后改变，或者未来替换模型，伙伴成长规则仍掌握在自己的服务端代码里。

## 2. 从喂养入口看完整调用链

主要入口仍然是：

`src/main/java/com/li/lipicturecloud/application/companion/CompanionLifeService.java`

一条首次完整喂养的链路是：

```text
CompanionController.feed
  ↓
CompanionLifeService.feed
  ├─ 检查伙伴功能和喂养开关
  ├─ 读取伙伴
  ├─ analyzer.policy()：记录请求允许的分析策略
  ├─ coordinator.reserve(...)：短事务登记 FeedingRun
  ├─ 检查当前图片查看权限
  ├─ 判断该图片是否已经完整喂养过
  │
  ├─ 首次图片：analyzer.analyze(picture)
  │    ├─ DemoPictureNutritionAdapter
  │    ├─ MetadataPictureNutritionAdapter
  │    └─ VisualPictureNutritionAdapter
  │
  ├─ 熟悉图片：analyzer.analyzeFamiliar(picture)
  │
  └─ coordinator.complete(run, nutrition)
       ├─ 校验“请求策略”是否接受“实际分析来源”
       ├─ 锁定伙伴
       ├─ Companion.feed(...) 结算实际成长
       ├─ 保存伙伴
       ├─ 追加 GrowthRecord 和 NutritionProvenance
       └─ FeedingRun → COMPLETED
```

有两个边界要特别注意：

1. 图片分析发生在最终数据库结算事务之外，避免拿着数据库锁等待 COS 或视觉供应商；
2. 分析结果回来以后，Coordinator 会再次校验实际来源，不能由某个 Adapter 随便声称自己调用了指定模型。

这部分与 0.2 的事务知识连接起来：

```text
短事务 reserve
  ↓ 提交 PROCESSING
事务外读取图片、调用模型
  ↓
短事务 complete
  ↓ 原子保存伙伴 + 成长记录 + 完成回执
```

## 3. 三条营养路径

配置类：

- `config/CompanionFeatureProperties.java`
- `config/CompanionConfiguration.java`

当前支持三种请求策略：

| NutritionPolicy | 实现 | 是否读取像素 | 是否调用外部模型 | 实际来源 |
| --- | --- | --- | --- | --- |
| `DEMO_ONLY` | `DemoPictureNutritionAdapter` | 否 | 否 | `DEMO_DETERMINISTIC` |
| `METADATA_ONLY` | `MetadataPictureNutritionAdapter` | 否 | 否 | `METADATA_DETERMINISTIC` |
| `VISUAL_WITH_METADATA_FALLBACK` | `VisualPictureNutritionAdapter` | 正常路径会读取 | 正常路径会调用 | 视觉成功或带原因的元数据降级 |

### 3.1 Demo 路径

Demo 实现只根据 `pictureId % 3` 选择固定营养档案。

它的价值不是“聪明”，而是：

- 本地没有模型凭据也能演示；
- 相同图片 ID 永远得到相同结果；
- 不下载图片，不产生隐私外发；
- 测试可以得到稳定结果。

它必须明确记录 `contentUnderstood=false`，因为它根本没有查看图片内容。

### 3.2 元数据路径

元数据实现只读取站内图片记录中的受控事实：

- 是否有宽高；
- 文件大小；
- 图片格式；
- 是否存在描述；
- 是否存在分类。

注意它只读取“有没有描述、有没有分类”，不会把描述文本或标签原文带入伙伴领域。

因此它可以知道：

```text
这是一张有尺寸、有格式、有描述的图片
```

但它不能声称知道：

```text
图片里有一个人在海边看日落
```

所以元数据路径的 `contentUnderstood` 必须是 `false`。

### 3.3 视觉路径

视觉路径会在通过授权、安全检查和额度预占后，把受控图片字节发送给 DashScope 兼容接口，并要求返回严格的结构化观察。

它不是“视觉失败就什么都吞掉”。只有提前列入白名单的安全失败才允许转成元数据营养，并且必须把降级原因写入成长记录。

## 4. Spring 如何只选择一个 Analyzer

`CompanionConfiguration` 使用 `@ConditionalOnProperty` 根据配置创建互斥 Bean。

可以通俗地理解为：

```text
nutrition-policy=DEMO_ONLY
  → Spring 只装配 DemoPictureNutritionAdapter

nutrition-policy=METADATA_ONLY
  → Spring 只装配 MetadataPictureNutritionAdapter

nutrition-policy=VISUAL_WITH_METADATA_FALLBACK
  → Spring 创建 DashScopeVisionClient
  → Spring 创建 VisualPictureNutritionAdapter
```

`CompanionLifeService` 只依赖 `PictureNutritionAnalyzer` 接口，不需要自己写一大串 `if/else` 判断当前环境。

### 为什么视觉客户端不能一直创建

视觉模式需要有效的 endpoint、model 和 API key。如果无论选择什么策略都创建视觉客户端，那么本地元数据模式也可能因为没有 API key 而启动失败。

当前设计只在显式选择视觉策略时创建客户端，因此：

- Demo 和元数据环境不依赖外部模型凭据；
- 视觉环境缺少凭据会尽早暴露配置错误；
- 不会把“配置错误”静默伪装成普通元数据模式。

### 当前配置默认值

普通配置默认使用：

```yaml
nutrition-policy: METADATA_ONLY
vision-timeout: 20s
vision-max-bytes: 8MB
vision-daily-limit: 10
```

生产配置则要求部署者显式提供视觉策略、endpoint、provider、model、API key、超时、大小和额度，避免生产环境无意继承开发默认值。

## 5. 必须掌握：Policy、Mode、Provenance 不一样

这是 0.3 最容易混淆、也最重要的知识点。

### 5.1 NutritionPolicy：请求策略

它回答：

> 这次请求允许系统走哪条路？

例如：

```text
VISUAL_WITH_METADATA_FALLBACK
```

表示系统优先尝试视觉模型，并允许在指定安全故障下退回元数据。

它不代表视觉调用一定成功。

### 5.2 NutritionMode：实际使用的来源类别

它回答：

> 这次结果最终来自 Demo、元数据还是真实视觉？

取值包括：

- `DEMO_DETERMINISTIC`
- `METADATA_DETERMINISTIC`
- `VISUAL_MODEL`

但只有 Mode 还不够。例如同样是元数据结果，它可能是用户主动选择元数据，也可能是视觉超时后的降级。

### 5.3 NutritionProvenance：完整来源事实

它回答：

> 这次分析实际上发生了什么，使用了谁、哪个模型、哪个提示词版本，是否真的理解内容，为什么降级？

主要字段：

| 字段 | 含义 |
| --- | --- |
| `actualMode` | 最终实际来源 |
| `contentUnderstood` | 是否真的分析了图片内容 |
| `providerCode` | 实际供应商 |
| `modelCode` | 实际模型 |
| `promptVersion` | 提示词语义版本 |
| `resultSchemaVersion` | 返回结构版本 |
| `confidence` | 视觉结果置信度，范围 0～1 |
| `fallbackReasonCode` | 降级原因；未降级时为空 |

因此一次视觉策略请求可能得到两种合法事实：

```text
请求：VISUAL_WITH_METADATA_FALLBACK

结果 A：
actualMode = VISUAL_MODEL
contentUnderstood = true
providerCode = dashscope
modelCode = qwen...
fallbackReasonCode = null

结果 B：
actualMode = METADATA_DETERMINISTIC
contentUnderstood = false
providerCode = internal
modelCode = metadata-v1
fallbackReasonCode = VISION_TIMEOUT
```

这就是“显式降级”：系统允许退路，但不会假装视觉成功。

## 6. 元数据路径的调用链

相关文件：

- `infrastructure/companion/MetadataPictureObservationProvider.java`
- `infrastructure/companion/MetadataPictureNutritionAdapter.java`
- `application/companion/PictureObservation.java`

调用过程：

```text
MetadataPictureNutritionAdapter.analyze
  ↓
MetadataPictureObservationProvider.observe
  ├─ 重新查询图片
  ├─ 再次检查 PICTURE_VIEW 权限
  └─ 只提取最小化元数据
       ↓
PictureObservation
       ↓
固定、可复算的服务端公式
       ↓
PictureNutrition + NutritionProvenance.metadata()
```

为什么进入分析器以后还要重新检查权限？

因为最外层的权限检查和真正读取图片不是同一个瞬间：

```text
时刻 1：用户有权限
时刻 2：图片被移动到私人空间，或者共享被撤销
时刻 3：分析器读取图片
```

如果时刻 3 不重新校验，就可能使用已经撤权的资源继续产生成长。

元数据营养公式目前是确定性的。例如存在宽高、大小、格式、描述、分类时分别增加固定候选经验和技能。这些仍然只是候选值，最终还会被 `CompanionBalance` 裁剪。

## 7. 真实视觉路径的安全流水线

核心类：`VisualPictureNutritionAdapter`

完整顺序是：

```text
1. contents.load(reference, maxBytes)
   ├─ 读取图片记录快照
   ├─ 检查当前查看权限
   ├─ 只接受已配置 COS 主机
   ├─ 校验对象路径
   ├─ 有上限地下载字节
   ├─ 校验扩展名和文件魔数
   ├─ 再读图片记录并再次鉴权
   └─ 确认下载前后资源没有变化

2. quota.reserve(...)
   └─ 在像素外发前预占当天一次平台额度

3. contents.verifyStillAuthorized(...)
   └─ 紧贴 HTTP 外发前再次检查权限、版本和资源绑定

4. visual.observe(content)
   └─ 调用 DashScope，得到结构化候选

5. visualNutrition(candidate)
   └─ 用服务端公式转换成 PictureNutrition
```

### 7.1 为什么不能直接拿数据库里的 URL 请求

如果服务端对任意 URL 发起下载，可能产生 SSRF：攻击者诱导服务端访问内网、云元数据地址或其他非预期主机。

当前 `CosAuthorizedPictureContentProvider` 只接受配置好的 COS origin，并拒绝：

- 不同协议、主机或端口；
- URL 中的用户名信息；
- 查询参数和 fragment；
- 空路径、`.`、`..`、反斜杠和控制字符；
- 不支持的图片扩展名。

这不是普通格式校验，而是图片外发边界的一部分。

### 7.2 为什么既检查扩展名，又检查文件魔数

文件名是 `cat.jpg` 不代表内容一定是 JPEG。

系统会检查 JPEG、PNG、WebP 的固定文件头。这样可以减少把伪装文件发送给模型或让下游按错误 MIME 解析的风险。

### 7.3 为什么下载前后要比较快照

这在并发安全里叫 TOCTOU：

```text
Time Of Check：检查时资源合法
Time Of Use：真正使用时资源已经变化
```

例如：

```text
检查图片 A 有权限
  ↓
开始下载 A
  ↓
图片记录被替换、移动或撤销共享
  ↓
仍把旧字节发给视觉模型
```

当前实现通过图片更新时间、资源 URL 摘要、MIME 和权限的多次核对，降低旧字节越过新权限状态的风险。

### 7.4 为什么 `AuthorizedPictureContent` 不暴露 URL

它只携带：

- 图片 ID；
- 资源版本；
- MIME；
- 不可逆资源绑定摘要；
- 防御性复制后的图片字节。

视觉客户端不需要知道 COS 对象键和真实 URL。减少信息在模块间传播，可以降低日志、异常或未来 Adapter 意外泄露地址的风险。

## 8. 视觉额度为什么在模型调用前预占

接口：`VisionQuotaGuard`

实现：`MybatisVisionQuotaGuard`

额度按“用户 + 上海自然日”建立日桶。默认每天 10 次。

```text
图片加载和校验失败
  → 还没有准备外发，不占视觉额度

图片已校验，准备调用 Provider
  → 先预占一次额度

Provider 超时或返回错误
  → 不退款
```

不退款看起来有些严格，但这是为了保护平台钱包。如果每次超时都退款，客户端可以不断重试，让平台持续产生真实模型成本，却永远不消耗业务额度。

### 并发预占如何保护

数据库以“主体 + 日期”唯一键保证每天只有一个桶：

```text
首次请求：尝试插入 attempts=1
并发首次请求：唯一键决定谁成功
后续请求：SELECT FOR UPDATE 锁住当天桶
条件更新：只有 attempts < dailyLimit 才能加 1
```

它不是 JVM 内存计数器，因此多个服务实例共享同一个数据库时仍然有效。

### 熟悉图片为什么不占额度

同一图片已经完整喂养过时，`CompanionLifeService` 调用 `analyzeFamiliar`。

视觉实现直接生成：

```text
元数据营养
fallbackReasonCode = SKIPPED_FAMILIAR
```

这条路径不读取像素、不调用 Provider，也不占视觉额度。最终领域规则仍只给熟悉度成长，不会把它当作一次新的完整图片喂养。

## 9. DashScope 客户端只负责“观察”，不负责“成长”

文件：`infrastructure/companion/DashScopeVisionClient.java`

它的职责是：

```text
AuthorizedPictureContent
  ↓ 组装受控请求
DashScope OpenAI-compatible endpoint
  ↓ 严格读取和校验响应
VisualObservationCandidate
```

它不负责：

- 图片业务权限；
- 视觉额度；
- 伙伴经验和等级；
- 保存成长记录；
- 决定是否降级。

这是一个相对清晰的 Adapter 边界。

### 9.1 为什么要求 JSON Schema

模型的自然语言输出不稳定。如果让模型自由返回：

```text
“这张图很有活力，我觉得可以加很多经验……”
```

服务端很难可靠解析。

当前客户端要求固定字段：

- `mood`
- `sceneComplexity`
- `energy`
- `socialPresence`
- `motionPotential`
- `creativity`
- `confidence`
- `companionMessage`

数值限制在 0～4，置信度限制在 0～1，不允许额外字段。响应还要再经过 Java 侧校验，不能只相信供应商声称遵守了 Schema。

### 9.2 为什么限制响应大小

客户端最多读取 64KB 响应，避免供应商异常响应或恶意中间层让服务端无限占用内存。

### 9.3 为什么模型文字还要二次限制

`companionMessage` 会进入成长记录并最终展示给用户，因此会检查：

- 字符数量；
- 控制字符；
- 外部链接；
- 是否为空。

模型输出仍然是不可信输入。使用了 JSON Schema 不等于可以跳过服务端验证。

### 9.4 为什么保存 promptVersion 和 resultSchemaVersion

半年后同一张图得到不同观察，可能是：

- 模型换了；
- 提示词改了；
- 返回字段含义改了；
- 成长平衡规则改了。

记录供应商、模型、提示词版本、结果结构版本和平衡版本，才能解释历史结果来自哪套规则。

## 10. 视觉观察怎样变成候选营养

`VisualObservationCandidate` 是供应商无关的观察结果。

例如模型返回：

```text
mood = JOYFUL
sceneComplexity = 3
energy = 4
socialPresence = true
motionPotential = 2
creativity = 3
confidence = 0.86
```

`VisualPictureNutritionAdapter.visualNutrition` 再使用服务端公式计算：

```text
候选生命经验
  = 35
  + sceneComplexity × 2
  + energy
  + creativity
```

特质和技能也使用服务端固定公式。例如高场景复杂度增加好奇心和观察技能，有人物线索时增加共情与故事技能。

这一步为什么不让模型直接返回 `experience=1000`？

因为模型负责看图，服务端负责游戏经济和平衡。二者职责不同。

而且这还不是最终结果：

```text
VisualObservationCandidate
  ↓ 固定转换公式
PictureNutrition.requested...
  ↓ Companion.feed + CompanionBalance
FeedingGrowth 实际增量
```

字段名使用 `requestedLifeExperience`、`requestedTraitDelta`，正是在提醒读代码的人：这些只是分析器申请的候选值。

## 11. 显式降级：哪些错误能降，哪些不能

视觉 Adapter 只允许以下安全错误码降级：

| 错误码 | 大致含义 | 当前处理 |
| --- | --- | --- |
| `VISION_TIMEOUT` | 视觉请求超时 | 元数据降级 |
| `VISION_RATE_LIMITED` | 供应商限流 | 元数据降级 |
| `VISION_UNAVAILABLE` | 供应商或网络暂不可用 | 元数据降级 |
| `VISION_INVALID_RESPONSE` | 返回内容不符合严格结构 | 元数据降级 |
| `VISION_IMAGE_TOO_LARGE` | 图片超过视觉大小上限 | 元数据降级 |
| `VISION_UNSUPPORTED_IMAGE_FORMAT` | 文件格式或魔数不支持 | 元数据降级 |
| `VISION_IMAGE_UNAVAILABLE` | 受控图片内容无法取得 | 元数据降级 |

降级结果必须记录：

```text
actualMode = METADATA_DETERMINISTIC
contentUnderstood = false
fallbackReasonCode = 对应安全错误码
```

### 不能静默降级的情况

以下情况不会被当作普通视觉故障吞掉：

- API key 错误：`VISION_CREDENTIALS`；
- 用户已经失去图片权限；
- 图片在下载到外发之间发生变化；
- 用户当天视觉额度已经耗尽；
- 不在白名单中的未知异常。

为什么凭据错误不能降级？

如果生产 API key 配错后仍返回元数据结果，系统表面看起来“能用”，运维人员可能长期不知道真实视觉从未工作。快速失败比静默伪装更容易发现配置事故。

为什么权限错误不能降级？

降级仍然会使用图片元数据。用户无权访问图片时，系统不能通过“换一条分析路径”绕过权限边界。

## 12. Coordinator 为什么还要复核实际来源

分析器返回 `PictureNutrition` 后，`CompanionFeedingCoordinator.complete` 会检查：

```java
run.requestedPolicy().accepts(nutrition.provenance())
```

规则可以理解为：

| 请求策略 | 可以接受的实际来源 |
| --- | --- |
| `DEMO_ONLY` | 只能是 Demo |
| `METADATA_ONLY` | 只能是未降级的元数据 |
| `VISUAL_WITH_METADATA_FALLBACK` | 真实视觉，或者带明确原因的元数据降级 |

如果是真实视觉结果，还会检查：

```text
请求记录中的 provider/model
  是否等于
实际 provenance 中的 provider/model
```

为什么需要双重检查？

因为 Adapter 属于系统内部组件，但内部组件也可能写错、接线错误或未来被替换。最终提交事务不能无条件相信上游结果。

元数据降级不要求匹配视觉模型，因为降级时根本没有成功使用那个模型；强行把请求模型记成实际模型反而是在制造假审计数据。

## 13. Provenance 最后保存到哪里

成功结算时：

```text
PictureNutrition.provenance
  ↓
GrowthRecord.provenance
  ↓
companion_growth_record 表
  ├─ nutritionMode
  ├─ contentUnderstood
  ├─ providerCode
  ├─ modelCode
  ├─ promptVersion
  ├─ resultSchemaVersion
  ├─ confidence
  └─ fallbackReasonCode
```

主页读取成长历史时，`CompanionViewAssembler` 再把这些字段转换成 `GrowthRecordView`。

因此前端可以区分：

```text
Qwen 视觉营养 · 已分析图片内容
元数据营养 · 未读取图片内容
元数据营养 · 视觉服务降级
```

`NutritionStatusView` 展示的是当前环境“准备怎样请求”，而每条 `GrowthRecordView` 展示的是那一次“实际上发生了什么”。二者不能混用。

## 15. Java 与 Spring 知识分级

### 【必须掌握】接口与依赖倒置

应用服务依赖：

```java
PictureNutritionAnalyzer
VisualObservationProvider
AuthorizedPictureContentProvider
VisionQuotaGuard
```

而不是直接依赖 DashScope、COS 或 MyBatis。

以后看到接口时先问：

1. 谁调用这个接口？
2. 哪个基础设施类实现它？
3. 它隔离的是外部供应商、存储，还是业务规则？

不要因为存在接口就认为一定是过度设计。这里的接口确实隔离了外部模型、对象存储和额度持久化，具有明确价值。

### 【必须掌握】不可信输入必须逐层校验

外部模型返回 JSON 以后经历：

```text
HTTP 状态和响应大小
  ↓
外层响应结构
  ↓
严格字段集合和字段类型
  ↓
数值范围
  ↓
VisualObservationCandidate 构造器不变量
  ↓
服务端营养公式
  ↓
CompanionBalance 最终裁剪
```

“供应商支持 JSON Schema”不能替代自己的服务端校验。

### 【必须掌握】请求意图和实际结果分离

`NutritionPolicy` 与 `NutritionProvenance` 的分离不只是命名问题，而是审计正确性问题。

类似思想还会出现在：

- 用户请求支付 100 元，与支付渠道实际扣款结果；
- 用户请求发送邮件，与供应商实际投递状态；
- 用户请求使用某模型，与网关最终路由的模型。

### 【需要看懂】`@ConditionalOnProperty`

它让 Spring 根据配置条件决定是否创建某个 Bean。这里用于保证三个 Analyzer 实现互斥，并避免非视觉环境创建网络客户端。

现在不要求默写注解参数，但要能看懂：配置值决定当前运行时使用哪套实现。

### 【需要看懂】record 与紧凑构造器

`PictureNutrition`、`NutritionProvenance`、`VisualObservationCandidate` 使用 record 表达不可变数据。

紧凑构造器会在每次创建对象时验证字段组合。这样非法的视觉来源，例如：

```text
actualMode = VISUAL_MODEL
contentUnderstood = false
```

不能进入系统后续流程。

### 【需要看懂】防御性复制

`AuthorizedPictureContent` 在接收和返回 `byte[]` 时都复制数组。因为数组本身可变，仅仅把 record 声明成不可变并不能阻止调用者修改其中的字节。

### 【暂时知道即可】RestClient 与 JSON Tree API

当前只需知道：`RestClient` 负责 HTTP 调用，Jackson `JsonNode` 负责严格读取动态 JSON。

不需要现在记住所有链式 API；学习重点是请求边界、超时、响应大小和结构校验。

## 16. 当前设计评价

### 值得保留的设计

1. **分析器只提供候选值**：模型不能直接控制伙伴经济和平衡；
2. **Policy 与 Provenance 分离**：不会把请求意图冒充成实际事实；
3. **视觉出站前多次授权与资源绑定核验**：安全边界清晰；
4. **外部调用位于数据库长事务之外**：不会长时间占用连接和伙伴行锁；
5. **额度使用数据库日桶**：支持多实例并发；
6. **严格结构化响应与 Java 二次校验**：不盲目信任模型；
7. **降级使用白名单并保存原因**：可用性与审计没有互相牺牲；
8. **成长记录保存版本信息**：未来能够解释历史结果。

这些复杂度主要来自真实的外部模型、安全、预算和审计需求，不属于单纯为了 DDD 漂亮而增加的抽象。

### 后续审查时值得关注，但本单元不修改的点

| 关注点 | 当前影响 | 后续建议 |
| --- | --- | --- |
| 图片字节会经过复制和 Base64 膨胀 | 8MB 图片一次请求会占用明显高于 8MB 的内存 | 做视觉并发容量评估，必要时限制并发或采用更节省内存的传输方式 |
| 为防泄密，供应商底层异常和原始响应被完全丢弃 | 对用户安全，但线上定位供应商故障的证据较少 | 增加不含敏感内容的指标、错误码计数和链路日志 |
| 相同提示词同时放在 system 和 user text | 可能增加 Token 使用，并让提示词维护产生重复 | 后续结合供应商行为验证是否确有必要 |
| 额度 Repository 的审计时间直接调用 `Instant.now()` | 不影响传入的上海日期桶，但时间测试不够可控 | 若以后测试时间边界，可统一注入 Clock |
| 降级码白名单写在 Adapter 常量中 | 当前简单直接；供应商和策略增加后可能膨胀 | 在确有多供应商需求时再提取策略，不要提前抽象 |

这几个点目前不等于已确认 Bug。它们是后续压测、运维和扩展时需要验证的工程风险。

## 17. 三个完整场景复盘

### 场景 A：视觉成功

```text
用户有图片权限
→ 图片小于 8MB，格式合法
→ 预占当天额度
→ 外发前权限和资源仍有效
→ DashScope 返回合法结构
→ 转为候选营养
→ Coordinator 验证 provider/model
→ CompanionBalance 裁剪
→ 保存真实成长和 VISUAL_MODEL provenance
```

### 场景 B：模型超时

```text
安全取图成功
→ 已预占额度
→ DashScope 超时
→ 转成 VISION_TIMEOUT
→ 白名单允许元数据降级
→ contentUnderstood=false
→ 保存 METADATA_DETERMINISTIC + VISION_TIMEOUT
→ 本次视觉额度不退还
```

### 场景 C：外发前图片撤权

```text
最初权限检查通过
→ 图片字节已经下载
→ 用户权限被撤销
→ verifyStillAuthorized 再检查失败
→ 不调用模型
→ 不允许用元数据绕过权限
→ 本次喂养失败或拒绝，不产生成长事实
```
