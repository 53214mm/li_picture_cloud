### 0.2-B 核心结论

```text
T1 / reserve：短事务登记 PROCESSING，然后立即提交
事务外：权限检查、COS 读取、视觉模型调用
T2 / complete：短事务原子提交伙伴、成长记录和完成回执
T3 / fail 或 reject：前一事务回滚后，用独立新事务记录失败或拒绝
```

`reserve`、`fail`、`reject` 使用 `REQUIRES_NEW`，表示它们拥有独立事务；`complete` 使用一个完整数据库事务保护最终结算。慢速外部调用不进入数据库长事务，因为 MySQL 事务既不能回滚已经发出的模型请求，也不应在等待模型时长期占用连接和锁。

Spring 的 `@Transactional` 通常通过代理生效。当前由 `CompanionLifeService` 调用独立的 `CompanionFeedingCoordinator` Bean，使调用经过事务代理；如果在同一个对象中使用 `this.reserve(...)` 自调用，则可能绕过代理，导致事务传播配置不生效。

## 1. 先从三个事故场景开始

如果没有保护，一次普通喂养可能出现三类事故。

### 场景 A：用户重复点击

```text
第一次请求：经验 +10，但响应在网络中丢失
用户再次点击：经验又 +10
```

用户只想喂一次，伙伴却成长了两次。这是幂等问题。

### 场景 B：两个请求同时完成

```text
请求 A 读到经验 100
请求 B 也读到经验 100
A 计算后写入 110
B 计算后也写入 110
```

理论上应该得到 120，实际只有 110。这是并发丢失更新问题。

### 场景 C：数据库只完成一半

```text
伙伴经验已经更新
成长记录写入失败
FeedingRun 仍然是 PROCESSING
```

用户重试时系统不知道第一次是否成功。这是事务原子性问题。

当前实现不是靠一种机制解决全部问题，而是让多层保护各管一件事。

## 2. 两类记录不要混淆

### `FeedingRun`：请求处理单

它回答：

```text
这次请求是谁发起的？
使用了哪个幂等键？
正在处理、成功、失败还是被拒绝？
重试了几次？
成功结果对应哪条成长记录？
```

它类似外卖订单或支付订单。

### `GrowthRecord`：已经发生的成长事实

它回答：

```text
伙伴实际增加了多少经验？
哪些性格和技能发生了变化？
来源是哪张图片？
分析实际使用了什么来源？
```

它类似交易流水或正式收据。

所以：

```text
FeedingRun = 这次请求处理到哪一步
GrowthRecord = 成长事实上发生了什么
```

成功的 `FeedingRun` 必须指向一条 `GrowthRecord`；没有成长记录却声称 `COMPLETED` 是非法状态。

## 3. `FeedingRun` 状态机

文件：`domain/companion/FeedingRun.java`

```text
                       ┌──────────────┐
            ┌─────────→│  COMPLETED   │  成功终态，可回放旧结果
            │          └──────────────┘
┌───────────┴─┐
│ PROCESSING  │────────→ FAILED          可重试
└───────────┬─┘              │
            │                └────────→ PROCESSING（restart）
            │
            └──────────────→ REJECTED    业务拒绝终态
```

各状态含义：

| 状态 | 含义 | 是否可用同一幂等键继续 |
| --- | --- | --- |
| `PROCESSING` | 有请求正在处理 | 未超时则不能抢占；超时后可以 restart |
| `COMPLETED` | 已成功并有成长记录 | 不再执行，直接回放原结果 |
| `FAILED` | 模型、权限基础设施或提交等暂时失败 | 可以 restart |
| `REJECTED` | 图片不存在、已撤权等业务拒绝 | 不重试，保持拒绝结果 |

为什么 `FAILED` 和 `REJECTED` 分开？

- `FAILED` 常表示暂时性故障，重试可能成功；
- `REJECTED` 表示当前请求本身不被允许，不应该靠自动重试绕过。

领域构造器还强制状态与附带字段一致：

```text
COMPLETED → 必须有 resultGrowthRecordId
FAILED/REJECTED → 必须有安全错误码、文案和时间
其他状态 → 不能携带成长结果 ID
```

这叫领域不变量：非法组合在对象创建时就被拒绝，而不是等接口返回错误数据后才发现。

## 4. 幂等到底是什么意思

幂等不是“请求只能发送一次”，而是：

> 相同业务请求发送多次，最终业务效果仍然只发生一次。

例如：

```text
POST /companion/feed
idempotencyKey = feed_20260826_abcd
pictureId = 8888
```

第一次成功后，客户端因为网络超时重新发送同一个 key。系统应该返回第一次的结果，不能重新分析和加经验。

## 5. 当前幂等保护有五层

### 第一层：客户端提供幂等键

同一次用户操作复用同一个 key；用户真正发起新的喂养时才创建新 key。

### 第二层：参数指纹

服务端根据 `pictureId` 生成 SHA-256 指纹。

如果客户端错误地把相同 key 用到另一张图片：

```text
key = feed_20260826_abcd, pictureId = 8888
key = feed_20260826_abcd, pictureId = 9999
```

系统会报“幂等键已用于另一张图片”，不会把第一张图片的结果冒充为第二张。

### 第三层：数据库唯一键

`companion_feed_run` 有唯一约束：

```sql
UNIQUE (companionId, idempotencyKey)
```

仅靠 Java 中的“先查询、再插入”不能防并发：

```text
请求 A 查询：不存在
请求 B 查询：不存在
请求 A 插入
请求 B 插入
```

数据库唯一键是最终裁判。B 插入冲突后重新读取 A 创建的同一条 run。

### 第四层：状态回放

如果 run 已是 `COMPLETED`：

```text
根据 resultGrowthRecordId 找到原成长记录
→ 重新组装原 FeedPictureResult
→ 不再分析图片
→ 不再修改伙伴
```

需要注意：回放前仍重新检查图片权限。旧成功结果不能成为图片撤权后的越权读取通道。

### 第五层：成长记录唯一键

`companion_growth_record` 对 `feedingRunId` 也有唯一约束：

```sql
UNIQUE (feedingRunId)
```

即使上层逻辑以后出现缺陷，同一个运行也不能插入两条成长事实。

## 6. `reserve` 为什么要先于图片分析

`reserve` 在分析前创建 `PROCESSING` 运行：

```text
短事务 T1：
  查找幂等键
  → 不存在则插入 FeedingRun(PROCESSING)
  → 提交

事务外：
  权限检查
  → 读取图片
  → 调用视觉模型

短事务 T2：
  完成伙伴成长并写回执
  → 提交
```

如果分析完成后才创建 run，两个并发请求都可能已经调用模型并计算成长，幂等保护就太晚了。

先登记还有一个价值：即使模型调用超时，也能看到这次请求曾经开始过，并允许之后安全重试。

## 7. 为什么图片分析不放进数据库事务

调用 COS 或视觉模型可能耗时数秒甚至更久。若整个过程一直开启数据库事务并持有锁：

```text
占用数据库连接
→ 锁住伙伴行
→ 其他请求排队
→ 模型超时时事务也长时间不结束
```

因此代码采用：

```text
reserve 短事务
→ 慢速外部分析不占数据库长事务
→ complete 短事务
```

这也是 `CompanionFeedingCoordinator` 独立存在的主要原因。

## 8. `REQUIRES_NEW` 是什么

`reserve`、`fail`、`reject` 使用：

```java
@Transactional(propagation = Propagation.REQUIRES_NEW)
```

通俗理解：

> 不管调用方将来有没有事务，这个方法都使用一笔独立的新事务，方法成功返回时自己的状态已经提交。

用途：

- `reserve` 返回后，PROCESSING 运行已经真实存在；
- 图片分析失败时，`fail` 可以独立记录失败状态；
- 图片撤权时，`reject` 可以独立记录拒绝状态。

当前 `CompanionLifeService.feed` 本身没有大事务，因此 `REQUIRES_NEW` 也明确表达了设计边界：不要把慢分析意外包进外层事务。

### Spring 代理提醒

`@Transactional` 通常由 Spring AOP 代理实现。外部 Bean 调用 Coordinator 的 public 方法时，调用会经过代理并开启事务。

如果在同一个对象中写：

```java
this.reserve(...);
```

这种自调用通常不会经过 Spring 代理，事务注解可能不生效。把事务方法放进独立的 `CompanionFeedingCoordinator`，也减少了这种自调用陷阱。

## 9. 同一个 key 并发时发生什么

假设请求 A、B 同时使用：

```text
companionId = 10
idempotencyKey = feed_20260826_abcd
```

可能发生：

```text
A 查询：不存在
B 查询：不存在
A 插入 PROCESSING 成功
B 插入命中唯一键冲突
B 捕获 DuplicateKeyException 后重新查询
B 发现 A 的 run 仍在 PROCESSING
B 返回 IN_PROGRESS，不调用分析器
A 继续分析并完成成长
```

如果 B 到达时 A 已经成功，B 得到的是 `REPLAY`，返回 A 的原结果。

因此“同 key 并发”主要由：

```text
数据库唯一键 + FeedingRun 状态
```

解决。

## 10. 不同 key 同时喂同一个伙伴怎么办

假设：

```text
请求 A：图片 8888，key-A
请求 B：图片 9999，key-B
```

它们是两次合法喂养，可以并行分析图片，但不能同时基于旧伙伴状态结算。

`complete` 使用：

```sql
SELECT * FROM companion
WHERE userId = ?
FOR UPDATE
```

效果类似“结算室只有一把钥匙”：

```text
A 获得伙伴行锁并结算
B 等待
A 提交并释放锁
B 重新读取 A 提交后的最新伙伴，再结算
```

这样 B 能看到最新经验、今日上限和重复图片事实。

### 为什么锁必须在事务中

`FOR UPDATE` 只在数据库事务存续期间有意义。事务结束后锁就释放。

因此 `findByOwnerIdForUpdate` 标记为：

```java
@Transactional(propagation = Propagation.MANDATORY)
```

`MANDATORY` 表示：调用它时必须已经存在事务，否则立即报错。这样不会让开发者误以为自己加了锁，实际上查询结束锁就释放了。

## 11. `revision` 和 CAS 是什么

伙伴表和运行表都有 `revision`，可以理解为文档版本号：

```text
最初 revision = 0
成功修改一次 → revision = 1
再修改一次 → revision = 2
```

保存伙伴时 SQL 条件类似：

```sql
UPDATE companion
SET lifeExperience = ?, revision = 1
WHERE id = ? AND revision = 0;
```

如果数据库已经被别人更新到 revision 1，旧请求仍拿 revision 0 更新时，受影响行数是 0，保存失败。

这就是 Compare-And-Set：

```text
只有当前版本仍等于我曾读取的版本，才允许写入新版本。
```

### 行锁和 revision 为什么同时存在

它们职责不同：

| 机制 | 类比 | 作用 |
| --- | --- | --- |
| `FOR UPDATE` | 先拿结算室钥匙 | 主动让同一伙伴的正常结算排队 |
| `revision` CAS | 提交前核对文档版本 | 防止漏锁、过期对象或其他写入路径覆盖新状态 |

行锁是主并发策略，revision 是第二道防线。这里同时使用有明确价值，不是简单重复。

## 12. `complete` 为什么必须是一个事务

最终结算包含：

```text
1. 锁住并读取最新伙伴
2. 查询今日经验和重复喂养事实
3. Companion.feed 计算新快照
4. CAS 保存伙伴和技能
5. 追加 GrowthRecord
6. CAS 把 FeedingRun 改成 COMPLETED
```

这六步都在 `CompanionFeedingCoordinator.complete` 的同一个事务中。

如果第 6 步发现 run 已被其他请求修改：

```text
runRepository.complete(...) 返回 false
→ 抛出异常
→ 整个事务回滚
→ 第 4 步伙伴更新和第 5 步成长记录也一起撤销
```

这保证：

```text
伙伴新快照
+ 成长事实
+ 可回放的完成回执
```

永远作为一个整体提交。

## 13. 失败发生在哪里，怎样记录

### 权限明确拒绝

图片不存在或当前用户无权查看：

```text
PROCESSING → REJECTED
safeErrorCode = PICTURE_UNAVAILABLE
```

### 图片分析失败

模型超时、内容读取失败等：

```text
PROCESSING → FAILED
safeErrorCode = 安全错误码
```

数据库只保存可以展示和审计的安全错误信息，不保存 Token、完整供应商响应或堆栈。

### complete 提交失败

`complete` 的事务先回滚，然后 `CompanionLifeService` 调用独立的 `fail` 事务记录：

```text
FEED_COMMIT_FAILED
```

所以“成长没提交”和“请求运行失败”能够保持一致。

## 14. 超时重启和旧请求问题

假设请求 A 调模型很久没有响应，run 超时后请求 B 使用同一 key 重试：

```text
A 持有 run revision 0
B restart 成功：run revision 1，attemptCount 2
```

此时 A 突然恢复，不能再使用旧 revision 0 完成或标记失败。

运行状态更新条件包含：

```text
id = runId
AND status = 预期旧状态
AND revision = expectedRevision
```

A 的旧 revision 更新会失败。

更关键的是，`transitionTerminal` 不会读取新 revision 后再次强行写失败。它只接受“别人已经完成了相同终态”，否则报告状态已经变化。

这防止旧请求摧毁新请求接管的运行。

## 15. 一张完整时间线

```text
客户端
  │ POST feed(key-1)
  ▼
LifeService
  │
  ├─ T1 / REQUIRES_NEW：reserve
  │      INSERT FeedingRun(PROCESSING, revision=0)
  │      COMMIT
  │
  ├─ 无长事务：检查权限、读取图片、调用分析器
  │
  └─ T2：complete
         SELECT companion FOR UPDATE
         Companion.feed
         UPDATE companion WHERE revision = old
         INSERT growth_record
         UPDATE feeding_run
           SET status=COMPLETED, revision=1
           WHERE status=PROCESSING AND revision=0
         COMMIT

响应丢失后客户端重发 key-1
  → reserve 找到 COMPLETED
  → 重新检查图片权限
  → 读取原 GrowthRecord
  → REPLAY，不再次成长
```

## 16. 哪些复杂度值得保留

本单元涉及的复杂度总体有明确业务理由：

- `FeedingRun`：外部模型调用和网络重试需要持久化运行状态；
- 独立 Coordinator：需要隔离慢调用与数据库短事务；
- 数据库唯一键：解决真正的并发插入竞争；
- 行锁：串行结算每日上限和重复图片规则；
- revision CAS：阻止过期写入；
- 追加式 GrowthRecord：支持回放和审计。

如果这只是一个没有外部调用、没有重试、没有成长审计的简单 CRUD，这套设计会过重。但当前喂养同时涉及模型、额度、权限、并发和审计，因此复杂度基本与风险匹配。
