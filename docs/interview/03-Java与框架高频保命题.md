# Java 与框架高频保命题

> 使用方法：先只看问题并口答，再展开答案。校招回答先保证正确和有结构，不要为了显得高级堆源码名词。

## 一、Java 集合

### 1. ArrayList 和 LinkedList 有什么区别？

**一句话回答：** ArrayList 基于连续数组，随机访问快；LinkedList 基于双向链表，按下标访问慢，已定位节点后的插入删除方便。

**60 秒回答：** ArrayList 查询 `get(index)` 可按下标计算位置，平均 O(1)，尾部追加通常 O(1)，扩容或中间插入需要复制/移动元素。LinkedList 每个节点保存前后指针，按下标访问要遍历 O(n)，节点额外占内存。常见业务大多读多、遍历多，ArrayList 通常更合适；不能笼统说 LinkedList 插入一定快，因为找到插入位置也需要时间。

**常见追问：** ArrayList 怎么扩容？容量不足时创建更大数组并复制；具体倍率属于实现细节。为什么遍历 ArrayList 往往更快？连续内存的缓存局部性更好。

**项目连接点：** 分页结果和权限列表适合 ArrayList；不需要为了“插入快”改用 LinkedList。

### 2. HashMap 的 put/get 流程是什么？

**一句话回答：** HashMap 用 key 的 hash 定位桶，在桶内通过 equals 找具体节点；冲突用链表/红黑树处理。

**60 秒回答：** put 时先计算扰动后的 hash，再通过数组长度定位桶。桶为空直接插入；桶不为空则比较 hash 和 equals，相同 key 覆盖，不同 key 追加到冲突结构。冲突较多且容量达到条件时链表可能树化。达到负载阈值后扩容并重新分布节点。get 使用相同 hash 定位桶，再比较 key。平均 O(1)，极端冲突会退化。

**常见追问：** 为什么长度常为 2 的幂？便于用位运算定位并让扩容迁移更规律。为什么必须同时正确实现 equals/hashCode？equals 相等的对象必须有相同 hash，否则可能落到不同桶。

**项目连接点：** 协同房间 `Map<pictureId, Set<WebSocketSession>>` 需要按 pictureId 快速定位。

### 3. HashMap 为什么线程不安全？

**一句话回答：** 并发 put、扩容和读写没有同步，可能覆盖数据、看到中间状态或产生结构竞争。

**60 秒回答：** HashMap 的数组和节点修改不是原子业务操作，多个线程同时判断桶为空、插入或扩容时会互相覆盖。即便某次运行没报错，也不代表有可见性和一致性保证。并发场景应使用 ConcurrentHashMap，或在外部使用合适同步，但不要简单给所有操作加一个全局大锁。

**常见追问：** Hashtable 呢？方法级 synchronized，粒度较粗且 API 老。只读 HashMap 安全吗？构建完成后安全发布且不再修改才可以讨论并发只读。

### 4. ConcurrentHashMap 怎么保证并发安全？

**一句话回答：** Java 8 主要通过 volatile 可见性、CAS 和桶级 synchronized 控制并发，而不是锁整张表。

**60 秒回答：** 读操作通常不加全局锁，依赖 volatile 读取最新节点；初始化、部分更新用 CAS，桶发生竞争时锁定桶头节点。扩容允许多个线程协助迁移。它提高不同桶并发能力，但复合操作仍要使用 `compute`、`putIfAbsent` 等原子 API，不能先 get 再 put 就认为整体原子。

**常见追问：** 能存 null 吗？不能，避免并发下无法区分 key 不存在还是 value 为 null。

**项目连接点：** WebSocketHandler 用 ConcurrentHashMap 保存本实例图片房间，并用并发 Set 保存连接。

### 5. equals 和 hashCode 有什么约定？

**一句话回答：** equals 相等的对象 hashCode 必须相等；hashCode 相等不代表 equals 相等。

**60 秒回答：** Hash 容器先用 hash 定位候选桶，再用 equals 判定逻辑相等。如果只重写 equals 不重写 hashCode，两个相等对象可能落入不同桶，导致查找或去重失败。作为 Map key 的对象还应尽量不可变，否则插入后修改参与 hash 的字段会找不到原记录。

**常见追问：** `==` 和 equals？基本类型 `==` 比值；引用类型 `==` 比地址，equals 可定义逻辑相等。

## 二、并发与线程池

### 6. 创建线程有哪些方式？

**一句话回答：** 可以继承 Thread、实现 Runnable/Callable，实际业务通常把任务提交给线程池。

**60 秒回答：** Runnable 无返回值，Callable 可返回结果并抛异常，Future 获取执行结果。直接不断 new Thread 会造成线程创建销毁开销和资源失控，服务端更常用 ThreadPoolExecutor 复用线程并限制并发。

**常见追问：** `start` 和 `run`？start 创建并调度新线程，直接 run 只是当前线程普通方法调用。

### 7. ThreadPoolExecutor 七个核心参数是什么？

**一句话回答：** 核心线程数、最大线程数、空闲时间、时间单位、任务队列、线程工厂、拒绝策略。

**60 秒回答：** 新任务先创建核心线程；核心线程满后进入队列；队列满且未达最大线程数时再创建非核心线程；全部达到上限后触发拒绝策略。线程工厂用于命名、优先级和异常处理。选择参数要看任务是 CPU 密集还是 IO 密集、允许的延迟、队列长度和下游容量。

**常见追问：** 为什么不推荐 Executors 默认工厂？部分方法使用无界队列或极大线程上限，可能 OOM。四种拒绝策略？抛异常、调用者执行、丢弃、丢弃最旧任务。

**项目连接点：** 外部图片抓取或 AI 调用若异步化，线程池必须限制并发，不能无限提交压垮 COS/AI 下游。

### 8. synchronized 和 ReentrantLock 有什么区别？

**一句话回答：** 两者都能互斥；synchronized 语法简单并自动释放，ReentrantLock 支持可中断、超时、公平锁和多个 Condition。

**60 秒回答：** synchronized 由 JVM 管理 monitor，退出代码块自动释放，适合大多数互斥场景。ReentrantLock 是显式锁，必须在 finally unlock，功能更丰富。两者都有可重入和内存可见性语义。选型先用简单正确的 synchronized，确实需要高级能力再用 Lock。

**常见追问：** 可重入是什么？同一线程获得锁后可以再次进入同一锁保护区域，内部记录持有次数。

**项目连接点：** WebSocket 向同一 Session 发送消息时同步 session，避免并发写同一连接。

### 9. volatile 能保证什么？

**一句话回答：** volatile 保证可见性和一定的有序性，不保证 `i++` 这类复合操作原子性。

**60 秒回答：** 一个线程写 volatile 后，其他线程读能看到最新值；它还通过内存屏障限制相关指令重排。`i++` 包含读、计算、写，多线程仍可能丢更新。状态标志适合 volatile，计数可用 AtomicInteger、锁或数据库/Redis 原子操作。

**常见追问：** 双重检查单例为什么需要 volatile？防止对象初始化与引用赋值重排，使其他线程看到未完全构造对象。

### 10. 什么是 JMM？

**一句话回答：** Java Memory Model 定义线程如何通过主内存交互，以及原子性、可见性、有序性和 happens-before 规则。

**60 秒回答：** 线程可能把共享变量缓存在工作内存，编译器和 CPU 也可能重排。JMM 不描述具体硬件，而规定同步语义。例如解锁 happens-before 后续对同一锁的加锁；volatile 写 happens-before 后续读；线程 start/join 也有规则。正确同步后，程序才能获得跨平台一致行为。

**常见追问：** happens-before 等于时间先后吗？不是单纯物理时间，而是保证结果可见的偏序关系。

### 11. CAS 是什么？ABA 怎么办？

**一句话回答：** CAS 比较内存值是否仍为预期值，相同才写入；ABA 可通过版本戳解决。

**60 秒回答：** CAS 是乐观并发原语，成功则更新，失败通常重试。低竞争时避免阻塞，高竞争时自旋消耗 CPU，而且只能直接处理有限状态。ABA 指值 A 变 B 又变 A，单看值没发现变化，可使用 AtomicStampedReference 或业务版本号。

**项目连接点：** 协同的 expectedVersion 类似业务级乐观锁，比只比较旋转角度更能识别中间变化。

### 12. ThreadLocal 有什么用和风险？

**一句话回答：** ThreadLocal 为每个线程保存独立变量副本，线程池中不 remove 可能造成数据串用和内存滞留。

**60 秒回答：** 数据实际存在线程的 ThreadLocalMap。Web 请求中可保存当前上下文，但在线程池里线程会复用，必须 finally remove。异步切换线程也不会天然传播，需要显式传递，不能把 ThreadLocal 当分布式 Session。

### 13. 死锁的四个必要条件？如何排查？

**一句话回答：** 互斥、持有并等待、不可剥夺、循环等待；可用线程 dump 看互相等待的锁。

**60 秒回答：** 预防通常破坏循环等待，例如统一锁顺序，或使用超时尝试锁。排查使用 jstack/JFR/监控查看 BLOCKED 线程、锁拥有者和调用栈，不要只重启掩盖问题。

## 三、JVM 与异常

### 14. JVM 运行时内存有哪些区域？

**一句话回答：** 线程私有有程序计数器、虚拟机栈、本地方法栈；共享区域主要有堆和方法区/元空间。

**60 秒回答：** 堆保存大多数对象，是 GC 重点区域；栈由栈帧组成，包含局部变量、操作数栈和返回信息；程序计数器记录当前指令位置；元空间保存类元数据并使用本地内存。直接内存也常影响进程内存，但不等同于 JVM 堆。

**常见追问：** 栈溢出和堆 OOM？递归过深可能 StackOverflowError；对象持续存活可能 Java heap space。

### 15. 一个对象创建的大致过程？

**一句话回答：** 检查类是否加载，分配内存，零值初始化，设置对象头，执行构造逻辑，最后安全发布引用。

**60 秒回答：** `new` 触发类加载检查，在堆中通过指针碰撞或空闲列表分配，处理并发后初始化零值和对象头，再执行 `<init>`。逃逸分析可能允许标量替换等优化，不能绝对说所有对象物理上都长期留在堆。

### 16. 类加载过程和双亲委派？

**一句话回答：** 类经历加载、验证、准备、解析、初始化；双亲委派先让父加载器尝试，避免核心类被重复或恶意替换。

**60 秒回答：** 加载取得字节码并创建 Class；验证保证格式与安全；准备给静态变量分配并设零值；解析把符号引用转直接引用；初始化执行静态赋值和静态块。双亲委派不是所有场景绝对不破坏，SPI、容器和模块化可能使用上下文类加载器等机制。

### 17. GC Roots 有哪些？

**一句话回答：** 常见 Roots 包括栈中的引用、静态字段、常量引用、JNI 引用和活跃线程相关对象。

**60 秒回答：** 可达性分析从 GC Roots 遍历引用图，不可达对象才有机会回收。年轻代通常使用复制思想，老年代根据收集器使用标记整理或区域化算法。校招先讲可达性和代际假设，不要背收集器参数大全。

### 18. 常见 OOM 如何区分？

**一句话回答：** 堆、元空间、直接内存和无法创建线程都可能 OOM，需要结合错误信息、监控和 dump 判断。

**60 秒回答：** 堆 OOM 查看对象增长和引用链；Metaspace 检查动态类加载；Direct buffer memory 检查 NIO/Netty 缓冲；unable to create native thread 检查线程数和系统限制。项目容器退出 137 还可能是宿主机 OOM Killer，不一定出现 Java heap space。

**项目连接点：** Compose 为后端设置内存上限，排障要看 `OOMKilled`、退出码、`docker stats` 和 dmesg。

### 19. Checked Exception 和 RuntimeException？

**一句话回答：** Checked Exception 编译期要求处理；RuntimeException 通常表示编程或业务运行错误，不强制捕获。

**60 秒回答：** 项目业务异常继承运行时异常，由全局处理器统一转响应，也便于 Spring 事务默认回滚。异常不能吞掉，外部错误应记录必要上下文，但返回用户时隐藏密钥、SQL、堆栈等内部细节。

### 20. finally 一定执行吗？

**一句话回答：** 通常执行，但进程退出、JVM 崩溃、线程被强制终止等情况可能不执行；不要在 finally return。

**60 秒回答：** try/catch return 前会先执行 finally，finally 的 return 还会覆盖原返回值或异常，导致排障困难。资源优先使用 try-with-resources。

## 四、Spring 与 Spring Boot

### 21. IOC 和 DI 是什么？

**一句话回答：** IOC 把对象创建和依赖管理交给容器，DI 是容器把依赖注入对象的实现方式。

**60 秒回答：** 业务类只声明需要什么接口，容器负责创建 Bean、解析依赖、管理生命周期，降低手工 new 的耦合。推荐构造器注入，因为依赖明确、对象可保持完整，也方便单元测试替换依赖。

**项目连接点：** Controller、Service、Mapper、RedisTemplate 和授权服务均由 Spring 容器装配。

### 22. AOP 是什么？

**一句话回答：** AOP 用代理把日志、权限、事务、限流等横切逻辑织入目标方法，避免散落重复代码。

**60 秒回答：** Spring AOP 主要基于 JDK 动态代理或 CGLIB 子类代理。调用代理对象时，拦截器链在目标方法前后执行。内部 `this.method()` 没经过代理是事务/切面失效常见原因。

**项目连接点：** `@AuthCheck`、空间权限注解和 Redis 限流切面属于横切能力。

### 23. JDK 代理和 CGLIB 区别？

**一句话回答：** JDK 代理基于接口，CGLIB 通过生成目标类子类代理，final 类/方法不能被其覆盖。

**60 秒回答：** Spring 会根据目标类型和配置选择代理方式。面试重点不是背默认细节，而是理解调用必须经过代理、final/私有方法限制以及自调用问题。

### 24. Bean 生命周期怎么说？

**一句话回答：** 实例化、属性填充、Aware 回调、前置处理、初始化、后置处理、使用、销毁。

**60 秒回答：** 容器创建对象后注入依赖，执行 Aware 与 BeanPostProcessor，在初始化前后可增强并可能返回代理；单例 Bean 在容器关闭时执行销毁回调。循环依赖、代理和后处理器都发生在这个大流程里。

### 25. 单例 Bean 线程安全吗？

**一句话回答：** Spring 单例只保证容器内一个实例，不自动保证线程安全；无可变共享状态通常安全。

**60 秒回答：** Service 如果只使用局部变量并调用线程安全依赖，一般可并发；把请求用户、临时 List 放成员字段就可能串数据。项目曾遇到的 MCP 共享回调污染，本质上也与共享对象被请求上下文修改有关。

### 26. `@Transactional` 为什么会失效？

**一句话回答：** 常见原因有自调用未经过代理、方法不可代理、异常被吞、抛出不回滚的异常类型、对象不是 Spring Bean、切换线程。

**60 秒回答：** Spring 声明式事务通常由代理在方法前开启、正常返回提交、异常时按规则回滚。`this.method()` 绕过代理；catch 后不抛使代理认为成功；默认主要对 RuntimeException/Error 回滚；异步线程不继承原事务。

**项目连接点：** 图片记录和空间额度更新放在 TransactionTemplate 中保证数据库内部一致，但 COS 外部上传不属于数据库事务。

### 27. Spring Boot 自动配置怎么回答？

**一句话回答：** 启动时导入自动配置候选，再用 classpath、配置属性和已有 Bean 等条件决定哪些配置生效。

**60 秒回答：** `@SpringBootApplication` 组合配置、扫描和自动配置。Starter 提供依赖，自动配置类使用 `@ConditionalOnClass`、`@ConditionalOnProperty`、`@ConditionalOnMissingBean` 等条件创建默认 Bean，用户自定义时可覆盖。排障可看启动日志和 Condition Evaluation Report。

## 五、MySQL

### 28. 为什么索引用 B+Tree？

**一句话回答：** B+Tree 分支多、树高低，非叶节点只存键，叶子有序且相连，适合磁盘页、范围查询和排序。

**60 秒回答：** 数据库一次 IO 读取页，B+Tree 高扇出减少 IO；所有数据定位到叶子，叶子链表支持范围扫描。Hash 适合等值但不支持范围和有序访问。索引不是越多越好，会占空间并增加写维护成本。

### 29. 聚簇索引、二级索引、回表、覆盖索引？

**一句话回答：** InnoDB 聚簇索引叶子保存整行，二级索引叶子保存索引列和主键；再查整行叫回表，索引已含所需列叫覆盖索引。

**60 秒回答：** 主键查询直接走聚簇树；普通索引先得到主键，再访问聚簇树。只查询二级索引包含的列可以避免回表。主键宜短且稳定，随机超长键会增加所有二级索引体积。

### 30. 联合索引和最左前缀？

**一句话回答：** 联合索引按定义列顺序排序，查询要从最左列开始形成连续可利用前缀，范围条件后的列通常难继续用于定位。

**60 秒回答：** `(a,b,c)` 可支持 `a`、`a,b`、`a,b,c` 等前缀。优化器可能重排等值条件书写顺序，但不能凭空跳过最左列。设计索引要看真实 WHERE、ORDER BY、选择性和覆盖需求。

### 31. ACID 和隔离级别？

**一句话回答：** ACID 是原子、一致、隔离、持久；隔离级别从读未提交、读已提交、可重复读到串行化逐步增强。

**60 秒回答：** InnoDB 默认常见为可重复读，通过 MVCC 和锁处理并发。级别越高通常并发代价越大。隔离级别解决读现象，不自动解决所有业务并发，例如余额扣减仍需条件更新、锁或乐观版本。

### 32. MVCC 是什么？

**一句话回答：** MVCC 通过事务版本、Read View 和 Undo Log，让一致性读看到适合自己的历史版本，减少读写阻塞。

**60 秒回答：** 行记录含隐藏事务信息，更新产生 Undo 版本链。Read View 根据活跃事务判断哪个版本可见。读已提交通常每次语句生成视图，可重复读通常事务内复用视图；当前读如 `for update` 仍会读最新并加锁。

### 33. INNER JOIN 和 LEFT JOIN？

**一句话回答：** INNER JOIN 只保留两侧匹配行；LEFT JOIN 保留左表全部行，右侧不匹配列为 null。

**60 秒回答：** 例如查询所有空间和可选成员数，LEFT JOIN 能保留没有成员的空间；只查询有成员的空间可用 INNER JOIN。连接列应有合适索引，注意一对多会放大行数，聚合前要理解重复。

```sql
SELECT s.id, s.spaceName, su.userId, su.spaceRole
FROM space s
LEFT JOIN space_user su ON su.spaceId = s.id
WHERE s.userId = ?;
```

### 34. 怎么排查慢 SQL？

**一句话回答：** 先用慢日志和指标找到 SQL，再用 EXPLAIN 看扫描、索引、行数、排序和临时表，结合数据分布改查询或索引并复测。

**60 秒回答：** 不要看到全表扫就立刻加索引。先确认频率和耗时，检查返回行数、过滤条件、联合索引顺序、隐式转换、函数、排序分页。改后比较执行计划和真实耗时，同时考虑写入成本。

## 六、Redis

### 35. Redis 常用数据结构？

**一句话回答：** String、Hash、List、Set、ZSet，以及 Stream、Bitmap、HyperLogLog、Geo 等扩展结构。

**60 秒回答：** String 适合缓存和计数；Hash 适合对象字段；List 适合有序队列但可靠消费要谨慎；Set 去重和集合运算；ZSet 按分值排序。选结构看访问模式，不要把所有对象都 JSON String 化。

**项目连接点：** 协同状态用 Hash，命令结果用 String，事件用 Pub/Sub，Session/AI 记忆使用各自序列化结构。

### 36. RDB 和 AOF？

**一句话回答：** RDB 周期生成快照，恢复快但可能丢最近数据；AOF 记录写命令，数据更完整但文件与恢复成本更高。

**60 秒回答：** Redis 可组合使用。实际选择看数据能否重建、允许丢失窗口和恢复目标。缓存可接受丢失，登录态和协同临时状态也要结合 TTL 与业务恢复策略。

### 37. 过期删除和内存淘汰？

**一句话回答：** 过期键主要通过惰性删除和定期抽样删除；达到 maxmemory 后按配置的 eviction policy 淘汰。

**60 秒回答：** TTL 到期不一定在同一毫秒物理删除，访问时检查并由后台周期清理。淘汰可在 allkeys/volatile 范围使用 LRU、LFU、random、TTL 或 noeviction。生产配置要避免把不能丢的数据与纯缓存混在随意淘汰实例里。

### 38. 缓存穿透、击穿、雪崩？

**一句话回答：** 穿透是查不存在数据；击穿是热点键失效时并发回源；雪崩是大量键同时失效或 Redis 故障造成大面积回源。

**60 秒回答：** 穿透可缓存空值、布隆过滤和参数校验；击穿可互斥重建、逻辑过期或热点不过期；雪崩可随机 TTL、多级缓存、限流降级和高可用。方案要防止锁失败和空值污染。

**项目连接点：** 图片查询有 Caffeine + Redis 二级缓存，Redis 异常时可降级回源数据库，但高流量下仍需限流防雪崩。

### 39. 数据库与缓存一致性怎么做？

**一句话回答：** 常见做法是更新数据库后删除缓存，配合 TTL、重试和幂等；强一致需要更高成本方案。

**60 秒回答：** 先更新数据库再删缓存仍存在删除失败窗口，应记录和重试；先删缓存再写库可能被并发旧查询回填。可用延迟双删、消息/CDC 做最终一致，但复杂度更高。项目通过版本化缓存键或清理策略让旧缓存失效，并允许 Redis 失败时回源。

### 40. Redis 为什么快？

**一句话回答：** 内存访问、高效数据结构、事件驱动网络模型和命令执行路径短共同作用，不能只回答“单线程”。

**60 秒回答：** Redis 大多数数据在内存，核心命令避免磁盘随机 IO；数据结构针对场景优化；IO 多路复用处理连接；核心命令串行减少锁竞争。现代 Redis 还可能用线程处理网络 IO，持久化也有后台过程。

## 七、Day 4 专项：网络与线程安全集合

> Day 4 先掌握“为什么这样设计”和“项目里怎么用”，不必背 TCP 报文全部字段，也不要一上来展开内核源码。

### D4-1. TCP 和 UDP 有什么区别？

**一句话回答：** TCP 面向连接、可靠、有序、按字节流传输；UDP 无连接、尽力而为、按数据报传输，开销更小但不保证到达和顺序。

**60 秒回答：** TCP 通信前先建立连接，通过序号、确认应答、超时重传、流量控制和拥塞控制等机制提高可靠性，接收方看到的是连续字节流，应用层要自己解决消息边界。UDP 每个数据报有边界，不需要建立连接，但可能丢包、乱序或重复。文件传输、HTTP 和 WebSocket 通常需要 TCP 的可靠性；实时音视频、在线游戏或 DNS 等更看重低延迟，并能在应用层容忍或处理少量丢包时可能使用 UDP。不能简单说 UDP 一定比 TCP 快，实际还取决于网络、协议实现和业务重传策略。

**常见追问：** TCP 是否百分百不会丢数据？TCP会尽力重传并向应用提供可靠字节流，但进程崩溃、连接异常和应用未正确处理仍可能造成业务数据丢失，所以关键业务还需要确认、幂等和持久化。TCP为什么会粘包？因为它没有消息边界，应用协议要使用固定长度、分隔符或长度字段拆包。

**项目连接点：** LiPictureCloud 的 HTTPS 和 WebSocket 都建立在可靠传输之上；WebSocket定义消息帧边界，而底层TCP只负责传输字节。

### D4-2. TCP 为什么需要三次握手？

**一句话回答：** 三次握手让双方都确认自己的发送和接收能力正常，并同步初始序号，避免历史失效连接被误当成新连接。

**60 秒回答：** 第一次客户端发送 SYN 和自己的初始序号，表示希望建立连接；第二次服务端回复 SYN+ACK，确认收到了客户端请求，同时发送自己的初始序号；第三次客户端回复 ACK，确认收到了服务端的响应。完成后，客户端和服务端都能确认双向通信能力，并完成双方序号同步。只有两次时，服务端无法确认自己的 SYN+ACK 是否真正到达客户端，也更难避免网络中滞留的旧 SYN 让服务端错误建立连接和分配资源。

```text
客户端                         服务端
  | -------- SYN ------------> |
  | <----- SYN + ACK ---------- |
  | -------- ACK -------------> |
  |        连接建立              |
```

**常见追问：** 第三次握手能携带数据吗？协议允许在连接状态满足条件后携带，但面试重点是第三次确认服务端的响应已到达。SYN Flood是什么？攻击者发送大量SYN但不完成握手，占用服务端半连接资源，可通过SYN Cookie等手段缓解。

### D4-3. TCP 为什么通常四次挥手？`TIME_WAIT` 和 `CLOSE_WAIT` 是什么？

**一句话回答：** TCP 是全双工连接，双方的发送方向需要分别关闭；主动关闭方通常进入 `TIME_WAIT`，被动关闭方收到 FIN 后在应用尚未关闭连接时处于 `CLOSE_WAIT`。

**60 秒回答：** 主动关闭方先发送 FIN，表示自己不再发送数据；对方先回复 ACK，但此时仍可能有数据需要发送，等发送完成后再发 FIN；主动关闭方最后回复 ACK，因此通常是四次挥手。`TIME_WAIT` 用来确保最后一个 ACK 丢失时还能重发，并让旧连接报文在网络中消失，避免影响相同四元组的新连接。大量 `CLOSE_WAIT` 往往说明本地应用收到了对方关闭通知，却没有及时调用 close 释放连接；大量 `TIME_WAIT` 不一定是故障，要结合主动关闭方、连接复用和数量判断。

```text
主动关闭方                      被动关闭方
  | -------- FIN -------------> |
  | <------- ACK -------------- |
  | <------- FIN -------------- |
  | -------- ACK -------------> |
  |       TIME_WAIT              |
```

**常见追问：** 为什么服务端的 ACK 和 FIN 有时可以合并？如果服务端收到FIN时也已经没有数据需要发送，可以同时确认并关闭自己的发送方向，报文数量可能少于四个；“四次挥手”是典型流程，不是每次抓包绝对四个独立报文。

### D4-4. HTTP 有什么特点？一次请求大致经历什么？

**一句话回答：** HTTP 是应用层请求—响应协议，本身无状态；浏览器发送方法、路径、请求头和可选请求体，服务器返回状态码、响应头和响应体。

**60 秒回答：** 用户访问URL时，通常先进行DNS解析，再与目标服务器建立底层连接；HTTPS还要进行TLS握手。请求到达Nginx后被反向代理到Spring Boot，进入Servlet容器和 `DispatcherServlet`，随后执行拦截器、Controller、Service和Mapper，最终将JSON响应返回浏览器。HTTP无状态表示协议本身不会天然记住上一次请求的用户身份，项目通过Cookie携带Session标识，再从Redis等服务端存储恢复登录状态。HTTP/1.1默认支持持久连接，不等于每次请求都新建TCP连接。

**常见追问：** 无状态是否表示服务器绝对不能保存状态？不是。它表示每个HTTP请求在协议语义上应携带处理所需信息，服务器仍可使用Session、数据库和Redis保存业务状态。Cookie与Session有什么区别？Cookie由浏览器保存并随请求发送，Session通常保存在服务端，Cookie中常只携带会话标识。

**项目连接点：** 请求链可以概括为“浏览器 → Nginx → DispatcherServlet → Controller → Service → Mapper”，登录Cookie用于恢复Sa-Token会话。

### D4-5. HTTP 方法、幂等性、状态码和长连接怎么回答？

**一句话回答：** GET用于读取，POST常用于创建或执行命令，PUT倾向整体替换，PATCH倾向部分修改，DELETE用于删除；幂等表示同一请求执行一次和多次对服务端最终状态的影响相同。

**60 秒回答：** GET、PUT和DELETE在HTTP语义上应设计为幂等，POST通常不保证幂等，但真实业务仍要用请求ID、唯一索引或状态机处理重复提交。幂等不代表每次响应必须完全相同，例如重复DELETE第一次返回成功、第二次返回不存在，但资源最终都处于删除状态。常见状态码包括200成功、201创建成功、204成功但无响应体、400参数错误、401未认证、403已认证但无权限、404资源不存在、409状态冲突、429请求过多和500服务端未知异常。HTTP/1.1的持久连接允许多个请求复用TCP连接；HTTP仍然通常是一问一答，WebSocket才提供连接建立后的双向主动消息。

**常见追问：** GET一定没有请求体吗？规范和实现可能允许，但很多网关、缓存和客户端不可靠支持，因此查询参数通常放URL。POST能否做幂等？可以，幂等性是业务设计能力，不是POST绝对做不到。

### D4-6. HTTP/1.1、HTTP/2 和 HTTPS 有什么区别？

**一句话回答：** HTTP/1.1支持持久连接但容易出现应用层队头阻塞；HTTP/2使用二进制分帧和多路复用；HTTPS是在HTTP与TCP之间增加TLS，提供加密、完整性校验和服务器身份认证。

**60 秒回答：** HTTP/1.1可以复用连接，但同一连接上的响应顺序和并发能力有限，浏览器常建立多个连接。HTTP/2把消息拆成二进制帧，在一个TCP连接中并发传输多个流，并支持头部压缩；但底层仍是TCP，一个TCP丢包仍可能影响该连接上的多个流。HTTPS通过TLS协商密钥，使用证书验证服务器身份，之后用对称加密保护传输内容，并用完整性机制防止报文被篡改。HTTPS不能防止服务器自身泄露数据，也不能代替后端认证授权。

**常见追问：** HTTPS为什么不是只用非对称加密？非对称加密计算成本高，TLS主要用它完成身份认证和密钥协商，实际大量数据使用更高效的对称加密。HTTP/2是否彻底消除队头阻塞？它解决了HTTP/1.1应用层的队头阻塞，但TCP层丢包仍可能阻塞同连接数据；HTTP/3改用QUIC进一步处理这个问题。

**项目连接点：** 生产环境由Nginx统一终止TLS，浏览器通过 `https://lipicturecloud.com` 访问，内部再反向代理到前后端容器。

### D4-7. WebSocket 如何通过 HTTP Upgrade 建立连接？

**一句话回答：** WebSocket先发送HTTP Upgrade握手，服务端返回 `101 Switching Protocols` 后，连接切换为WebSocket帧通信，并继续复用底层TCP连接。

**60 秒回答：** 浏览器先发送带有 `Upgrade: websocket` 和 `Connection: Upgrade` 等请求头的HTTP握手。Nginx必须保留这些升级头并使用合适的HTTP代理配置。服务端校验请求、身份和加入权限后返回101，之后这条连接不再按普通HTTP的一次请求一次响应处理，而是双方持续收发WebSocket帧。握手阶段可以使用HTTP Cookie和Session恢复用户身份；连接建立后的编辑消息不再经过 `DispatcherServlet` 和MVC `HandlerInterceptor`，必须由WebSocket处理器继续校验消息和资源权限。

```text
HTTP Upgrade 握手 → 101 Switching Protocols
                     ↓
              WebSocket 双向消息帧
                     ↓
                 底层 TCP
```

**常见追问：** WebSocket和长轮询的区别？长轮询仍是服务器挂起一个HTTP请求，响应后需要重新请求；WebSocket握手后维持双向连接，服务端可以主动推送。WebSocket是不是消息队列？不是，它解决客户端和服务器实时双向通信；消息队列解决服务端组件间的异步解耦、缓冲和可靠消费。

**项目连接点：** LiPictureCloud在握手时校验 `collaboration:join`，在编辑消息到达时再校验 `collaboration:edit`；viewer可以连接并观看，但不能发送有效编辑命令。

### D4-8. Java 常见线程安全集合应该怎么选？

**一句话回答：** 并发Map优先考虑ConcurrentHashMap，读多写少列表可考虑CopyOnWriteArrayList，生产者消费者使用BlockingQueue，普通集合的同步包装适合简单低并发场景。

**60 秒回答：** 选型先看访问模式，而不是看到多线程就统一加锁。ConcurrentHashMap允许较高并发的Map访问；CopyOnWriteArrayList每次写入复制底层数组，读取不加锁且快照迭代稳定，适合读远多于写、元素较少的监听器列表；BlockingQueue提供阻塞式放入和取出，适合线程间任务交接和生产者消费者。`Collections.synchronizedList`、`synchronizedMap` 使用统一互斥锁包装普通集合，简单但锁粒度较粗，而且遍历时仍要按其约定在外部同步。线程安全集合只保证它承诺的单次操作，跨多个操作的业务不变量仍需原子API或额外同步。

**常见追问：** `Vector` 和 `Hashtable` 呢？它们是较老的同步容器，许多方法使用同一把锁，现代代码通常根据访问模式选择并发集合。是否可以用 `Collections.synchronizedList` 后直接无锁迭代？不应这样做，迭代期间需要按包装对象的约定同步，否则仍可能出现并发问题。

### D4-9. ConcurrentHashMap 为什么线程安全？复合操作有什么坑？

**一句话回答：** Java 8的ConcurrentHashMap综合使用volatile、CAS和桶级同步保证并发访问，但“线程安全的单个方法”不代表多个方法组合后仍然原子。

**60 秒回答：** ConcurrentHashMap读取通常不锁整张表，依靠volatile等可见性机制读取节点；初始化和部分更新使用CAS，发生桶竞争时对桶头进行较细粒度同步，扩容时多个线程还可以协助迁移。不同桶可并发更新，因此吞吐通常高于整表锁。下面的“先检查再写入”不是原子操作：

```java
if (!map.containsKey(key)) {
    map.put(key, value);
}
```

两个线程可能同时判断不存在并分别执行。应该根据语义使用 `putIfAbsent`、`computeIfAbsent`、`compute` 或 `merge` 等原子API。回调函数应短小，避免阻塞、递归修改同一映射或执行耗时网络调用。

**常见追问：** ConcurrentHashMap为什么不允许null？并发环境下 `get(key) == null` 需要明确表示键不存在；若允许null，就难以区分键不存在和值本身为null。它是否保证遍历期间完全不变化？迭代器是弱一致性的，可以反映部分并发修改，但不会给出整个Map某一瞬间的强快照。

**项目连接点：** 协同房间可使用 `computeIfAbsent(pictureId, ...)` 原子创建本机连接集合，不能用“先get、为空再put”假装整体线程安全。

### D4-10. CopyOnWriteArrayList、BlockingQueue 和 ThreadLocal 各适合什么场景？

**一句话回答：** CopyOnWriteArrayList解决读多写少的共享列表，BlockingQueue负责线程间任务交接，ThreadLocal为每个线程隔离上下文；三者解决的问题不同。

**60 秒回答：** CopyOnWriteArrayList写入时复制数组并替换引用，读操作和快照迭代开销低，但高频写会产生复制成本和大量临时数组，因此不适合频繁增删的大列表。BlockingQueue的 `put/take` 可以在队列满或空时阻塞，常用于生产者消费者和线程池，但它通常只在单进程内存中，不具备Kafka、RabbitMQ那样的跨进程持久化、确认和重放能力。ThreadLocal不是集合选型，而是把值绑定到当前线程；线程池会复用线程，所以必须在 `finally` 中 `remove()`，否则可能把上一个请求的上下文泄漏给下一个请求，异步切线程时也不会自动传播。

```java
try {
    requestContext.set(context);
    // 执行业务
} finally {
    requestContext.remove();
}
```

**常见追问：** CopyOnWriteArrayList迭代时能看到刚写入的数据吗？已有迭代器读取创建时的数组快照，不保证看到之后的修改。BlockingQueue能代替Redis Pub/Sub吗？不能，它主要解决单JVM线程协作；Redis Pub/Sub可以跨实例传播事件，但本身也不提供可靠消息积压和重放。

**项目连接点：** WebSocket房间的连接集合要结合加入、移除和广播频率选型；连接很多且频繁变化时不能因为“遍历方便”就盲目使用CopyOnWriteArrayList。

## 八、最后 20 分钟速记

如果马上面试，只复述下面 19 句：

1. HashMap 用 hash 定位桶、equals 定位节点，冲突用链表/红黑树。
2. ConcurrentHashMap 依靠 volatile、CAS 和桶级锁，复合操作要用原子 API。
3. 线程池先核心线程、再队列、再最大线程、最后拒绝。
4. volatile 保证可见性和有序性，不保证复合操作原子性。
5. JMM 用 happens-before 规定线程间可见性。
6. 堆存对象，栈存栈帧，元空间存类元数据。
7. IOC 管对象，AOP 用代理处理横切逻辑。
8. Spring 事务常因自调用、吞异常和异步线程失效。
9. 自动配置依据 classpath、配置和已有 Bean 条件生效。
10. B+Tree 适合磁盘页和范围查询，二级索引可能回表。
11. MVCC 用 Read View 和 Undo 版本链支持一致性读。
12. 穿透查不存在、击穿打热点、雪崩大面积同时回源。
13. TCP 是可靠有序的字节流，UDP 是无连接的尽力而为数据报。
14. 三次握手确认双方收发能力并同步序号，典型四次挥手分别关闭两个发送方向。
15. TIME_WAIT 多见于主动关闭方，CLOSE_WAIT 堆积常说明应用没有及时关闭连接。
16. HTTP 是无状态的请求—响应协议，状态通过 Cookie、Session、Token 等机制补充。
17. HTTPS 使用 TLS 提供加密、完整性和服务器身份认证，但不能代替业务授权。
18. WebSocket 先经 HTTP Upgrade 返回 101，再在同一 TCP 连接上双向传输消息帧。
19. 并发集合按访问模式选：Map用ConcurrentHashMap，读多写少列表考虑CopyOnWriteArrayList，任务交接用BlockingQueue。
