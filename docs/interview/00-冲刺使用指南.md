# LiPictureCloud 校招面试冲刺使用指南

> 适用对象：Java 后端实习/校招；准备周期：10 天；每天：5～6 小时。

## 先稳住：你不是从零开始

你已经具备表设计、索引选择、CRUD、业务逻辑、接口开发、Redis 缓存和 AI Agent 实践能力。当前真正的短板是：知道功能怎么做，却不容易把 Spring、WebSocket、Lua、ShardingSphere 和 Java 基础讲成一条清楚的逻辑链。

这十天不追求“所有源码都懂”。目标是把已有项目经验变成面试官听得懂、经得住追问、又不夸大的表达。

## 最低完成标准

十天结束时，至少做到：

- [ ] 能脱稿讲完 2 分钟项目介绍。
- [ ] 能画出普通请求、图片上传、协同编辑和 AI 生图四条数据流。
- [ ] 能回答每个红色必补技术的一句话定义和项目用途。
- [ ] 每个核心项目亮点至少完成 L1～L3 三层追问。
- [ ] 三套模拟卷中至少两套达到 60 分。
- [ ] 遇到不会的问题能说明边界，不编造源码、数据或生产规模。

60 分不是“稳拿 Offer”，而是说明你已经避免大面积空白，可以边投递边复盘。

## 四级学习优先级

### 红色必补：不会就容易在基础面失守

- Java：HashMap、ArrayList、ConcurrentHashMap、线程池、锁、JMM、JVM 内存结构、GC、异常。
- Spring：IOC、AOP、Bean 生命周期、事务与事务失效。
- Spring Boot：启动流程、自动配置、条件装配、配置加载。
- WebSocket：HTTP Upgrade、握手、长连接、Session、消息处理和重连。
- ShardingSphere：分片键、逻辑表、真实表、路由、静态/动态分表、关闭分表。

要求：能说一句话定义，能结合项目说用途，能回答至少两个追问。

### 黄色项目强化：会用，但要讲清原理和取舍

- Redis 缓存穿透、击穿、雪崩、双写一致性、过期与淘汰。
- Redis Lua、版本号、命令幂等、Pub/Sub。
- MySQL 索引、事务、MVCC、INNER JOIN、LEFT JOIN、慢查询。
- Spring MVC 一次请求链路。
- Docker 网络和 Nginx 对 REST、SSE、WebSocket 的代理差异。

要求：能画流程，能指出失败点，知道为什么没有选择更复杂方案。

### 绿色优势：把已有能力变成亮点

- AI 记忆、知识库、Advisor/拦截器、工具调用和 Agent。
- MCP ToolCallback 的用户上下文污染问题。
- AI 生图结果如何保存到正确用户空间。
- 输入长度、历史消息和工具权限如何限制。

要求：少背定义，多讲你发现了什么 Bug、如何定位、如何验证。

### 灰色暂缓：十天内只知道边界

- JVM 调优参数大全。
- Spring 和 ShardingSphere 源码逐行分析。
- 分布式事务完整方案。
- 超大规模高并发架构。
- 完整 DDD 战术设计。

面试被问到时可以说：“我目前掌握使用链路和核心机制，还没有深入到框架源码；如果业务需要，我会先用最小复现和官方文档验证。”

不要连续阅读 5 小时。面试考的是提取和表达，必须把一半时间用于闭卷输出。

## 主动回忆：正确使用方式

每个知识点执行四步：

1. 阅读一次教程和源码入口。
2. 关闭文档，不看答案，大声解释。
3. 对照标准回答，只记录漏掉的关键词。
4. 30 分钟后和第二天各重答一次。

判断是否掌握，不看“读起来是否眼熟”，只看能否脱稿说出来。

## 三种学习卡模板

### 知识卡

| 概念 | 项目位置 | 完整流程 | 核心原理 | 能力边界 |
| --- | --- | --- | --- | --- |
| 例：Redis Lua | `RedisCollaborationStateStore` | Java 调脚本→校验版本→更新状态→返回 | 脚本执行期间不被其他命令插入 | 不能替代事务消息，脚本不应长时间阻塞 |

### 错题卡

| 原问题 | 我的回答 | 漏掉的关键词 | 下次回答 | 重答日期/得分 |
| --- | --- | --- | --- | --- |
| 为什么用 Lua？ | 只说了“快” | 原子性、版本校验、幂等 | 先说并发状态更新问题，再说脚本设计 | 第 2 天 / 3 分 |

### 源码卡

| 入口 | 下游调用 | 数据变化 | 异常路径 |
| --- | --- | --- | --- |
| `PictureController.uploadPicture` | `PictureServiceImpl.uploadPicture` → 上传模板 → Mapper | COS 文件、picture 记录、空间用量 | 文件为空、无权限、额度不足、上传失败 |

## 回答题目的万能骨架

回答项目题时按以下顺序：

```text
1. 先说业务问题：为什么需要它。
2. 再说项目方案：入口、核心组件、数据流。
3. 然后说关键原理：为什么方案能工作。
4. 最后说边界：失败场景、替代方案、没有做什么。
```

示例：“为什么协同状态放 Redis？”

> 团队协同需要多个 WebSocket 连接看到同一份旋转和缩放状态，如果只放在单个 JVM 内存，多实例时状态会分裂。项目用 Redis Lua 原子校验版本并更新权威状态，再通过 Pub/Sub 把事件传播给各后端实例。Pub/Sub 本身不持久，所以重连后仍从 Redis 状态键恢复，而不是依赖历史消息。当前规模下这个方案足够，尚未引入 Kafka 一类持久消息系统。

## 不会时如何诚实收口

不要只说“不会”，也不要现场编造。使用四句话：

> 这个问题我没有深入到源码层。我的理解是……（说确定的定义）。在项目里我实际使用的是……（说真实链路）。更底层的……我目前没有验证过。如果继续研究，我会通过最小示例、官方文档和源码调用链确认。

这样不是扣分逃跑，而是在展示边界意识。
