# LiPictureCloud 项目全流程与自我介绍

> 本册先解决最重要的问题：你到底做了一个什么项目，请求如何流动，你负责了什么。

## 一、三种项目介绍

先理解，再改成自己的口吻。不要逐字背诵。

### 30 秒版本

> LiPictureCloud 是一个面向个人和团队的智能图片资产管理平台。它包含公共图库、个人空间和团队空间，支持图片上传、检索、审核、图库分析，以及基于角色的成员权限。项目里我重点实现和治理了 WebSocket 实时协同编辑，使用 Redis Lua 保存带版本的权威状态、Pub/Sub 做跨实例传播；同时接入 Spring AI 和 MCP 生图，并解决了工具回调共享导致图片归属错误的问题。项目使用 Docker Compose 和 Nginx 部署到了线上。

适用场景：面试官说“简单介绍一下项目”。说完停下来，等他选择追问方向。

### 2 分钟版本

> LiPictureCloud 是一个智能云图库，目标是解决图片从上传、存储、审核，到个人管理和团队协作的一整套流程。
>
> 业务上分成三种范围：公共图库中的图片需要管理员审核；个人空间由所有者管理；团队空间通过 SpaceUser 成员关系分为查看者、编辑者和管理员。权限不只在前端隐藏按钮，后端会把角色映射成具体权限码，并在 REST 接口和 WebSocket 消息入口重复校验。
>
> 项目比较有代表性的功能是图片协同编辑。编辑者可以对团队图片执行左旋、右旋、放大和缩小，查看者能实时观看但不能修改。WebSocket 负责浏览器长连接，Redis Lua 原子校验命令 ID 和版本号并更新权威状态，Redis Pub/Sub 再把事件传播给不同后端实例。
>
> AI 部分使用 Spring AI，包含 Redis 对话记忆、Agent 和 MCP 工具调用。MCP 生图完成后会把图片保存到当前用户的个人空间。这里实际排查过一个共享 ToolCallback 被原地包装的问题，它会让后续用户继承第一个用户上下文，修复方式是每次请求创建独立包装，不修改 Provider 的共享回调数组。
>
> 数据层使用 MySQL、Redis、Caffeine 和 Tencent COS，并准备了 ShardingSphere 静态、动态和关闭分表三种 Profile。生产上使用 Docker Compose 编排，公共 Nginx 统一处理 HTTPS、REST、SSE 和 WebSocket。这个项目让我完整经历了需求拆分、数据建模、权限设计、测试、部署和线上排障。

### 5 分钟版本

#### 1. 背景和用户

> 我做 LiPictureCloud 是为了把“图片上传工具”扩展成一个可管理、可协作、可分析的平台。主要用户包括普通用户、团队成员和平台管理员。普通用户保存图片并管理个人空间；团队成员共享图片资产；管理员负责公共内容审核和用户治理。

#### 2. 核心业务模型

> 系统有公共图库、个人空间、团队空间三种范围。Picture 通过 `spaceId` 表示所属空间，`spaceId` 为空时是公共图片；Space 记录空间所有者和额度；SpaceUser 是团队成员关系，记录 viewer、editor、admin 三种角色。一个用户可以拥有空间，也可以作为成员加入别人的团队空间。

#### 3. 典型请求链路

> 浏览器请求先经过 Nginx，再由 Vue 的 Axios 请求封装调用 Spring Boot。Controller 负责参数和登录入口，授权组件判断用户是否能操作图片或空间，Service 编排业务和事务，Mapper/MyBatis-Plus 访问 MySQL。图片二进制保存到 COS，Redis 保存 Session、缓存、AI 记忆和协同状态，最后统一响应对象返回前端。

#### 4. 技术亮点

> 第一个亮点是权限。团队查看者需要能打开图片、进入协同房间接收消息，但不能上传、删除或发送编辑命令。因此项目拆分了 `collaboration:join` 和 `collaboration:edit`，握手和消息处理都进行服务端校验。
>
> 第二个亮点是协同状态。WebSocket 只负责连接和收发，真正的旋转角度、缩放比例、版本号放在 Redis。Lua 脚本原子检查 expectedVersion 和 commandId，防止并发覆盖与重复命令。更新成功后用 Pub/Sub 跨实例广播，客户端重连时重新读取权威状态。
>
> 第三个亮点是 AI。Agent 可以调用本地工具和 MCP 生图工具。生成结果需要保存到发起请求的用户空间，因此工具回调必须绑定请求级用户上下文，而不能污染共享对象。项目还限制消息长度和对话历史，避免上下文无限增长。
>
> 第四个亮点是工程部署。项目有后端、前端和 Redis 协同集成测试；Docker Compose 给 MySQL、Redis、后端和前端设置健康检查及内存限制；Nginx 对 SSE 禁用缓冲，并为 WebSocket 配置 Upgrade 请求头。

#### 5. 项目当前边界与下一步

> 当前线上以普通数据源运行，ShardingSphere 是可选 Profile 和算法验证，不能说成线上已经大规模分表。服务器资源有限，也没有百万并发数据。项目已经对权限和协同做了局部领域边界整理，但完整 DDD 改造仍是后续方向。下一步我会优先补充可观测性、数据库迁移工具和更完整的端到端测试，而不是盲目增加中间件。

## 二、核心数据关系

```mermaid
erDiagram
    USER ||--o{ PICTURE : uploads
    USER ||--o{ SPACE : owns
    USER ||--o{ SPACE_USER : joins
    SPACE ||--o{ PICTURE : contains
    SPACE ||--o{ SPACE_USER : has_members

    USER {
        bigint id PK
        string userAccount
        string userPassword
        string userRole
    }
    PICTURE {
        bigint id PK
        bigint userId FK
        bigint spaceId FK_nullable
        string url
        bigint picSize
        int reviewStatus
    }
    SPACE {
        bigint id PK
        bigint userId FK
        int spaceType
        bigint totalSize
        bigint totalCount
    }
    SPACE_USER {
        bigint id PK
        bigint spaceId FK
        bigint userId FK
        string spaceRole
    }
```

### 四张表怎么讲

- **User**：账号、密码密文、昵称和平台角色。平台角色主要区分普通用户和管理员。
- **Picture**：图片元数据，不保存图片二进制。`userId` 是上传者，`spaceId` 是所属空间。
- **Space**：空间所有者、类型、等级、最大额度和已用额度。
- **SpaceUser**：只服务于团队空间的成员关系，保存成员角色；数据库对 `(spaceId, userId)` 建唯一约束，防止重复入组。

### `spaceId = null` 为什么重要

`Picture.spaceId` 为空表示公共图库，不表示“这个用户没有归属”。上传者仍由 `userId` 记录。图片进入个人或团队空间时，`spaceId` 指向具体 Space。

面试时不要说“用户上传的所有图片都自动进入个人空间”。上传请求是否携带 `spaceId` 决定存储范围。

## 三、一次普通请求如何走完整个系统

```text
浏览器
→ Nginx（HTTPS、域名、反向代理）
→ Vue API 模块
→ Axios request/response 拦截器
→ Spring DispatcherServlet
→ Controller
→ 登录/权限/AOP
→ Service
→ Mapper / MyBatis-Plus
→ MySQL、Redis 或 COS
→ BaseResponse
→ Axios 解包
→ Vue 更新状态和页面
```

### 每层职责

| 层 | 在项目里做什么 | 不应该做什么 |
| --- | --- | --- |
| Controller | 接收 DTO、取得当前用户、调用 Service、封装响应 | 堆积复杂事务和 SQL |
| DTO | 表达某个接口允许传入的字段 | 直接作为数据库长期模型 |
| Service | 权限、业务规则、事务和跨资源编排 | 依赖前端保证安全 |
| Mapper | 执行数据库查询和更新 | 决定业务角色权限 |
| Entity | 对应数据库记录 | 直接把密码等敏感字段返回前端 |
| VO | 返回前端需要的安全视图 | 承担数据库持久化职责 |
| AOP/授权服务 | 处理可复用的横切校验 | 替代所有业务语义判断 |

### Spring MVC 的位置

Nginx 转发到后端后，Servlet 容器接收 HTTP 请求，`DispatcherServlet` 查找匹配的 Controller 方法，参数解析器把 JSON、查询参数或 Multipart 转成 Java 对象，Controller 执行业务后，消息转换器把 `BaseResponse` 序列化成 JSON。

## 四、五条必须会画的业务流程

## 1. 图片上传链路

### 触发与输入

用户选择本地文件或 URL，可选目标 `spaceId`。文件上传进入 `PictureController.uploadPicture`，URL 上传进入 `uploadPictureByUrl`。

### 完整流程

```text
PictureController
→ 获取 loginUser
→ PictureServiceImpl.uploadPicture
→ 如果有 spaceId：查询空间、校验 picture:upload、检查容量
→ 选择 FilePictureUpload 或 UrlPictureUpload
→ 上传到 COS，取得 URL/尺寸/格式等元数据
→ 构造 Picture，设置 userId 和 spaceId
→ 事务保存 Picture
→ 若属于空间，累加 Space.totalSize / totalCount
→ 返回 PictureVO
```

### 数据变化

- COS 新增图片对象。
- `picture` 表新增或更新记录。
- 空间图片新增时更新 `space.totalSize` 和 `totalCount`。
- 图片变更后相关查询缓存通过版本或清理策略失效。

### 失败路径

文件为空、未登录、空间不存在、没有上传权限、空间额度不足、COS 上传失败或数据库保存失败。面试官追问“一半成功怎么办”时，要区分 COS 外部操作与数据库事务：数据库事务不能自动回滚已经上传到 COS 的文件，生产级方案需要补偿删除或异步清理孤儿对象。

## 2. 团队空间查看与权限链路

### 业务规则

团队创建者固定是管理员。查看者能浏览空间和图片，编辑者额外具有上传、修改、删除和协同编辑权限，管理员还能管理成员。

### 完整流程

```text
请求携带 pictureId 或 spaceId
→ 查询资源，确定 public/private/team 类型
→ 取得当前用户平台角色
→ 团队空间查询 SpaceUser 成员记录
→ 将 owner/admin/memberRole 转成 AuthorizationSubject + Resource
→ SpaceAuthorizationManager 计算权限集合
→ 检查 picture:view、picture:edit 等目标权限
→ 允许或抛出无权限异常
```

### 为什么列表能看、详情却可能打不开

列表查询和详情查询必须使用一致的授权语义。项目曾出现团队查看者能在列表看到图片，但详情接口只按所有者判断，从而显示“不存在或已删除”。修复方向不是删除校验，而是让详情接口也解析团队成员权限。

## 3. 协同编辑链路

### 连接阶段

```text
浏览器以 ws/wss 连接 /api/ws/collaboration?pictureId=...
→ Nginx 转发 Upgrade 请求
→ CollaborationHandshakeInterceptor 读取登录用户与 pictureId
→ 校验团队图片和 collaboration:join
→ 将 userId、pictureId 放入 WebSocketSession attributes
→ CollaborationWebSocketHandler 建立会话
→ 从 Redis 读取权威状态并返回 state 事件
```

### 编辑命令阶段

```text
编辑者发送 commandId、expectedVersion、operation
→ Handler 解析消息
→ 再次校验 collaboration:edit
→ CollaborationSessionService 调用 RedisCollaborationStateStore
→ Lua 校验版本与幂等记录，原子更新角度/缩放/版本
→ Java 发布 Redis Pub/Sub 事件
→ 各实例 Subscriber 收到事件
→ 各实例向本机相关 WebSocketSession 广播
→ 编辑者和查看者应用同一权威状态
```

### 查看者为什么能看不能改

查看者拥有 `collaboration:join`，所以能握手和收消息；没有 `collaboration:edit`，因此服务端拒绝编辑命令。前端隐藏编辑按钮只是体验优化，不是安全边界。

- [`CollaborationWebSocketHandler`](../../src/main/java/com/li/lipicturecloud/collaboration/websocket/CollaborationWebSocketHandler.java)

## 4. AI 生图链路

### 完整流程

```text
前端 EventSource 发起 /ai/chat/stream
→ AIController 校验登录和消息长度
→ AiRequestIntent 判断是否需要显示生图进度
→ PicCloudApp / Agent 组装 Prompt、ChatMemory 和工具
→ 每次请求为 MCP ToolCallback 绑定当前 User
→ 模型决定调用生图工具
→ MCP 返回结果文本或图片 URL
→ McpGeneratedImageHandler 提取 URL
→ AiPictureSaveService 下载/上传并保存到当前用户私有空间
→ SSE 持续向前端发送文本与结果
```

### 真实 Bug：图片为什么曾保存到管理员空间

Provider 返回的 ToolCallback 数组是共享/缓存对象。旧代码在原数组上把回调替换为带当前用户的包装器，第一个请求后共享对象就被绑定；后续用户又包装已经绑定的回调，产生跨用户上下文污染。修复后每次请求只构造新的包装对象，不修改 Provider 数组。

## 5. 图库分析链路

### 完整流程

```text
SpaceAnalyzeView 等待当前用户加载
→ 查询当前用户拥有的空间并选择个人空间
→ 调用 usage/category/tag/size/user 分析接口
→ SpaceAnalyzeController 获取 loginUser
→ SpaceAnalyzeServiceImpl 校验具体空间、公共或全量查询范围
→ MyBatis-Plus 使用 count/sum/groupBy 或查询必要列后聚合
→ 返回用量、分类、标签、大小、上传趋势
→ ECharts 渲染
```

### 为什么曾一直显示“暂无数据”

前端曾在用户信息异步加载完成前查询空间，`userId` 为空导致选择错误空间或没有 `spaceId`，后端按权限/参数拒绝；页面又把异常转换成空图表。修复后监听当前用户 ID，用户状态就绪后再加载并重试分析。

## 五、你负责了什么：真实性表达

### 你负责了什么？

> 我负责从业务需求拆分到落地验证的一整条链路，包括图片和空间数据模型、团队成员权限、协同编辑、AI 生图归属、图库分析、工程治理和 Docker 部署。开发过程中使用 AI 辅助检索和生成部分样板代码，但关键业务规则、方案选择、代码审查、测试和线上故障定位由我推进。例如查看者详情权限、MCP 用户上下文污染、前端用户状态加载时序和 Docker 旧镜像问题，都是通过日志、请求链路和最小复现定位的。

### 哪些代码使用了 AI 辅助？

> AI 主要帮助我生成初始代码、测试框架、文档和排查候选方向。我不会说每一行都手写。我的工作重点是明确需求、检查生成代码是否符合项目模型、补权限与异常边界、运行测试，并对线上结果负责。面试中提到的每个流程我都会沿源码重新验证。

### 项目最难的问题是什么？

推荐回答协同权限与状态一致性：

> 难点不是建立 WebSocket，而是同时满足查看者只读、编辑者可写、重复命令幂等、并发版本冲突和多实例广播。我把连接权限与编辑权限拆开，用 Redis Lua 维护权威版本状态，Pub/Sub 做实例间事件传播，重连时从状态存储恢复。这个方案也有边界：Pub/Sub 不持久，所以不能把它当可靠消息队列。

### 项目有哪些不足？

- 线上资源规模有限，没有真实大流量压测结论。
- 数据库脚本仍偏初始化式管理，后续应引入 Flyway/Liquibase。
- 外部 COS 和 AI 调用需要更系统的指标、告警、超时、重试和补偿。
- 前端错误提示曾经吞掉后端异常，需要进一步统一可观察的错误状态。
- 完整 DDD 改造尚未完成，当前只做了局部领域边界整理。

### 如果重做你会改什么？

> 我会先固定领域词汇和权限矩阵，再设计接口；数据库变更从第一天使用迁移工具；外部资源操作设计幂等键和补偿任务；为上传、协同、AI 生图建立端到端测试；在部署前加入结构化日志、指标和告警。不会一开始就引入 Kafka 或复杂微服务，而是根据可靠消息和扩容需求再演进。
