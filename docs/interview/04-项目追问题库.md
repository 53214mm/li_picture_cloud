## 一、项目总览

### Q1（L1→L4）：你的项目和普通图片 CRUD 有什么区别？

**参考回答：**

> 普通 CRUD 主要解决图片记录增删改查，LiPictureCloud 增加了三类资源范围、团队成员权限、管理员审核、实时协同、AI 工具调用、图库聚合分析和生产部署。难点不在接口数量，而在同一图片通过 REST、WebSocket 和 AI 工具访问时，用户身份、空间归属和权限必须一致；外部 COS、Redis 和 AI 服务失败时也要有明确边界。

**合格关键词：** 三种空间、资源权限、WebSocket、AI 生图归属、工程部署。

**危险回答：** “用了很多高级中间件，所以是高并发系统”；“线上百万用户”；只背技术栈不讲业务。

**继续追问：**

1. 如果删掉 WebSocket，核心业务还能运行吗？——能，图片管理仍可用，只失去实时协同。
2. 最核心的数据模型是什么？——User、Picture、Space、SpaceUser，重点是 Picture 的 userId/spaceId 与成员关系。
3. 哪项能力线上默认没开？——ShardingSphere 分表是可选 Profile。

**诚实收口：**

> 当前是资源受限服务器上的完整业务项目，不是大规模微服务。我重点展示业务建模、权限一致性、状态协同和排障能力。

**源码入口：** [`README.md`](../../README.md)、[`Picture`](../../src/main/java/com/li/lipicturecloud/model/entity/Picture.java)、[`Space`](../../src/main/java/com/li/lipicturecloud/model/entity/Space.java)。

### Q2（L2→L4）：一次图片上传经过哪些组件？一致性怎么保证？

**参考回答：**

> Controller 获取当前用户并把文件和 DTO 交给 PictureServiceImpl。Service 若收到 spaceId，会查询空间、校验 picture:upload 和额度；随后选择文件或 URL 上传模板，把二进制写入 COS，取得 URL、尺寸和格式等元数据，再在数据库事务中保存 Picture 并更新空间用量。数据库内部通过事务保证记录与额度一起成功，但 COS 不属于本地事务，因此上传成功、数据库失败时仍可能产生孤儿对象，后续应通过补偿删除或定时清理解决。

**合格关键词：** 权限、额度、上传模板、COS、数据库事务、外部资源补偿。

**危险回答：** “加了 `@Transactional`，COS 和 MySQL 就全都回滚”；忽略更新场景和 spaceId。

**继续追问：**

1. 为什么数据库不存图片二进制？——对象存储更适合大文件，数据库保存可查询元数据。
2. 如何防止重复上传？——可增加内容哈希、幂等键或业务唯一约束；当前不能声称已完整实现秒传去重。
3. COS 超时怎么办？——配置超时、有限重试、幂等对象键和补偿，不能无限重试占用请求线程。

**诚实收口：**

> 当前数据库事务已覆盖记录和空间用量，跨 COS 的最终一致性补偿仍有演进空间。

**源码入口：** [`PictureController`](../../src/main/java/com/li/lipicturecloud/controller/PictureController.java)、[`PictureServiceImpl`](../../src/main/java/com/li/lipicturecloud/service/impl/PictureServiceImpl.java)。

## 二、权限与空间

### Q3（L1→L4）：为什么查看者能看协同，却不能编辑？

**参考回答：**

> 产品需求把“进入房间接收状态”和“发送修改命令”拆成两种能力。查看者拥有 `collaboration:join`，握手成功后可以接收 state、operation 和 presence 事件；但没有 `collaboration:edit`，WebSocketHandler 每次收到命令都会重新检查 edit 权限并拒绝。前端不显示编辑按钮只是体验层，真正边界在服务端。

**合格关键词：** join/edit 分离、握手校验、消息级校验、服务端边界。

**危险回答：** “前端把按钮 disabled，所以安全”；“viewer 完全不能连接 WebSocket”。

**继续追问：**

1. 为什么握手成功后还要校验消息？——join 与 edit 不同，角色也可能变化，不能把连接成功当永久写权限。
2. 管理员和创建者怎么处理？——授权模型根据平台角色、资源所有权和成员角色计算权限。
3. 如果用户被降级但连接未断？——后续命令实时校验会拒绝；可进一步主动踢下线或刷新权限事件。

**诚实收口：**

> 当前实现保证消息入口重新鉴权；角色变更后的主动断连属于可增强体验，不影响写操作安全。

**源码入口：** [`spaceUserAuthConfig.json`](../../src/main/resources/biz/spaceUserAuthConfig.json)、[`CollaborationWebSocketHandler`](../../src/main/java/com/li/lipicturecloud/collaboration/websocket/CollaborationWebSocketHandler.java)。

### Q4（故障题）：团队查看者能看到列表，却打不开详情，怎么定位？

**参考回答：**

> 先把链路拆成“列表接口”和“详情接口”，比较两者发送的 pictureId/spaceId、登录 Cookie、后端状态码和授权调用。现象说明图片确实存在，重点怀疑详情接口仍使用所有者判断，没有解析 SpaceUser 的 viewer 权限。修复不是绕过校验，而是让两个入口都调用统一的 SpaceAuthorizationAccessService，并增加团队查看者详情测试。

**合格关键词：** 比较接口、状态码、资源存在、授权语义不一致、回归测试。

**危险回答：** 直接把异常改成成功；给所有登录用户开放详情；只在前端改提示。

**继续追问：** 如何防 IDOR？——服务端根据真实资源归属和当前登录用户校验，不能只信传入 userId。为什么返回“不存在”？——有时用于避免泄露资源存在性，但调试要看服务端业务码和日志。

**诚实收口：**

> 我会用最小双账号用例验证 viewer、editor、非成员，而不是只测管理员账号。

**源码入口：** [`PictureControllerTeamAccessTest`](../../src/test/java/com/li/lipicturecloud/controller/PictureControllerTeamAccessTest.java)。

## 三、WebSocket 与 Redis 协同

### Q5（L2→L4）：两个用户的协同消息到底怎么传？

**参考回答：**

> 浏览器 A 的 WebSocket 命令到达它连接的后端实例。Handler 校验 edit 权限后，SessionService 用 Redis Lua 更新权威状态。成功后 Publisher 把事件发到 Redis Channel，各后端实例的 Subscriber 都能收到，再调用 Handler 只广播给本实例中同 pictureId 的 WebSocketSession。浏览器 B 收到事件并应用服务端返回的新状态。

**合格关键词：** 浏览器 WebSocket、后端本地房间、Lua 状态、Pub/Sub 跨实例、本地广播。

**危险回答：** “两个 Java 对象通过消息队列直接通信”；“WebSocketSession 存 Redis”；“Redis Pub/Sub 负责永久保存状态”。

**继续追问：**

1. 单实例还需要 Pub/Sub 吗？——可不需要，但统一事件总线方便扩展和测试；需衡量复杂度。
2. 为什么不直接广播客户端发来的命令？——应先校验并产生权威版本状态，避免客户端成为真相来源。
3. Pub/Sub 丢消息怎么办？——重连或冲突时读取 Redis current state，不靠回放事件恢复。

**诚实收口：**

> 当前只同步旋转和缩放，不是复杂图像像素级协同，也没有 OT/CRDT 文档算法。

**源码入口：** [`RedisCollaborationEventPublisher`](../../src/main/java/com/li/lipicturecloud/collaboration/event/RedisCollaborationEventPublisher.java)、[`CollaborationEventSubscriber`](../../src/main/java/com/li/lipicturecloud/collaboration/event/CollaborationEventSubscriber.java)。

### Q6（L3→L4）：Lua 为什么能保证原子？脚本具体做了什么？

**参考回答：**

> Redis 在执行 Lua 脚本期间不会插入其他客户端命令，所以读取状态、校验版本、修改角度/缩放、递增版本和记录 commandId 结果作为一个原子步骤。脚本先检查 commandKey，重复命令返回保存结果；再比较 baseVersion，冲突返回当前状态；成功才更新 Hash 并设置 TTL。它只保证 Redis 内的脚本操作原子，不保证 MySQL/COS 的分布式事务。

**合格关键词：** 不被插入、commandId、baseVersion、APPLIED/DUPLICATE/CONFLICT、TTL、边界。

**危险回答：** “Redis 单线程，所以所有业务都是事务”；“Lua 能保证系统全局一致”。

**继续追问：**

1. synchronized 行不行？——单 JVM 行，多实例不行。
2. 为什么要 expectedVersion？——识别基于旧状态的并发命令，避免静默覆盖。
3. 为什么 commandKey 也设 TTL？——控制幂等记录内存，协同命令只需有限窗口去重。

**诚实收口：**

> 我第一次实战 Lua 主要用于这段状态机，不会把自己包装成 Lua 专家。

**源码入口：** [`collaboration-apply.lua`](../../src/main/resources/redis/collaboration-apply.lua)、[`RedisCollaborationStateStore`](../../src/main/java/com/li/lipicturecloud/collaboration/store/RedisCollaborationStateStore.java)。

## 四、分库分表

### Q7（L1→L4）：项目为什么做分表？线上启用了吗？

**参考回答：**

> 图片元数据是潜在增长最快的表，所以项目实现 ShardingSphere 可选分表来学习和验证路由。静态 Profile 以 userId 对两张表取模；动态 Profile 优先按 spaceId、没有空间时按 userId，在四张表中路由；没有分片键会广播。线上当前使用普通数据源，不能声称生产已启用分表或有大规模收益。

**合格关键词：** 可选 Profile、逻辑表/真实表、分片键、广播、线上未默认启用。

**危险回答：** “加 ShardingSphere 就能无限扩容”；“动态算法会自动创建表”；虚构数据量。

**继续追问：**

1. 为什么空间图片优先 spaceId？——空间查询可定向同一分片。
2. 从 4 扩 8 怎么办？——取模变化导致重映射，需要数据迁移和校验。
3. 分表后 JOIN/分页？——跨分片路由与归并成本上升，需调整查询和数据模型。

**诚实收口：**

> 我做过规则、算法、Profile 和测试，没有做在线迁移与跨库事务，会明确区分。

**源码入口：** [`DynamicPictureShardingAlgorithm`](../../src/main/java/com/li/lipicturecloud/sharding/DynamicPictureShardingAlgorithm.java)、[`dynamic.yaml`](../../src/main/resources/sharding/dynamic.yaml)。

## 五、AI 与 MCP

### Q8（L2→L4）：AI 生图为什么曾保存到管理员图库？

**参考回答：**

> 根因不是数据库 userId 写错，而是共享 ToolCallback 的生命周期。Provider 返回缓存数组，旧代码原地把 callback 替换为绑定当前用户的包装器。管理员先请求后，共享回调内部已经绑定管理员；后续用户再次包装时仍委托到旧的管理员包装，形成上下文污染。修复为每次请求基于原始 callback 创建新包装，绝不修改 Provider 数组，并用连续两个用户的测试验证归属。

**合格关键词：** 共享数组、原地修改、嵌套包装、请求级上下文、双用户回归测试。

**危险回答：** “Redis 缓存串了”；“把管理员 ID 改成当前 ID 就好了”；说不清第一用户为何持续影响后续用户。

**继续追问：**

1. 这和单例 Bean 线程安全吗？——共享可变对象被请求上下文修改，是单例/共享生命周期中的线程与污染风险。
2. ThreadLocal 能解决吗？——可能传递当前线程上下文，但 AI/异步调用线程切换复杂；显式请求级包装更清晰。
3. 如何测试？——Provider 返回同一回调数组，先 admin 再 user，断言原数组未变且委托各自用户。

**诚实收口：**

> 这是我实际遇到并沿对象生命周期定位的问题，比单纯背 Agent 概念更能说明我理解工具调用边界。

**源码入口：** [`PicCloudApp`](../../src/main/java/com/li/lipicturecloud/AI/app/PicCloudApp.java)、[`PicCloudAppContextTest`](../../src/test/java/com/li/lipicturecloud/AI/app/PicCloudAppContextTest.java)。

### Q9（故障题）：为什么每次聊天都显示“图片生成需要 1～2 分钟”？

**参考回答：**

> 先检查提示由模型生成还是 Controller 固定发送。代码显示 AIController 在每个 SSE 请求开始都无条件发送生图进度，所以普通问答也出现。修复为通过 AiRequestIntent 只对明确生图表达发送提示，并增加普通问答和生图文本测试。意图规则宁可保守，不能把所有含“图片”的问题都当生图。

**合格关键词：** SSE、无条件提示、意图识别、普通/生图对照测试。

**危险回答：** 直接让前端隐藏固定文字；用 LLM 再调用一次判断导致成本和不确定性却不说明取舍。

**源码入口：** [`AiRequestIntent`](../../src/main/java/com/li/lipicturecloud/AI/AiRequestIntent.java)、[`AiRequestIntentTest`](../../src/test/java/com/li/lipicturecloud/AI/AiRequestIntentTest.java)。

## 六、图库分析与前端时序

### Q10（故障题）：图库分析为什么一直空白？

**参考回答：**

**继续追问：** 如何避免吞错？——区分 loading/empty/error，展示业务错误并记录请求 ID。怎么证明线上还是旧版？——检查静态 chunk hash/内容、容器镜像构建时间和提交号。

## 七、安全、部署与工程化

### Q11（L2→L4）：项目如何保护密码、Session 和生产密钥？

**参考回答：**

> 用户密码使用 BCrypt strength 12，并校验 72 UTF-8 字节边界；登录态通过 Redis Session 支持多实例；生产数据库、Redis、COS 和 AI 密钥由 `.env` 注入，仓库只保留模板。生产种子 SQL 不含可直接登录的弱密码，需要离线生成密文并首次登录后轮换。Nginx 启用 HTTPS 后 Cookie 配 Secure，外部异常返回统一错误而不泄露堆栈。

**合格关键词：** BCrypt 12、72 字节、Redis Session、环境变量、生产模板、Secure Cookie、异常脱敏。

**危险回答：** “MD5 加盐”；把真实 `.env` 贴进日志；声称加密可逆找回密码。

**继续追问：** BCrypt 为什么每次密文不同还能验证？——盐编码在密文中，matches 取出参数重算。如何让旧 Session 失效？——轮换 Session namespace/删除对应会话并重启配置。

**源码入口：** [`PasswordHashService`](../../src/main/java/com/li/lipicturecloud/service/PasswordHashService.java)、[密码与 AI 安全指南](../round-16-password-ai-security-guide.md)。

### Q12（故障题）：CI 报 `./mvnw: Permission denied` 怎么处理？

**参考回答：**

> 错误码 126 和日志说明脚本存在但没有执行权限，不是 Maven 测试失败。根因通常是 Windows 提交时 Git 没记录 executable bit。可在 Git 中设置 `git update-index --chmod=+x mvnw` 并提交；工作流也可显式 `chmod +x mvnw` 作为防御。然后重新运行 CI，确认进入 Maven 阶段。

**合格关键词：** exit 126、文件权限、Git executable bit、chmod、重新验证。

**危险回答：** 修改 Java 代码；换 JDK；使用 `sudo` 掩盖仓库权限。

**源码入口：** [CI 工作流](../../.github/workflows/ci.yml)、[`mvnw`](../../mvnw)。

### Q13（故障题）：Redis 没密码，应用为什么还 NOAUTH？

**参考回答：**

> 先确认实际 Redis 是否配置 requirepass，再检查 IDEA 运行配置和系统环境变量。`${REDIS_PASSWORD:}` 只在变量不存在时使用空字符串；如果 IDE 仍保存旧密码或连接到另一个 Redis，YAML 改空也不会覆盖高优先级环境变量。用 redis-cli 分别无密码和 AUTH 验证服务端，再重启应用读取新配置。

**合格关键词：** 服务端 requirepass、配置优先级、IDE 环境变量、实际 host/port、重启。

**危险回答：** 在仓库写死密码；删除所有 Redis 数据；只反复改 YAML。

**源码入口：** [`application.yaml`](../../src/main/resources/application.yaml)、[`application-prod.yaml`](../../src/main/resources/application-prod.yaml)。

### Q14（故障题）：为什么 git pull 后线上仍是旧前端？

**参考回答：**

> 需要逐层证明版本：服务器 HEAD、Docker build context、镜像创建时间、运行容器 image ID、Nginx 返回的静态 chunk。真实故障中第一次 git pull 网络失败后 Docker 全部命中旧缓存；后来拉取成功，却把 `docker` 输入成 `ocker`，无缓存构建根本没执行，只用旧镜像 force-recreate。正确做法是确认提交号，成功执行 build，再 up，最后检查线上 chunk hash。

**合格关键词：** 分层版本证据、pull 失败、build 未执行、旧镜像、chunk hash。

**危险回答：** 只让用户清浏览器缓存；不断 restart Nginx；不读终端错误。

**源码入口：** [Docker 部署指南](../round-18-docker-deployment-guide.md)。

## 八、真实性压力题

## 十、快速问答答案

1. `spaceId = null` 是公共图片，非空指向空间。
2. userId 是上传者，spaceId 是资源范围。
3. 保证团队始终有稳定管理员和所有者责任人。
4. viewer 可查看/join，editor 可上传、修改、删除和 edit。
5. 防止不同入口产生越权差异。
6. 不是，每条编辑消息仍校验 edit。
7. 它是当前 JVM 的活连接对象，不是共享数据。
8. ConcurrentHashMap 和并发 Set。
9. 记录 commandId 的第一次结果，实现重试幂等。
10. 识别命令是否基于旧状态，防覆盖。
11. 使用服务端最新状态刷新后重新发起新的命令。
12. Pub/Sub 不持久，只推送给当时在线订阅者。
13. Redis 权威状态 Hash。
14. userId。
15. 先 spaceId，空时 userId。
16. 广播到所有可用真实表保证正确性。
17. 取模结果变化，大量旧数据需要迁移。
18. Agent 可循环决定和调用工具，再观察结果继续处理。
19. 标准化工具/上下文交互协议，不是模型。
20. 控制 Token、延迟与 Redis 空间。
21. 原地修改 Provider 缓存的回调数组并绑定首个用户。
22. 提示是 Controller 无条件发送，应按明确生图意图触发。
23. 不能，本地数据库事务不覆盖外部对象存储。
24. 捕获缓存异常并回源数据库，同时应配限流防雪崩。
25. usage 请求失败，不等于合法的统计零值。
26. 环境变量通常优先于配置文件默认值。
27. 否则代理可能攒完响应，破坏流式体验。
28. 从 HTTP 协商升级为 WebSocket 协议。
29. 内部网络已可访问，公开只增加攻击面和端口冲突。
30. 不能夸大线上分表、百万并发、完整 DDD。
