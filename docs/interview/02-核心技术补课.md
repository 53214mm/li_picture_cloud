# LiPictureCloud 核心技术补课

> 目标不是背框架源码，而是做到：一句话说定义、画出项目流程、解释关键原理、知道能力边界。

## 1. Spring MVC：一次请求是怎么找到 Controller 的

### 一句话是什么

Spring MVC 是基于 Servlet 的 Web 框架，用前端控制器 `DispatcherServlet` 统一接收请求，再把请求分派给匹配的 Controller 方法。

### 项目为什么需要

项目有图片、用户、空间、AI、分析等 HTTP 接口，需要统一完成路由、参数绑定、JSON 转换、异常处理和响应序列化。

### 项目位置

- [`PictureController`](../../src/main/java/com/li/lipicturecloud/controller/PictureController.java)
- [`GlobalExceptionHandler`](../../src/main/java/com/li/lipicturecloud/exception/GlobalExceptionHandler.java)
- [`BaseResponse`](../../src/main/java/com/li/lipicturecloud/common/BaseResponse.java)

### 完整流程

```text
HTTP 请求进入 Servlet 容器
→ DispatcherServlet
→ HandlerMapping 找到 Controller 方法
→ HandlerAdapter 调用方法
→ 参数解析器绑定 JSON、Query、Multipart、HttpServletRequest
→ Controller 调 Service
→ 返回对象
→ HttpMessageConverter 序列化 JSON
→ 异常由 @RestControllerAdvice 统一转换
```

### 核心原理

`DispatcherServlet` 本身不写业务，它协调路由、参数解析、方法调用、返回值处理。`@RequestMapping` 等注解会在启动期形成请求路径到方法的映射。Jackson 消息转换器负责 Java 对象和 JSON 之间转换。

### 面试标准回答

> 一个请求进入 Spring MVC 后先到 DispatcherServlet。它通过 HandlerMapping 找到 Controller，通过 HandlerAdapter 和参数解析器调用目标方法。Controller 调用 Service 后返回 Java 对象，再由 HttpMessageConverter 转成 JSON。项目用全局异常处理器把业务异常统一转成 BaseResponse，避免把堆栈或密码等内部信息返回给前端。

### 三层追问

1. **Controller 和 Service 为什么分层？** Controller 负责协议适配，Service 负责业务和事务，使相同业务可被不同入口复用。
2. **DTO、Entity、VO 为什么分开？** DTO 限定输入，Entity 对应持久化，VO 控制输出，避免越权字段和敏感字段泄露。
3. **Filter、Interceptor、AOP 区别？** Filter 属于 Servlet 层；Interceptor 围绕 MVC Handler；AOP 围绕 Spring Bean 方法，适合权限、限流等方法级横切逻辑。

### 容易说错

- 不要说 DispatcherServlet 直接执行 SQL。
- 不要说所有异常都应该返回 200；HTTP 状态和业务码是两层设计，可按团队规范决定。

### 诚实收口

> 我掌握 Spring MVC 的请求分派和项目调用链，没有逐行研究 DispatcherServlet 源码，但能沿 HandlerMapping、HandlerAdapter、参数解析和消息转换定位接口问题。

## 2. Spring Boot：为什么加注解就能启动

### 一句话是什么

Spring Boot 通过约定、Starter、自动配置和条件注解，根据 classpath 与配置自动创建常用 Bean，减少手工 XML/Java 配置。

### 项目为什么需要

项目同时使用 MVC、Redis、WebSocket、MyBatis、Sa-Token、Spring AI 等组件，如果全部手动创建工厂和生命周期管理，配置成本很高。

### 项目位置

- [`LiPictureCloudApplication`](../../src/main/java/com/li/lipicturecloud/LiPictureCloudApplication.java)
- [`pom.xml`](../../pom.xml)
- [`application.yaml`](../../src/main/resources/application.yaml)
- [`application-prod.yaml`](../../src/main/resources/application-prod.yaml)

### 完整流程

```text
main 调 SpringApplication.run
→ 创建并准备 Environment
→ 读取 application、Profile、环境变量
→ 创建 ApplicationContext
→ 扫描 @Component/@Service/@Controller/@Configuration
→ 导入自动配置候选
→ @ConditionalOnClass/@ConditionalOnMissingBean 等条件筛选
→ 创建 Bean、执行后处理器和生命周期回调
→ 启动内嵌 Web Server
→ 发布应用已就绪事件
```

### 核心原理

`@SpringBootApplication` 组合了配置类、组件扫描和自动配置能力。Starter 主要解决依赖集合问题；AutoConfiguration 解决“满足什么条件时创建哪些 Bean”。自动配置不是魔法：classpath 有对应类、配置满足条件、用户没有提供替代 Bean 时，配置类才生效。

### 面试标准回答

> Spring Boot 的核心是约定优于配置。`@SpringBootApplication` 开启组件扫描和自动配置，SpringApplication 读取 Environment、创建容器并刷新 Bean。自动配置类通过条件注解检查 classpath、配置和已有 Bean，例如引入 Redis Starter 且配置连接信息后，Boot 才自动准备 Redis 相关 Bean；用户自己声明 Bean 时，很多默认配置会通过 `@ConditionalOnMissingBean` 让位。

### 三层追问

1. **Starter 等于自动配置吗？** 不等于。Starter 是依赖聚合，自动配置是创建 Bean 的配置逻辑，两者经常配合。
2. **环境变量为什么能覆盖 YAML？** Spring Environment 汇总多个 PropertySource，并按优先级解析；命令行和环境变量通常高于配置文件。
3. **Bean 怎么注入？** 容器根据类型、名称、限定符解析依赖；推荐构造器注入，依赖明确且便于测试。

### 容易说错

- 不要只说“打注解就装上了”。要说出组件扫描、自动配置、条件注解、容器刷新。
- 不要把 Spring Boot 和 Spring MVC 混成一个概念：Boot 管配置与启动，MVC 管 Web 请求。

### 诚实收口

> 我能解释启动和自动配置主流程，也能通过 Condition Evaluation Report 排查 Bean 为什么没有装配；自动配置选择器的源码细节还没有逐行研究。

## 3. 项目权限：平台角色、空间角色和权限码

### 一句话是什么

项目把“用户是谁”“资源属于哪类空间”“要做什么操作”组合成授权决策，而不是只写 `if (userId == ownerId)`。

### 项目为什么需要

公共图片、个人空间和团队空间的规则不同；团队又有 viewer/editor/admin。相同权限需要在列表、详情、上传、删除和 WebSocket 中一致执行。

### 项目位置

- [`SpaceAuthorizationManager`](../../src/main/java/com/li/lipicturecloud/manager/auth/SpaceAuthorizationManager.java)
- [`SpaceAuthorizationAccessService`](../../src/main/java/com/li/lipicturecloud/manager/auth/SpaceAuthorizationAccessService.java)
- [`SpaceUserPermissionConstant`](../../src/main/java/com/li/lipicturecloud/manager/auth/model/SpaceUserPermissionConstant.java)
- [`spaceUserAuthConfig.json`](../../src/main/resources/biz/spaceUserAuthConfig.json)

### 完整流程

```text
取得 loginUser
→ 查询 Picture/Space/SpaceUser
→ 判断平台管理员、资源所有者或团队成员
→ 构造 AuthorizationSubject 和 SpaceAuthorizationResource
→ SpaceAuthorizationManager 返回权限集合
→ 检查 picture:view / picture:upload / collaboration:join 等权限
→ 允许或抛出 NO_AUTH
```

### 核心原理

角色是权限集合的载体，权限码才是操作判断的最小单位。这样角色变化时集中修改映射，而业务入口只关心“是否有某权限”。同时必须在服务端资源边界校验，不能信任前端传来的角色。

### 面试标准回答

> 项目同时有平台角色和空间角色。平台管理员拥有治理权限；团队空间通过 SpaceUser 得到成员角色，再映射为具体权限码。HTTP 和 WebSocket 不直接相信前端按钮，而是根据当前用户与真实资源重新解析权限。例如查看者有 picture:view 和 collaboration:join，但没有 collaboration:edit。

### 三层追问

1. **为什么不用只看角色？** 权限码粒度更细，入口与角色枚举解耦。
2. **AOP 能代替所有校验吗？** 不能。AOP 适合声明式入口校验，资源归属和复合业务条件仍需服务层解析。
3. **为什么 WebSocket 要校验两次？** 握手控制能否进入，消息处理控制能否执行；角色可能变化，且 join 与 edit 本来就是不同能力。

### 容易说错

- Sa-Token 负责登录/角色能力，但项目空间权限仍有自己的资源授权模型。
- 前端隐藏按钮不等于后端鉴权。

### 诚实收口

> 这是项目级 RBAC/资源授权组合，不是完整 IAM 产品；没有实现策略语言、租户级委托等企业能力。

## 4. WebSocket：从 HTTP 握手到双向消息

### 一句话是什么

WebSocket 先通过 HTTP Upgrade 握手建立持久 TCP 连接，之后客户端和服务器可以随时双向发送帧，不需要每条消息都新建 HTTP 请求。

### 项目为什么需要

协同编辑要求一个用户操作后，其他在线用户立即看到。轮询会产生延迟和大量无效请求，SSE 又主要是服务器单向推送；WebSocket 更适合双向命令与事件。

### 项目位置

- [`CollaborationWebSocketConfig`](../../src/main/java/com/li/lipicturecloud/config/CollaborationWebSocketConfig.java)
- [`CollaborationHandshakeInterceptor`](../../src/main/java/com/li/lipicturecloud/collaboration/websocket/CollaborationHandshakeInterceptor.java)
- [`CollaborationWebSocketHandler`](../../src/main/java/com/li/lipicturecloud/collaboration/websocket/CollaborationWebSocketHandler.java)
- [`collaborationClient.js`](../../li-picture-cloud-frontend/src/services/collaborationClient.js)

### 完整流程

```text
浏览器 new WebSocket(wss://...pictureId=...)
→ Nginx 转发 Upgrade / Connection 头
→ Spring HandshakeInterceptor 读取 Cookie Session 和 pictureId
→ 校验 collaboration:join
→ HTTP 101 Switching Protocols
→ afterConnectionEstablished 加入 JVM 本地房间
→ 发送 Redis 当前状态
→ 客户端发送 JSON 命令
→ handleTextMessage 再校验 collaboration:edit
→ 更新状态并发布事件
→ broadcastLocal 向本实例房间连接发送
→ close 时移除 Session 并发布 LEAVE
```

### 核心原理

HTTP Upgrade 只用于协商，连接建立后使用 WebSocket 帧。`WebSocketSession` 表示服务器侧的一条连接，不是登录 Session；登录信息在握手时从 HTTP Session/认证体系取得，再放入 WebSocket attributes。项目 `rooms` 只保存本 JVM 的连接集合，跨实例事件由 Redis Pub/Sub 衔接。

### WebSocket 和消息队列不是一回事

- WebSocket：网络通信协议，解决浏览器与服务器的长连接和双向传输。
- 消息队列：服务端组件间异步解耦、削峰或可靠传递。
- 本项目：浏览器 ↔ 后端用 WebSocket；后端实例 ↔ 后端实例用 Redis Pub/Sub。

### 面试标准回答

> 项目使用 WebSocket 是因为协同既有客户端编辑命令，也有服务端实时广播。连接先经过 HTTP Upgrade，握手拦截器校验登录和 join 权限，成功后后端用 WebSocketSession 管理连接。每条编辑消息还会校验 edit 权限。单实例内连接按 pictureId 分房间，跨实例事件通过 Redis Pub/Sub 到达后再广播给本地连接。

### 三层追问

1. **断线怎么办？** 前端区分主动关闭和异常关闭，异常时退避重连；重连后读取 Redis 权威状态，而不是假设漏掉的事件会重放。
2. **连接放 Redis 吗？** 不能直接把活 TCP 连接放 Redis；连接对象属于当前进程，只把共享状态和事件放 Redis。
3. **发送需要同步吗？** 同一个 WebSocketSession 的发送需避免并发写冲突；项目在 send 时同步 session。

### 容易说错

- 不要说 WebSocket 天然保证消息不丢、不重复、严格顺序。
- 不要说 Redis 在两个“用户对象”之间传消息；它在后端实例之间传播事件。

### 诚实收口

> 我理解握手、连接管理和项目消息链路；没有实现复杂的离线消息、断点续传和全局连接调度，这些需要额外协议与持久消息设施。

## 5. Redis Lua：原子更新、版本冲突与幂等

### 一句话是什么

Redis Lua 把多条 Redis 读写组合成一次脚本执行，脚本运行期间不会插入其他命令，因此适合原子完成“读取版本—校验—更新—记录结果”。

### 项目为什么需要

两个编辑者可能同时基于同一版本操作；网络重试又可能重复发送同一个命令。若 Java 分多次 GET/SET，中间会被其他请求插入，导致覆盖更新或重复旋转。

### 项目位置

- [`RedisCollaborationStateStore`](../../src/main/java/com/li/lipicturecloud/collaboration/store/RedisCollaborationStateStore.java)
- [`collaboration-apply.lua`](../../src/main/resources/redis/collaboration-apply.lua)
- [`collaboration-current.lua`](../../src/main/resources/redis/collaboration-current.lua)

### 完整流程

```text
Java 生成 stateKey 和 commandKey
→ 传入 ttl、pictureId、operation、baseVersion
→ Lua 先 GET commandKey
→ 已存在：返回 DUPLICATE 和第一次结果
→ 初始化不存在的状态 Hash
→ 读取 rotation、scale、version
→ baseVersion 不等：返回 CONFLICT 和最新状态
→ 应用旋转/缩放边界
→ version + 1
→ HSET 新状态并刷新 TTL
→ SET commandKey 保存结果和 TTL
→ 返回 APPLIED
```

### 核心原理

- **原子性**：脚本执行期间 Redis 不执行其他客户端命令，避免检查和更新之间的竞态。
- **乐观版本**：客户端携带 `baseVersion`，只有等于当前版本才更新。
- **幂等**：`commandId` 对应 commandKey；重复请求直接返回第一次结果。
- **TTL**：状态和幂等记录不是永久业务数据，闲置后过期，控制内存。

Lua 的原子性不代表脚本可无限执行。长脚本会阻塞 Redis；也不等于跨 MySQL、COS 的分布式事务。

### 面试标准回答

> 协同命令需要同时解决并发覆盖和网络重试。项目把状态版本检查、操作计算、版本递增和 commandId 结果记录放进一个 Redis Lua 脚本。版本不一致返回冲突，commandId 已存在返回原结果。这样单次状态变更在 Redis 内原子完成，Java 只有在应用成功后才发布协同事件。

### 三层追问

1. **为什么不用 synchronized？** 只能保护单 JVM，多实例之间无效。
2. **为什么不用 Redis 事务？** WATCH/MULTI 可以实现乐观锁，但 Lua 能把判断与计算集中在服务端，一次往返更直观。
3. **脚本执行失败怎么办？** 不发布成功事件，客户端获得错误或最新状态后刷新；业务层不假设操作已完成。

### 容易说错

- Redis 核心命令处理通常串行，不等于整个 Redis 所有工作只有一个线程。
- Lua 保证脚本内 Redis 操作的原子执行，不保证外部 COS/MySQL 原子性。

### 诚实收口

> 这是我第一次在项目中使用 Lua，我重点掌握了脚本输入、版本校验、幂等和 Java 返回值解析；Lua 语言本身没有做复杂开发。

## 6. Redis Pub/Sub：跨实例传播事件

### 一句话是什么

Redis Pub/Sub 是实时发布订阅机制，Publisher 把消息发到 Channel，当前在线 Subscriber 收到消息，但 Redis 不持久保存历史消息。

### 项目为什么需要

WebSocket 连接保存在各自后端实例内存。用户 A 连接实例 1、用户 B 连接实例 2 时，实例 1 不能直接访问实例 2 的 WebSocketSession。

### 项目位置

- [`RedisCollaborationEventPublisher`](../../src/main/java/com/li/lipicturecloud/collaboration/event/RedisCollaborationEventPublisher.java)
- [`CollaborationEventSubscriber`](../../src/main/java/com/li/lipicturecloud/collaboration/event/CollaborationEventSubscriber.java)
- [`CollaborationRedisConfig`](../../src/main/java/com/li/lipicturecloud/config/CollaborationRedisConfig.java)

### 完整流程

```text
Lua 成功更新状态
→ 当前实例 Publisher 发布 pictureId + event
→ Redis Channel 推送给所有订阅实例
→ Subscriber 反序列化并校验消息
→ 调用 Handler.broadcastLocal
→ 每个实例只遍历自己的房间连接
```

### 核心原理

Pub/Sub 解决实时扇出，不解决可靠存储。订阅者离线时消息不会补发，因此项目把权威状态单独放 Redis Hash；连接恢复后先读取 current state，事件只是低延迟通知。

### 面试标准回答

> 本地 rooms 只能覆盖单实例连接，所以项目使用 Redis Pub/Sub 把协同事件发给所有后端实例。每个实例收到后只广播自己的本地 WebSocket 连接。Pub/Sub 不持久，因此不能依赖它恢复历史；重连客户端从 Redis 权威状态同步最新版本。

### 三层追问

1. **为什么不用 Kafka？** 当前事件只要求在线实时传播，Redis 已是项目依赖；若需要可靠消费、回放、审计，再考虑 Stream/Kafka。
2. **消息重复怎么办？** 客户端以权威版本为准；命令端有 commandId 幂等。
3. **订阅消息格式错误怎么办？** Subscriber 丢弃无效事件并记录告警，避免破坏本地连接。

### 容易说错

不要说 Pub/Sub 保证消息必达，也不要称它为持久队列。

### 诚实收口

> 当前方案优先低复杂度实时同步，没有实现事件回放；这是明确边界，不是遗漏后还声称可靠消息。

## 7. ShardingSphere：静态分表、动态分表和关闭分表

### 一句话是什么

ShardingSphere-JDBC 位于应用 JDBC 层，把逻辑 SQL 按分片规则路由到实际表，并合并结果，让业务代码尽量仍操作逻辑表。

### 项目为什么需要

图片元数据可能随用户和空间增长，单表未来可能面临索引、维护和容量压力。项目实现可选分表配置，用于学习和验证路由，但线上默认不强制启用。

### 项目位置

- [`application-sharding-static.yaml`](../../src/main/resources/application-sharding-static.yaml)
- [`application-sharding-dynamic.yaml`](../../src/main/resources/application-sharding-dynamic.yaml)
- [`static.yaml`](../../src/main/resources/sharding/static.yaml)
- [`dynamic.yaml`](../../src/main/resources/sharding/dynamic.yaml)
- [`DynamicPictureShardingAlgorithm`](../../src/main/java/com/li/lipicturecloud/sharding/DynamicPictureShardingAlgorithm.java)

### 先理解术语

- **逻辑表**：业务 SQL 中看到的 `picture`。
- **真实表**：数据库中的 `picture_0`、`picture_1` 等。
- **分片键**：用于决定路由的列，如 `userId`、`spaceId`。
- **路由**：根据 SQL 条件计算目标真实表。
- **广播路由**：缺少分片键时访问多个分片，再合并结果，成本更高。

### 静态分表流程

```text
启用 sharding-static Profile
→ ShardingSphereDriver 读取 sharding/static.yaml
→ 逻辑 picture 对应 picture_0..1
→ 以 userId 为分片键
→ picture_${userId % 2}
```

例：`userId=5`，`5 % 2 = 1`，路由到 `picture_1`。

### 动态分表流程

```text
启用 sharding-dynamic Profile
→ 逻辑 picture 对应 picture_0..3
→ ComplexKeys 读取 spaceId,userId
→ 有 spaceId：按 spaceId 路由团队/个人空间图片
→ 无 spaceId：按 userId 路由公共图片
→ 两者都没有：为正确性返回全部目标表
→ floorMod(key, shardCount) 选择后缀
```

“动态”指自定义算法根据可用目标数量和复合键计算，并不表示运行时自动创建无限新表。

### 如何关闭

不激活 `sharding-static` 或 `sharding-dynamic` Profile，应用使用普通数据源配置。测试还会验证两个 Profile 不同时开启。

### 核心原理与代价

分片键条件能定向路由；缺少分片键会广播。跨分片 JOIN、排序、分页、聚合和事务更复杂。分表不是“用了就快”，需要根据真实数据量、查询模式和运维能力决定。

### 面试标准回答

> 项目把分表做成可选 Profile。静态配置用 userId 对两张 picture 表取模；动态算法优先用 spaceId，没有空间时用 userId，在四个目标表中取模。查询没有任一分片键时会广播保证正确性，但性能较差。线上当前没有默认启用，所以我把它描述为已实现和测试的扩展能力，而不是生产规模成果。

### 三层追问

1. **为什么空间图片用 spaceId？** 同一空间图片落在同一分片，空间内查询更容易定向。
2. **范围查询怎么办？** Inline 规则可能需要广播；需要结合时间等维度重新设计，不能假设取模适合所有查询。
3. **扩容从 4 到 8 张表？** 直接改变取模会重映射大量数据，需要迁移、双写/停机方案和校验，不是改数字即可。

### 容易说错

- 分库和分表不是同一件事，本项目配置主要演示单数据源分表。
- 不要说线上已启用、数据量巨大或性能提升多少。

### 诚实收口

> 我掌握项目的分片键、路由和 Profile 切换，并写过自定义算法；数据迁移、在线扩容和跨库事务没有实战，会明确说明。

## 8. Nginx 与 Docker：REST、SSE、WebSocket 为什么配置不同

### 一句话是什么

Docker Compose 编排容器和内部网络；Nginx 作为统一网关，根据路径把浏览器请求转发到前端、REST、SSE 或 WebSocket 后端。

### 项目为什么需要

服务器上有其他项目，不能随意占用常见宿主机端口；AI 流式响应不能被缓冲；WebSocket 需要协议升级；HTTPS 证书应集中管理。

### 项目位置

- [`compose.yaml`](../../compose.yaml)
- [`lipicturecloud-domain-https.conf`](../../deploy/nginx/lipicturecloud-domain-https.conf)
- [`Dockerfile`](../../Dockerfile)
- [`前端 Dockerfile`](../../li-picture-cloud-frontend/Dockerfile)

### 完整流程

```text
公网 443 → 公共 Nginx
普通页面 → lipicturecloud-web
/api/* → lipicturecloud-backend:8124
/api/ai/chat/stream → 关闭 proxy_buffering，增加读取超时
/api/ws/collaboration → HTTP/1.1 + Upgrade + Connection upgrade
```

Compose 内 MySQL、Redis、backend、web 只在 `lipicturecloud` 网络通信，不映射数据库和 Redis 到公网。健康检查控制依赖启动，内存限制避免项目无限占用小服务器资源。

### 核心原理

SSE 仍是 HTTP 流，如果代理缓存响应，用户会最后一次性收到；WebSocket 握手需要保留 Upgrade 语义。容器名通过 Docker DNS 解析，公共 Nginx 必须加入项目网络才能访问容器。

### 面试标准回答

> 项目用 Compose 管四个服务，业务端口不直接暴露宿主机，公共 Nginx 加入项目网络后按域名代理。REST 用普通反向代理；SSE 禁用 buffering 并延长超时；WebSocket 使用 HTTP/1.1 和 Upgrade 头。密钥放 `.env`，容器配置健康检查、日志轮转和内存上限。

### 三层追问

1. **容器重建后 Nginx 502？** 检查网络连接、容器 DNS、健康状态和 Nginx 上游解析/重载。
2. **为什么不公开 3306/6379？** 应用内部访问即可，减少公网攻击面和端口冲突。
3. **镜像为何多阶段？** 构建阶段有 JDK/Node 与依赖，运行阶段只带 JRE/JAR 或 Nginx/dist，减小运行面。

### 容易说错

不要把 Docker 说成虚拟机；容器共享宿主机内核。不要说健康检查等于业务功能完全正常，它只是一个可定义的探针。

### 诚实收口

> 我完成了单机 Docker Compose 与 Nginx 部署，尚未使用 Kubernetes；当前规模没有必要为了名词复杂化架构。

## 9. AI Agent 与 MCP 用户上下文

### 一句话是什么

Agent 让模型基于任务循环选择工具；MCP 用标准协议向模型提供外部工具。项目把工具调用和当前登录用户绑定，生成结果才能正确授权和入库。

### 项目为什么需要

普通对话只能返回文本，用户还希望生成图片并保存。工具需要调用外部服务，但不能获得服务器终端和任意文件权限，也不能跨用户保存资源。

### 项目位置

- [`PicAgent`](../../src/main/java/com/li/lipicturecloud/AI/agent/PicAgent.java)
- [`ToolCallAgent`](../../src/main/java/com/li/lipicturecloud/AI/agent/ToolCallAgent.java)
- [`PicCloudApp`](../../src/main/java/com/li/lipicturecloud/AI/app/PicCloudApp.java)
- [`RedisBasedChatMemory`](../../src/main/java/com/li/lipicturecloud/AI/chatMemory/RedisBasedChatMemory.java)
- [`PicCloudApp` 内的 `UserContextToolCallback`](../../src/main/java/com/li/lipicturecloud/AI/app/PicCloudApp.java)
- [`AIGenerationTool`](../../src/main/java/com/li/lipicturecloud/AI/tools/AIGenerationTool.java)

### 完整流程

```text
用户消息 → 长度与登录校验
→ 读取用户级 Redis ChatMemory
→ 组装系统提示、本地工具、MCP callbacks
→ 每个 callback 创建请求级 UserContext 包装
→ 模型决定直接回答或发起 tool call
→ MCP 服务执行生图
→ 结果返回 Agent
→ 提取图片 URL
→ 当前用户对应的保存服务写入个人空间
→ 助手文本与结果通过 SSE 推送
→ 对话历史限制为固定消息数
```

### 核心原理

模型只输出工具名和参数，真正执行发生在应用/MCP 服务。ToolCallback 可能由 Spring Provider 缓存，所以不能把用户写进共享回调对象。请求级包装类似给本次调用附加安全上下文，委托原工具执行，再在结果处理时使用当前用户。

### 面试标准回答

> 项目用 Spring AI Agent 组合本地工具和 MCP 生图工具，对话记忆按用户保存在 Redis。最关键的安全点是 ToolCallback 的生命周期：Provider 回调可能共享，不能原地绑定用户。每次请求创建新的 UserContextToolCallback，MCP 图片结果再按当前用户保存到私有空间，从而避免跨用户上下文污染。

### 三层追问

1. **为什么每次聊天都曾显示生图进度？** Controller 无条件发送提示；修复为先用明确意图规则判断是否属于生图请求。
2. **ChatMemory 为什么要限制？** 控制 Token、延迟和 Redis 占用；当前保留有限消息，不是永久聊天档案。
3. **如何限制工具风险？** 工具白名单、参数校验、登录用户绑定、禁止危险终端/文件工具、超时和结果校验。

### 容易说错

- MCP 不是模型本身，也不是消息队列。
- 不要说 LLM “自动访问数据库”；应用显式注册并执行工具。

### 诚实收口

> AI 是我的优势区，我能讲 Agent、记忆和工具链；模型内部训练原理和 MCP 服务端全部实现不是本项目范围，我会区分应用集成与模型研发。

## 10. 总复习：一张对照表

| 技术 | 解决的问题 | 项目关键点 | 明确边界 |
| --- | --- | --- | --- |
| Spring MVC | HTTP 路由和参数/响应转换 | DispatcherServlet 到 Controller | 未逐行研究框架源码 |
| Spring Boot | 自动配置与应用启动 | Starter、条件装配、Environment | 不是“注解魔法” |
| 权限模型 | 资源级操作控制 | subject + resource + permission | 不是企业 IAM |
| WebSocket | 浏览器双向实时通信 | 握手 join，消息 edit | 不保证离线可靠消息 |
| Redis Lua | 并发状态原子更新 | version + commandId | 不等于跨系统事务 |
| Pub/Sub | 多实例实时传播 | 状态存 Redis，事件只通知 | 不持久、不回放 |
| ShardingSphere | 逻辑表路由实际表 | Profile + 分片键 + 算法 | 线上默认未开启 |
| Nginx/Docker | 部署与协议代理 | SSE 缓冲、WS Upgrade | 不是 K8s 集群 |
| Agent/MCP | 模型调用外部能力 | 请求级用户上下文 | 不等于模型研发 |
