# 第 07 轮：动态分表算法与开关

## 1. “动态”指什么

这里的动态不是每次请求都创建新表，而是路由算法会根据当前资源计算目标表。物理表仍由运维脚本提前创建，这样表结构、索引和权限都可审计，也不会让普通业务请求拥有建表权限。

动态模式准备 4 张表。空间图片用 `spaceId % 4`，因此同一空间的图片聚集在同一张表；公共图片没有空间编号，就使用 `userId % 4`。

## 2. 为什么同一空间要放在一起

常见请求是“列出某空间的图片”。如果同一空间的数据散落在所有表中，每次都要广播查询和合并；按空间路由后，带 `spaceId` 的请求通常只访问一张表。

## 3. 三种模式怎样切换

| 模式 | Spring profile | 表 |
| --- | --- | --- |
| 单表 | 不添加 sharding profile | `picture` |
| 静态 | `sharding-static` | `picture_0..1`，按用户 |
| 动态 | `sharding-dynamic` | `picture_0..3`，空间优先 |

所谓“关闭分库分表”，就是不启用 `sharding-static` 和 `sharding-dynamic`。默认配置仍连接原始 MySQL 数据源，所以回滚路径简单。

不要同时启用两个 sharding profile，因为它们都会覆盖 `spring.datasource.url`，最后生效顺序不够直观。部署配置应明确三选一。

## 4. 上线动态模式的顺序

1. 备份原表。
2. 执行 `sql/picture_sharding_dynamic.sql` 创建四表并复制数据。
3. 核对源表行数与四张分表总行数。
4. 在测试环境启用 `sharding-dynamic`。
5. 验证公共图片与团队空间图片的新增、按 ID 查询、按空间分页、更新和逻辑删除。
6. 观察慢查询与广播查询后再安排生产切换。

## 5. 算法如何处理没有键的查询

按图片 ID 查询时，SQL 中没有 `spaceId` 或 `userId`，算法无法提前知道表。本轮返回全部候选表，让 ShardingSphere 广播查询并合并。它可能较慢，但不会漏数据。未来若需要优化，可增加“图片 ID 到分片”的定位索引或把分片信息编码进 ID。

## 6. 测试关注什么

- 空间图片优先使用空间编号，即使同时存在用户编号。
- 公共图片能回退到用户编号。
- 没有路由键时返回全部表。
- 配置文件能明确区分单表、静态和动态模式。

```powershell

.\mvnw.cmd -B "-Dspring.profiles.active=test" package
```
