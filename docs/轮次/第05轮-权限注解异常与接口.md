# 第 05 轮：把权限规则真正接到接口上

## 1. 为什么有权限表还不够

第 4 轮解决的是“规则怎么算”，但控制器如果不调用规则，攻击者仍可直接请求接口。因此第 5 轮增加一道统一门禁：业务方法执行前，先识别当前用户、目标资源和所需权限。

可以把它想成办公楼：权限矩阵是门禁系统里的名单，权限注解是装在每扇门上的读卡器。只有名单没有读卡器，门仍然是开的。

## 2. 为什么不从 JSON 请求体里猜资源

旧实现会根据 URL 猜 `id` 的含义，还会尝试重新读取 JSON 请求体。请求体通常是一条只能顺序读取的流；Spring MVC 已经读取一次后，AOP 再读可能得到空字符串。

本轮使用显式表达式，例如：

```java
@SpacePermission(value = "spaceUser:manage", spaceId = "#request.spaceId")
```

它表示：需要成员管理权限，空间编号从方法参数 `request.spaceId` 获取。代码读起来就能知道保护的是哪个资源，也不依赖请求体能否被再次读取。

## 3. 一次权限检查经过哪些步骤

1. AOP 找到 `@SpacePermission`。
2. SpEL 从已经反序列化的方法参数中提取资源编号。
3. 权限访问服务读取当前登录用户。
4. 服务端查询空间、图片或成员关系，绝不相信客户端传来的角色。
5. 第 4 轮的 `AuthorizationManager` 计算权限集合。
6. 包含所需权限则继续执行；否则抛出无权限异常。

## 4. HTTP 状态和业务码是两层信息

响应体里的 `40100`、`40300` 是项目内部业务码；HTTP 的 401、403 是浏览器、网关和监控系统能直接理解的标准状态。本轮让两者保持一致：

| 场景 | HTTP 状态 | 业务码 |
| --- | ---: | ---: |
| 参数错误 | 400 | 40000 |
| 未登录 | 401 | 40100 |
| 无权限/禁止访问 | 403 | 40101 或 40300 |
| 资源不存在 | 404 | 40400 |
| 未预料异常 | 500 | 50000 |

暂时保留历史业务码 `40101`，避免前端立即发生破坏性变化，但它在 HTTP 层会正确表现为 403。

## 5. 前端怎样获取权限

前端只提交资源编号，后端根据登录态和数据库成员关系返回权限字符串集合。前端可据此隐藏“删除成员”或“协同编辑”等按钮。但要注意：隐藏按钮只是改善体验，真正安全仍依赖后端注解。
