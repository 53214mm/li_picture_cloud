# 第 06 轮：图片仓储与静态分表

## 1. 分表到底解决什么

一张表持续增长后，索引会变大，单表维护和部分查询的成本也会上升。分表是把逻辑上的一张 `picture` 表拆成多张物理表。本轮拆为 `picture_0`、`picture_1`。应用仍写 `picture`，ShardingSphere 根据规则选择真实表。

## 2. 为什么先按 userId 分

项目的公共图片没有 `spaceId`，但每张图片都有 `userId`。如果静态阶段直接按 `spaceId` 分片，公共图片会遇到空分片键。使用 `userId % 2` 可以保证每次新增图片都有唯一目标：偶数用户进入 0 表，奇数用户进入 1 表。

代价是仅按图片 ID 查询时不知道目标表，ShardingSphere 会查询两张表再合并结果。第 7 轮会引入可扩展策略和动态算法，但本轮先保证迁移简单、结果正确。

## 3. 为什么要有 Repository

原先业务服务直接继承 MyBatis-Plus 的 `ServiceImpl`，所以业务层同时知道数据库框架细节。`PictureRepository` 像一个插座标准：业务层只说“查图片、保存图片”，`MybatisPictureRepository` 再把意图翻译成 Mapper 调用。

这也解释了 `save()` 和 `mapper.insert()` 的关系：`save()` 属于 MyBatis-Plus 服务层能力；仓储适配器本身处于更底层，直接使用 Mapper，并把受影响行数转换成布尔结果是合理的。

## 4. 如何启用

1. 备份数据库。
2. 执行 `sql/picture_sharding_static.sql`。
3. 核对脚本最后输出的原表和分表总行数相等。
4. 设置 `MYSQL_HOST`、`MYSQL_PORT`、`MYSQL_DATABASE`、`MYSQL_USERNAME`、`MYSQL_PASSWORD`。
5. 增加 Spring profile：`local,sharding-static`。
6. 先在测试环境验证新增、查询、更新、逻辑删除，再切换生产环境。

不要立刻删除原 `picture` 表。回滚时去掉 `sharding-static` profile 即可重新使用原数据源和原表。

## 5. 配置文件怎样阅读

- `application-sharding-static.yaml`：把 Spring 数据源驱动切换为 ShardingSphereDriver。
- `sharding/static.yaml`：声明真实数据源、物理表、分片列和算法。
- `actualDataNodes`：列出逻辑表能路由到的真实表。
- `algorithm-expression`：计算物理表后缀，本轮是 `userId % 2`。

## 6. 验证命令

```powershell
.\mvnw.cmd -B "-Dtest=MybatisPictureRepositoryTest" test
.\mvnw.cmd -B "-Dspring.profiles.active=test" package
```

默认测试不连接真实 MySQL，因此用于证明“新增依赖和仓储边界没有破坏现有系统”。真实分片路由必须在准备好两张物理表的集成环境中验证。
