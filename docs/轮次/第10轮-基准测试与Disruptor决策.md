# 第 10 轮：先测量，再决定要不要 Disruptor

## 1. Disruptor 是什么

Disruptor 是一种高性能进程内事件队列，擅长让生产者把事件快速写入环形缓冲区，再由消费者按顺序处理。它适合极高吞吐、事件结构固定、能够接受异步处理的场景。

“性能框架”不是装上就会变快。队列只优化线程之间怎样交接工作，无法让数据库查询或网络传输本身变快。

## 2. 当前一次协同命令做了什么

1. 从 WebSocket 收到 JSON。
2. 查询用户和团队成员关系，重新检查编辑权限。
3. 修改一个内存状态：旋转、缩放、版本加一。
4. 序列化事件。
5. 向房间内每个连接发送网络消息。

第 3 步才是 Disruptor可能优化的部分。第 2 和第 5 步通常比一次整数运算慢几个数量级。

## 3. 本轮怎样测

基准连续执行 100,000 条版本正确的右旋命令，不连接数据库和网络，只测状态机核心。一次本机运行结果：

```text
commands=100000 elapsedMs=70.09 opsPerSecond=1426674
```

结果不是跨机器性能承诺，CI 和不同电脑会有波动；它用于判断数量级。每秒约 142 万次远高于当前产品可预期的人工点击频率。

## 4. 为什么现在不引入

- 状态机不是已证明的瓶颈。
- 当前同步流程能立即把版本冲突回给发送者；异步队列需要额外的命令结果通道。
- 环形缓冲区满时必须决定阻塞、丢弃还是拒绝，每种选择都会改变业务语义。
- 应用关闭时还要等待队列排空，否则最后几条编辑可能丢失。
- 权限检查和 WebSocket 发送仍然存在，整体延迟不会按状态机吞吐比例下降。

因此，本轮“优化”的正确结果是保留更简单的直接路径，并增加测量能力，而不是增加一个尚无收益证据的依赖。

## 5. 新增了哪些指标

`CollaborationSessionService.metrics()` 返回：

- `appliedCommands`：真正执行的命令数；
- `duplicateCommands`：被幂等保护拦住的重发数；
- `versionConflicts`：客户端版本落后的次数；
- `activePictures`：当前 JVM 中存在协同状态的图片数。

这些计数使用 `LongAdder`，高并发下比单个原子计数器争用更小。

## 6. 什么时候重新考虑 Disruptor

同时满足“有生产数据”和“瓶颈确实在状态处理”再做：状态机 p99 超过 2 ms、单实例持续超过 20,000 条操作/秒，或者 WebSocket 线程明确在等待状态计算。届时还要先设计队列满载策略、错误回传、分区顺序和优雅停机。
