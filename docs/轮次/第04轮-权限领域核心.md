# 第 4 轮：权限领域核心

## 1. 这一轮要解决什么

权限系统要回答一个简单问题：某个用户能不能对某个资源执行某个操作。

当前代码把以下职责集中在 `StpInterfaceImpl` 中：

1. 从 HTTP 请求读取参数。
2. 根据 URL 判断参数代表图片、空间还是成员。
3. 查询图片、空间和成员。
4. 判断公共图库、私人空间或团队空间。
5. 把角色转换成权限。
6. 返回 Sa-Token 需要的权限列表。

这会导致权限规则只能在 HTTP 请求中测试，WebSocket 以后也难以复用。本轮先建立一个不依赖 HTTP、Sa-Token、数据库和 Spring 的权限策略 seam。

## 2. 新手先理解四个名词

### 身份

身份表示“用户是谁”，包含用户 ID，以及是否为平台管理员。

### 资源

资源表示“用户准备操作什么”。本轮关心公共图片、私人空间和团队空间三种授权场景。

### 角色

团队空间成员拥有 `viewer`、`editor` 或 `admin` 角色。角色本身不是最终判断结果，它会先转换成权限集合。

### 权限

权限表示一个具体动作，例如 `picture:edit`。业务入口应询问是否具备权限，不应到处写 `role.equals("admin")`。

## 3. 权限规则

### 公共图库图片

- 所有人可以查看。
- 图片上传者或平台管理员可以编辑和删除。
- 公共图库不开放团队协同权限。

### 私人空间

- 空间所有者或平台管理员可以查看、编辑和管理空间内图片。
- 其他用户没有权限。
- 私人空间不开放成员管理和协同编辑。

### 团队空间

- viewer：查看空间和图片。
- editor：在 viewer 基础上，可以上传、编辑、删除图片，并加入和操作协同编辑。
- admin：在 editor 基础上，可以管理空间和成员。

空间创建者继续由 `Space.userId` 表示，同时拥有 admin 成员记录。本轮不新增 owner 数据库角色。

## 4. 代码结构

```text
AuthorizationSubject
  用户身份，只保存判断规则需要的数据

SpaceAuthorizationResource
  已经解析好的资源事实，不负责查数据库

AuthorizationManager
  调用方使用的稳定 interface

SpaceAuthorizationManager
  纯 Java 权限规则 implementation

SpaceUserAuthManager
  负责把团队角色映射成权限
```

数据库查询与 HTTP 参数解析留在 adapter 中。第 5 轮会把现有 Sa-Token 实现迁移为 adapter。

## 5. 为什么先写测试

权限错误通常不会导致编译失败，而是让错误的人获得数据。因此每一条规则都必须先写成测试。测试只创建普通 Java 对象，不启动 Spring，也不连接数据库。

重点场景：

- 公共图片所有者与普通访客。
- 私人空间所有者与陌生用户。
- 团队 viewer、editor、admin。
- 未知角色。
- 协同权限只能出现在团队 editor/admin 中。

## 6. 验证命令

```powershell
$env:JAVA_HOME = '<JDK 21 路径>'
.\mvnw.cmd -B "-Dtest=SpaceAuthorizationManagerTest" test
.\mvnw.cmd -B "-Dspring.profiles.active=test" package
```

第一条只验证权限规则，速度快；第二条验证整个应用仍能启动和打包。

## 7. 本轮完成标准

- 权限策略不依赖 Spring、HTTP、Sa-Token 或数据库。
- 未知角色默认没有权限。
- 公共与私人资源不会获得协同权限。
- 团队 editor/admin 具备协同权限。
- 单元测试和完整构建通过。
