## 1. 首版已选路线与未来升级边界

用户正式选择 **Sprite + 静态 / 表情差分 Portrait**：Shell 用适合小尺寸的简化静态 Sprite，Home 用正常比例全身 Sprite 与有限帧最小 Idle，Conversation 用正常比例半身，默认 Neutral。可以准备少量差分，但 neutral / happy / curious / thinking / annoyed / sleepy 只是示例，不是本轮冻结的状态集；真实状态到表情的映射由 R06 / R11 决定，不按聊天关键词猜测。

首版不引入 Live2D Runtime、Spine Runtime、Pixi 或其他动画依赖。采用原生 CSS frame player 或极小 Sprite Player，验证一个 Idle；不用完整 Renderer Framework、R06 协议或 R07 状态机。

长期可让不同 Representation 采用不同技术，三者不互斥：

| 位置 | 首版 | 未来可重新评估的方向 |
| --- | --- | --- |
| Shell | 简化静态 Sprite | 按真实需求增添有限帧；保持安静与导航可用 |
| Home | 正常比例全身 + 一个帧动画 Idle | 若持续全身动作成为实际需求，再评估 Spine / 其他骨骼动画 |
| Conversation | 静态 Neutral + 可选表情差分 | 若近景表演有实际价值，再评估 Live2D |
| Desktop Pet | 本轮不实现，Q 版仅参考 | 可采用 Sprite；宿主、窗口与功耗独立设计 |

Representation 可替换，CompanionInstance 不变化；资源格式升级不能创建实例、重置成长或重算 Feed。下面的官方调查是初轮研究快照，保留为将来升级依据，不要求再次三选一。本次文档收口没有重新核验厂商版本 / 许可，未来实际集成时再查当时条款。

### 给未来开发者看的解释

**Sprite：先把完整画面画好，再按时间播放。** 比如 `idle_01 → idle_02 → idle_03 → idle_04` 循环播放，浏览器主要负责选帧。适合小尺寸、全身角色、少量固定动作，以及个人项目的 Web / Desktop Pet。实现简单、资源直观、原生播放层轻；代价是动作越多，完整帧通常越多。四帧只是解释示例，真实帧数通过 PoC 决定。正常比例角色同样能制作 Sprite，不需要改成 Q 版。

**Live2D：把立绘拆成可变形的部件，用网格和参数驱动。** 它适合眼神、嘴型、眨眼、呼吸、头部转动、头发物理和近景表情，因此未来可能用于 Conversation Portrait。相较当前少量帧与静态差分的范围，拆件、遮挡补全、建模、参数绑定、Runtime 和许可核验会增加第一步的制作与接入成本，所以首版不引入。这是本项目范围下的成本判断，不是所有动画场景的通用排名。

**Spine：把身体部件交给 2D 骨骼系统运动。** 头、身体、手臂、腿、翼和衣服通过骨骼 / 网格、附件与时间线组合动作，适合 Walk、Sit、Sleep、Turn、Pick Up 等复杂全身动作和换装附件。若未来 Home 真正需要伙伴持续在房间活动，可重新评估；当前只验证 Idle，不支付整套骨骼接入和美术绑定成本。

可以同时有 Sprite Shell、Spine Home 和 Live2D Portrait，它们仍是同一位伙伴。改变播放工具不等于动画资源自动互转；保留制作源文件和稳定的表示组件边界，远比提前装三个 Runtime 更有用。具体制作与格式证据见下文第 4 节，实施范围见[第二阶段计划](R05-第二阶段实施计划.md)。

## 2. 本仓库的实际技术边界

已只读检查：

- `li-picture-cloud-frontend/package.json`：Vue `^3.4.21`、Vite `^7.3.6`、Pinia `^2.1.7`、Vue Router `^4.3.0`；Node 声明 `>=22 <23`。这里记录的是 manifest 声明范围，不冒充 lockfile / 实际安装版本。
- 当前依赖中没有 PixiJS、Cubism、Spine、Phaser 或其他角色 runtime，因此任何骨骼 / 变形方案都是新增集成与资产管线，不是复用现成 renderer。
- `src/components/shell/CompanionPresenceSlot.vue` 是指向 `/companion` 的 `router-link`。现状为静态 `ShellIcon`，标记容器 `40 × 44 CSS px`、图标 `28 × 28`、卡片 `min-height: 80px`；源码注释明确它当前是栖居标记。已有 `prefers-reduced-motion` 分支只关闭 CSS transition，不能自动停止未来的 Canvas / WebGL 循环。

因此，未来接入必须保留导航可访问性，让身体绘制留在独立展示组件内。Vue 的挂载 / 卸载钩子可以管理外部绘制对象、监听器和计时器；逐帧顶点、骨骼、纹理不宜塞进业务 store 或深层响应式对象。这是基于仓库结构与 [Vue 生命周期 API](https://vuejs.org/api/composition-api-lifecycle.html) 的集成建议，并非已经实现。

## 4. 三种身体路线：逐项比较

下表中，功能与文件格式来自列明的官方资料；“适合”“复杂度”“成本趋势”是针对 LiPictureCloud 的工程判断。**没有做同画面、同设备 benchmark，不给出未经测量的 FPS、耗电或成本小时数。** 制作能力比 runtime 名称更决定最终质量。

| 比较维度 | Sprite Sheet / Frame Animation | Live2D Cubism Web | Spine / 2D Bone Animation |
| --- | --- | --- | --- |
| 1. Web / Vue 集成 | Vue 管容器和状态；CSS 离散帧或 Canvas `drawImage` 管播放。单角色可以无第三方 runtime。[Canvas](https://html.spec.whatwg.org/multipage/canvas.html#dom-context-2d-drawimage) | 在组件中管理 Canvas、SDK 初始化、模型加载、更新 / 绘制与释放。官方是 TypeScript / JavaScript Web SDK，不是开箱 Vue 组件。[SDK](https://www.live2d.com/en/sdk/about/) | 官方 `spine-ts` 提供 ESM / TypeScript 与自包含 WebGL backend；Vue 只包生命周期与展示接口。[spine-ts](https://raw.githubusercontent.com/EsotericSoftware/spine-runtimes/4.3/spine-ts/README.md) |
| 2. Runtime 构成 | 浏览器 + 小型播放器；也可采用 Pixi `AnimatedSprite`。图集生产工具与播放器分开。[Pixi 固定版本源码](https://github.com/pixijs/pixijs/blob/v8.21.0/src/scene/sprite-animated/AnimatedSprite.ts) | Core + Framework + 应用层。Core 要从官方 SDK 包取得；不能把公开 GitHub Framework 当成完整 runtime。[官方 Framework](https://github.com/Live2D/CubismWebFramework) | `spine-core` 处理骨架，`spine-webgl` 绘制；也有 player / Pixi adapter。简单 Canvas backend 对网格 / 裁剪等有限制，不能当完全等价降级。[spine-ts](https://raw.githubusercontent.com/EsotericSoftware/spine-runtimes/4.3/spine-ts/README.md) |
| 3. 开源 / 商业授权 | 原生播放本身无 Spine / Live2D 许可依赖；编辑工具、打包工具、美术资产分别核验。可选 Pixi 是 MIT，保留其声明。[MIT](https://github.com/pixijs/pixijs/blob/v8.21.0/LICENSE) | Framework 源码可见但适用 Live2D Open Software License；Core 为 Proprietary License；Editor 与发布许可另算，不能概括成“完全开源免费”。详见第 5 节。 | runtime 源码可见、不是 MIT；适用厂商定制许可与 Editor 协议。集成主体需要核验许可，购买美术成品不能自动替代。详见第 5 节。 |
| 4. 角色制作流程 | 设定 → 一致的逐帧画面 → 校准脚底 / 画幅 / 透明边缘 → 图集 + 帧时长。可手绘，也可从获许可的绑定工程预渲染。[Krita 动画流程](https://docs.krita.org/en/user_manual/animation.html) | 原画分层 / 遮挡补全 → ArtMesh / 变形器 / 参数 → 动作 / 表情 → 导出 `.moc3`、贴图及 JSON 等。[嵌入导出](https://docs.live2d.com/en/cubism-editor-manual/export-moc3-motion3-files/) | 拆分部件 → bones / slots / attachments → 网格权重、约束与时间线 → 导出 JSON / binary、atlas 和贴图。[导出](https://esotericsoftware.com/spine-export)、[Skins](https://esotericsoftware.com/spine-skins) |
| 5. 动作制作成本 | 每新增姿势 / 视角都可能增加重绘；少量短循环简单，长动作与大量变体累计成本高。预渲染能减少手绘负担，却仍有每帧交付与存储成本。 | 初次拆件绑定重；已覆盖的参数可复用，眨眼 / 呼吸 / 视线较容易增量制作；大角度转身和全身位移仍可能补画 / 重绑。 | 初次 rig 重；既有骨架适合积累 Walk / Sit 等动作与转场；遮挡、极端姿势、不同身体结构需要补件和动画修整，不能默认自动复用。 |
| 6. 表情 | 小尺寸可换头部 / 面部帧；Portrait 可用独立表情差分。表情 × 动作若全量烘焙会膨胀，分层则增加对齐工程。 | 参数化面部与 `.exp3.json` 可与普通 motion 叠加；表情与动作计算顺序需要约定。[Expression](https://docs.live2d.com/en/cubism-sdk-manual/expression/) | 面部附件替换、骨骼 / 网格关键帧可以组合表情；细腻程度依赖面部 rig。它不自动生成口型或情绪。 |
| 7. 换装 | 整套重绘 / 预渲染最直观；把衣物拆成叠层可以复用，但所有帧需统一锚点与遮挡。 | 可预制服装部件 / 参数切换；变化大的衣服要补画、绑参数与测试遮挡。不要承诺任意服装零成本套入。 | Skin / attachment 是正式能力，可复用同骨架动作并组合部件；结构或轮廓不兼容的服装仍需适配。[Skins](https://esotericsoftware.com/spine-skins) |
| 8. 多成长阶段 | Egg / Juvenile / Adult 各有素材包；结构差异不受骨架约束，但每阶段动作都要制作。 | 差异大的三阶段通常是独立模型；蛋不是把成年人形参数压缩，阶段切换也不是新 Instance。 | 差异大的阶段采用不同 skeleton；相近阶段可能复用约定。禁止为了共享 rig 把 Juvenile 只做成 Adult 缩小。 |
| 9. 多角色扩展 | 共用帧播放器与素材清单；新增 Species 的美术量仍随角色数增加。按当前角色 / 阶段加载，不能全预载。 | 共用 SDK / 参数映射边界，各 Species 分别建模；相同参数名不保证表演效果一致。 | 共用 runtime、动作语义与加载规范；同骨架家族可复用更多，不同魔物轮廓不能假设一套骨架通吃。 |
| 10. 内存 | 主要是解码位图 / 图集；增长近似取决于像素数 × 帧数 × 已加载变体。压缩文件小不代表解码内存小。 | 贴图 + Core 模型数据 + 参数 / 顶点 + mask / offscreen buffer；不能只看 `.moc3` 文件大小。 | atlas + skeleton / mesh / animation 状态 + render buffers；长动画一般不需要逐帧新增整张贴图，但网格 / skin 也有成本。三者计算例见第 6 节。 |
| 11. CPU / GPU | JS 选帧与重绘、浏览器解码 / 上传 / 合成。CSS background-position 不保证只跑 GPU compositor。分辨率大仍能很贵。 | 每帧参数、物理与模型求值，加 WebGL 网格 / mask 绘制；复杂遮罩和透明叠层会改变负担。[Web 注意事项](https://docs.live2d.com/en/cubism-sdk-manual/point-to-note/) | 每帧时间线、骨骼约束 / 网格计算与 WebGL 提交；负担随骨骼、顶点、混合动画、裁剪及透明覆盖变化。没有统一“必比 Live2D 省”的结论。 |
| 12. 移动端 | 小图集 / 低分辨率易控制；要实测高 DPR、纹理尺寸、内存与后台恢复。不能把桌面结果外推手机。 | 官方覆盖 Android / iOS 浏览器；实际可用性需按 SDK / WebGL 支持和模型复杂度实测。[平台表](https://www.live2d.com/en/sdk/about/) | WebGL 路线适用于支持该能力的移动浏览器；fallback 有功能差异。限制绘制分辨率、控制网格与图集，并实测触屏。[spine-ts](https://raw.githubusercontent.com/EsotericSoftware/spine-runtimes/4.3/spine-ts/README.md) |
| 13. reduced-motion | 保留一张静态关键帧，停止计时 / 重绘；导航文字继续可用。CSS 帧播和 JS 帧播分别控制。 | 停止自动 motion、look / 呼吸 / 物理驱动；必要时绘制一次稳定姿势或直接静态立绘，不只把播放速度变慢。 | 停止状态更新 / 自动播放，并保留稳定 setup / 指定姿势或静态 fallback。三条路线都由应用响应偏好。[W3C](https://drafts.csswg.org/mediaqueries-5/#prefers-reduced-motion) |
| 14. 加载体积 | 不增加商业 runtime；图集的帧数、画幅与压缩决定传输量。首屏可以只取静态图 / Idle，后续动作懒加载。 | Core / Framework 代码 + `.moc3` + texture + motion / expression 等；可分角色与动作加载，不能把整套示例包当产品体积。[导出文件](https://docs.live2d.com/en/cubism-editor-manual/export-moc3-motion3-files/) | runtime + binary / JSON + atlas + texture。二进制、裁剪打包与懒加载需实际比较；不能拿 npm unpacked size 直接当下载体积。[导出](https://esotericsoftware.com/spine-export) |
| 15. 开发复杂度 | 单角色有限帧较低；复杂分层换装、混合表演、事件调度会增长，不宜把完整动画引擎重新造在业务组件里。 | 中高：SDK 生命周期、Core 版本、参数优先级、坐标 / 命中、渲染上下文与资源释放都要管理。 | 中：官方 Web backend 能省底层绘制，但 skin / animation mapping、混合与版本匹配仍需适配；加 Pixi 另有依赖边界。 |
| 16. 美术门槛 | 入门路径清晰，但稳定的轮廓、体积、节奏与帧间一致性要求动画经验；生成几张相似图不等于可用循环。 | 分层原画与 rig 是不同技能；面部微动上限高，遮挡补全、网格变形和参数组合需要专门学习 / 外包。 | 拆件、骨骼绑定、网格权重、动画节奏要配合；不懂动画规律时容易出现纸片关节或滑步。 |
| 17. 个人项目适配 | 如果接受有限动作与有限首发资源，最容易控制一次交付范围；大量手绘动作未必比绑定省时间。 | 如果 Portrait 是核心体验且可负担建模，值得投入；授权分类与持续模型维护是前置条件。 | 如果 Home 动作 / 换装是近期核心且能持续制作，前期 rig 投入可能更合算；需要预算和许可。 |
| 18. 未来 Desktop pet | 图集与清单可复用，渲染实现可替换；小型常驻展示适合有限帧。 | 可以沿 Web runtime 或另评 Native SDK；精细正面陪聊有价值，不能因此假设桌面宿主和许可自动解决。 | Web 或原生 runtime 均存在，适合持续全身动作；数据 / rig 复用需版本一致。所有路线都另需窗口、置顶、点击穿透、DPI、休眠与功耗设计。 |

## 6. 内存与性能：可计算部分、未知部分

### 6.1 三条路线共用的纹理估算

假设未压缩 RGBA8，每像素 4 byte，无 mipmap，则一个实际上传的纹理页面占用近似：

`textureBytes = width × height × 4`

`textureMiB = Σ(textureBytes) / 1,048,576`

据此：`1024² ≈ 4 MiB`、`2048² ≈ 16 MiB`、`4096² ≈ 64 MiB`。完整 mipmap 链在常见二维情形下额外约三分之一。以上是格式 / 面积算术，不是某 SDK 的实测内存；padding、打包空白、GPU 压缩格式、对齐、浏览器副本及驱动会改变结果。PNG / WebP 的网络压缩体积不能代入这个公式。

**Sprite 示例（设计假设）**：一个动作 12 帧、每帧 `256 × 256`，无裁切紧密拼装，RGBA8 约 `12 × 256 × 256 × 4 = 3 MiB`。若全部预载 3 阶段 × 5 动作 × 3 服装且每个组合都单独烘焙，纹理面积总量约 `135 MiB`，还没算 Portrait 和场景。真实 Egg 未必需要 5 动作 / 3 服装，此例只说明组合数量为何必须控制；不是本轮资产要求。

**Live2D / Spine 示例（设计假设）**：某模型只有一张 `2048 × 2048` atlas，纹理基数约 `16 MiB`；再加一张就是约 `32 MiB`。播放更多动作不会像全帧烘焙那样必然增加整张画面的每帧纹理，但曲线、骨架、顶点、模型数据仍会增长。这个假设不能推出“任意骨骼模型比任意 Sprite 更小”。

**绘制表面示例（设计假设）**：`400 × 500 CSS px` 的视口，DPR 为 2，单张 RGBA8 颜色缓冲约 `400 × 500 × 2² × 4 = 3.05 MiB`；DPR 为 3 则约 `6.87 MiB`。深度 / stencil、抗锯齿、双缓冲与 offscreen 另计。Shell 显示几十像素，不值得直接常驻一套大 Portrait 贴图。

### 6.2 对 CPU / GPU 能确定什么

Sprite 的核心可简化为选帧、裁切与合成；Live2D 增加参数与变形模型求值；Spine 增加骨骼 / 约束 / 时间线求值。但实际总成本还由贴图尺寸、屏幕面积、透明覆盖、mask、draw call、帧率、实例数、浏览器和设备决定。Pixi 官方也把 batch、纹理、过滤器、mask 等列为优化变量。[Pixi 性能建议](https://pixijs.com/8.x/guides/concepts/performance-tips)

因此本轮不写“移动端稳定 60 FPS”“某方案仅占 20 MB”“某路线永远最省电”。三条路线目前都 **未实测**。静态 fallback、可见时才更新、离开页面释放重资源，是下一阶段需要验证的策略，不是已完成的优化成果。

### 6.3 第二阶段才开展的最小 Sprite 验证

用已选绫页的一个最小 Idle，记录：冷加载传输字节 / 解码时间、首次可见耗时、持续 Idle 的帧时间和 CPU、可获得的 GPU 资源证据、后台 / 前台恢复、页面切换后内存是否持续增长。至少覆盖目标桌面浏览器与可取得的低配移动设备；缺少实体设备或 GPU 内存 API 时明确记录缺口，不把模拟器说成实机。首版不制作另外两种 Runtime 样本来重新选型。

检查资源失败、暂停控制、页面 hidden、系统 `prefers-reduced-motion`、高 DPR 与透明边缘；首版原生帧播不以 WebGL 为前提。保留静态第一帧和可点击文字入口，伙伴展示失败不能阻断 Gallery / Feed / Chat。未来若引入 WebGL，再补上下文丢失等测试；本轮没有启动技术实验。

## 7. 制作与显示合同：避免身份被 runtime 绑住

首版资产清单使用本地角色资源键 / visualStage / representation / assetVersion，并声明静态 fallback、画幅、脚底锚点与帧时长。调用方保留真实 currentStage 输入；视觉选择不改后端 lifeStage，也不要求 speciesId。未来多角色、换装或 renderer 类型按需要扩展，不提前建立 DB 字段或公共协议。

| 表现层 | 本轮设计关注点 | 后续制作建议 |
| --- | --- | --- |
| Shell Presence | 与当前固定导航位兼容；小尺寸轮廓可识别、安静、无业务遮挡 | 单独裁制小尺寸姿势；可提出短 Idle，但静止帧必须成立。不要把 Portrait 缩到 28px 当完成。 |
| Habitat / Home | 当前 Hero 中全身尺度、脚底、宽翼边界与稳定占位 | 独立静态 Scene + 一个最小 Idle，不增加 Look / Walk / Sleep。 |
| Conversation Portrait | 发型、种族结构、主纹样与 Scene 一致；不阻碍阅读 | 正常比例 Neutral + 可选 1～2 个差分；无可信表现状态时只显示 Neutral。 |

生命阶段与表现比例相互独立；按最新人工指示，A 的 Web Adult 使用正常比例 Scene 全身与正常比例 Portrait，Q 版只保留为未来桌宠参考，不表示 Juvenile。三阶段的身体变化可以很大，但用户名称、记忆、关系与经历仍属于原 Instance。即使以后由 Sprite 升级成 Spine，旧资产版本和实例身份也不应混为同一个 ID。

制作源文件必须保留；导出的 sprite、`.moc3` 或 skeleton data 都不应是唯一可维护资产。交付时固定色彩、轮廓要点、图层命名与动作语义，可以减少下一位画师 / 动画师接手时的返工。

## 8. PixiJS 与其他路线的边界

PixiJS 提供 renderer、纹理 / scene graph / ticker 等，不会替团队绘制原画、拆件或绑定。`AnimatedSprite` 可播放图集；官方 `spine-pixi` 可承载 Spine。Pixi 本身的 MIT 不改变 Spine 的许可。[Pixi Application](https://pixijs.com/8.x/guides/components/application)、[AnimatedSprite](https://github.com/pixijs/pixijs/blob/v8.21.0/src/scene/sprite-animated/AnimatedSprite.ts)、[Spine Pixi 官方适配](https://esotericsoftware.com/spine-pixi)

R05 不增加 Unity / Godot Web 导出、3D 模型、完整游戏引擎或另一套状态机评估：当前需要的是伙伴身份与少量 2D 展示，仓库没有这些基础；此阶段加入它们会增加无助于角色选择的实验范围。这是范围判断，不是断言其他工具无法实现。

Desktop pet 也不是选定 Web renderer 就自然完成：窗口行为、托盘、跨屏 DPI、点击穿透、前后台调度属于未来桌面宿主。身体资产可复用程度与这部分宿主开发分别评估。本轮不选定 Electron / Tauri，也不把它们的成本藏进角色 runtime 数字中。

## 9. 生产准备与未来风险

1. 角色与首版路线已经决定。待落实的是独立生产母版、透明静态图、最小 Idle 的帧间一致性、资源预算和源文件交付，不是再次评选角色或 Runtime。
2. 首版不换装、不做多角色、不做完整动作集；表情差分可选，表情状态集留给 R06 / R11。
3. 未来实际考虑 Live2D / Spine 时再核验相应许可、开发主体和资产产能；保留的历史许可调查不是首版 Sprite 接入的阻塞项，也不是未来许可保证。
4. 移动内存、加载、透明边缘、后台恢复仍未实测，数字示例与趋势不构成验收结果。
