## 第 1 题：图片上传完整链路

### 原题

用户在个人空间上传一张本地图片。请从前端选择文件开始，一直讲到图片最终能够在图库中展示，并解释为什么不能只保存 COS URL。

### 推荐答题结构

请求进入 → 业务校验 → 文件存储 → 元数据入库 → VO 返回 → 缓存失效。

### 标准答案

> 前端根据输入类型调用文件上传或 URL 上传接口，并在请求中携带 `spaceId` 等信息。文件接口接收 `MultipartFile` 和 `PictureUploadRequest`，URL 接口从请求体取得 `fileUrl`，两个接口最终都调用统一的 `uploadPicture` Service 方法。Controller 还会从 Session 中取得当前登录用户。
>
> Service 校验输入、空间是否存在、用户是否具有上传权限，以及空间是否允许继续上传。之后根据输入源选择文件模板或 URL 模板，处理图片并将原图、缩略图等上传到腾讯 COS。上传结果包含 URL、名称、大小、宽高、比例和格式等元数据。
>
> Service 使用这些结果构造 `Picture`，补充 `userId`、`spaceId` 和审核信息后写入 MySQL，再转换成 `PictureVO` 返回。Controller 包装为 `BaseResponse`，清理图片列表缓存后返回前端。
>
> COS 适合保存图片二进制，MySQL 负责图片归属、空间关系、权限、审核、分页检索和图库分析等结构化业务数据。只有 COS URL 时，系统无法高效回答图片属于谁、谁能看、是否审核以及如何分类统计。

### 今日易错点

- “COS 适合大文件”只能解释文件为什么进 COS，不能解释业务元数据为什么必须进 MySQL。
- 不要遗漏上传成功后的列表缓存清理。
- 文件上传和 URL 上传是两个 Controller 接口，但最终复用同一个 Service 入口。

### 继续追问

2. 上传完成后为什么需要清理列表缓存？

## 第 2 题：`@Transactional` 能否回滚 COS？

### 原题

图片成功上传到 COS，但 MySQL 插入 `Picture` 失败。加上 `@Transactional` 后 COS 会自动删除吗？产生什么问题？如何补偿？

### 推荐答题结构

本地事务范围 → 外部系统不受控 → 孤儿文件 → 同步补偿 → 异步兜底。

### 标准答案

> `@Transactional` 管理的是本地数据库事务，腾讯 COS 是通过网络调用的外部系统，没有加入 MySQL 事务，所以数据库回滚不会自动删除 COS 对象。COS 成功而 MySQL 失败会产生没有业务记录引用的孤儿文件，占用存储空间但不会出现在正常图库查询中。
>
> 当前项目可以在捕获数据库异常后，立即尝试删除本次上传的新对象。如果删除仍因超时或网络错误失败，就记录对象 Key 和失败原因，由定时补偿任务重试。周期性清理还应使用业务路径、上传任务 ID 和安全时间窗口，避免删除仍在处理或被其他记录引用的对象。
>
> 更复杂的异步方案可以先在同一数据库事务中写入 `PENDING` 上传任务或 Outbox 事件，再由后台上传 COS，成功后写 URL 并改为 `SUCCESS`，失败则重试并最终进入 `FAILED`。这属于可恢复的最终一致性，而不是跨系统本地事务。

### 今日易错点

- 不要只说“捕获异常回滚”，因为回滚只能撤销数据库操作。
- COS 删除本身也可能失败，必须保留重试依据。
- 直接发消息也可能丢失，任务或 Outbox 记录应与业务状态在同一数据库事务中落库。

### 继续追问

1. 定时清理如何避免误删刚上传但事务尚未提交的文件？
2. 为什么不能遍历 COS 后删除所有数据库查不到的 Key？

## 第 3 题：先上传 COS 还是先写 MySQL？

### 原题

比较方案 A“先 COS 后 MySQL”和方案 B“先 MySQL 后 COS”的失败残留、用户可见状态、补偿难度与当前项目适用性。

### 推荐答题结构

分别讲失败状态 → 如何隐藏或补偿 → 结合当前上传结果字段做选择 → 说明未来切换条件。

### 标准答案

> 方案 A 先上传 COS，再写 MySQL。数据库失败时会留下孤儿文件，但没有数据库记录就不会出现在正常图库中，主要问题是存储占用，可以同步删除并异步补偿。
>
> 方案 B 先写 MySQL，再上传 COS。上传失败时会留下没有有效 URL 或完整元数据的记录。如果查询不区分状态，用户可能看到裂图。它可以通过 `PENDING`、`SUCCESS`、`FAILED` 状态并只展示成功记录来解决，但需要异步任务、重试、超时恢复和失败清理。
>
> 当前项目需要先取得 COS 处理后的 URL、缩略图、大小、宽高和格式再构造完整 `Picture`，因此更适合方案 A。未来若文件上传很慢、必须异步化或需要更强任务追踪，再考虑方案 B 的状态机。

### 今日易错点

- 方案 B 不是必然展示裂图；有状态字段和查询过滤时可以隐藏未完成记录，只是复杂度更高。
- 选型不能只说哪种“更安全”，要结合项目需要哪些上传结果。

## 第 4 题：重新上传如何切换新旧文件？

### 原题

新 COS 上传成功但数据库更新失败时删什么？数据库更新成功后，旧 COS 文件何时删除？为什么不能提前删除？

### 推荐答题结构

保留旧版本 → 上传新版本 → 提交数据库引用切换 → 删除旧版本 → 删除失败补偿。

### 标准答案

> 重新上传时应让旧数据库记录和旧文件继续作为当前可用版本。新文件上传成功但数据库更新失败时，删除新上传的对象，保留旧 URL 与旧文件，用户仍可访问原图。
>
> 数据库切换到新 URL 并且事务成功提交后，才能清理旧文件。不能在更新前删除，也不能在 `UPDATE` SQL 刚执行成功时立即删除，因为后续异常仍可能让事务回滚到旧 URL，造成数据库重新指向已删除对象。
>
> 更稳妥的方式是在事务提交后产生旧文件清理任务，异步删除并支持重试。同时需要确认旧对象没有被其他业务记录共享引用。

### 今日易错点

- SQL 执行成功不等于事务已经提交。
- 删除旧对象前要确认没有其他引用。

### 继续追问

1. Spring 中怎样在事务提交后触发清理事件？
2. 如果新旧文件的删除都失败，补偿任务要记录哪些字段？

> 记忆：新文件失败删新的，切换提交后删旧的。

## 第 5 题：事务 ACID

### 原题

解释事务的原子性、一致性、隔离性和持久性，并结合图片元数据入库举例。

### 推荐答题结构

英文名称 → 一句话定义 → 项目例子 → 辨析容易混淆的边界。

### 标准答案

> 原子性（Atomicity）表示事务内的数据库操作要么全部成功，要么全部回滚。例如新增图片记录和更新空间用量不能只成功一个。
>
> 一致性（Consistency）表示事务前后数据都满足数据库约束和业务规则。例如新增 10 MB 图片后，空间统计应正确增加 10 MB，而不是增加 100 MB；图片数量与有效图片记录也应匹配。
>
> 隔离性（Isolation）表示并发事务之间的可见性受隔离级别控制，避免脏读、不可重复读等异常，使并发执行结果尽量接近正确的串行结果。
>
> 持久性（Durability）表示事务一旦成功提交，即使数据库进程崩溃或服务器重启，结果仍能通过 redo log 等机制恢复。

### 今日易错点

- 一致性不是“数据不变化”，而是事务完成后仍满足规则。
- 隔离性不是“其他事务完全不能打扰”，而是控制并发事务的可见性。
- 持久性从事务成功提交开始成立，不是从执行一条 INSERT 开始。

### 继续追问

1. 原子性和持久性分别依赖 undo log 还是 redo log？
2. 一致性为什么常被称为事务最终目标？

> 记忆：A 管全做或全不做，C 管业务结果正确，I 管并发可见性，D 管提交后不丢。

## 第 6 题：脏读、不可重复读与幻读

### 原题

分别解释三种并发读取异常，给出图片项目示例，并说出 InnoDB 默认隔离级别。

### 推荐答题结构

事务 A 做什么 → 事务 B 在同一事务中怎样读取 → 两次结果为何异常。

### 标准答案

> 脏读是 B 读到了 A 尚未提交的数据，A 随后回滚，B 曾看到的状态从未正式生效。例如 B 读取到 A 尚未提交的“审核通过”并提前展示图片。
>
> 不可重复读是 B 在同一事务中两次读取同一行，期间 A 修改该行并提交，导致字段值不同。例如图片名称第一次是“风景图”，第二次变成“北京风景”。
>
> 幻读是 B 在同一事务中两次执行相同范围查询，期间 A 插入或删除符合条件的行，导致结果集行数或行集合变化。例如同一空间第一次查到 20 张图片，第二次变为 21 张。
>
> MySQL InnoDB 默认通常使用 `REPEATABLE READ`，即可重复读。

### 今日易错点

- 不可重复读的主体必须是同一个事务两次读取同一行。
- 幻读关注符合范围条件的“行”增加或消失，不是同一行字段变化。

### 继续追问

1. 四种隔离级别从低到高是什么？
2. InnoDB 可重复读如何处理许多幻读场景？

### 补充：四种隔离级别

| 隔离级别 | 主要效果 |
| --- | --- |
| READ UNCOMMITTED | 可能出现脏读、不可重复读、幻读 |
| READ COMMITTED | 避免脏读 |
| REPEATABLE READ | 避免脏读和不可重复读 |
| SERIALIZABLE | 进一步避免幻读，但并发能力最低 |

按 SQL 标准，可重复读仍可能有幻读；InnoDB 结合 MVCC 和 Next-Key Lock，在许多场景中能够避免，需要区分快照读与当前读。

## 第 7 题：MVCC 如何实现非阻塞快照读？

### 原题

解释 InnoDB MVCC，覆盖隐藏事务信息、undo log、Read View、快照读和写写冲突。

### 推荐答题结构

更新保存历史版本 → Read View 判断可见性 → 沿版本链读取 → 说明只优化读写并发。

### 标准答案

> MVCC 是 InnoDB 的多版本并发控制机制。聚簇索引记录中包含最后修改该行的事务 ID `DB_TRX_ID` 和指向 undo log 旧版本的 `DB_ROLL_PTR`。更新记录时，旧值写入 undo log，并通过回滚指针形成版本链。
>
> 事务执行快照读时生成 Read View，记录生成快照时的活跃事务范围。InnoDB 将版本的事务 ID 与 Read View 比较，判断它是否对当前事务可见；若当前版本不可见，就沿回滚指针寻找更早的可见版本。
>
> 因此读事务可以读取满足自己视图的旧版本，而写事务继续产生新版本，普通快照读不一定阻塞写操作。MVCC 主要优化读写并发，不能单独解决两个事务同时修改同一行；写写冲突仍需要行锁、乐观锁、条件更新和死锁重试。

### 今日易错点

- undo log 不是“提前准备一个版本”，而是在更新时保存旧值并形成历史版本链。
- 快照读不一定读取 undo log；当前版本可见时可直接读取。
- MVCC 不负责让两个写事务无冲突地同时修改同一行。

### 继续追问

1. RC 和 RR 生成 Read View 的时机有什么区别？
2. undo log 何时可以被清理？

> 记忆：事务 ID → 回滚指针 → undo 版本链 → Read View 判断可见性。

## 第 8 题：快照读、当前读与额度并发

### 原题

比较普通 `SELECT` 与 `SELECT ... FOR UPDATE`，再说明两个用户同时上传时如何避免基于相同剩余额度同时放行。

### 推荐答题结构

快照读的可见版本 → 当前读的最新版本与锁 → 悲观锁方案 → 条件更新方案。

### 标准答案

> 普通 `SELECT` 通常是快照读，根据 Read View 读取可见版本，不主动对记录加排他锁。`SELECT ... FOR UPDATE` 是当前读，需要读取最新状态，并对符合条件的记录加排他锁；其他事务修改或锁定同一行时需要等待。
>
> 悲观锁方案是在事务中使用 `FOR UPDATE` 锁住空间行，检查额度、更新用量后提交。但不应持有数据库锁去执行耗时的 COS 网络上传。
>
> 另一种方案是把检查与更新合成一条原子 SQL，并根据受影响行数判断成功：

```sql
UPDATE space
SET totalSize = totalSize + :pictureSize,
    totalCount = totalCount + 1
WHERE id = :spaceId
  AND totalSize + :pictureSize <= maxSize
  AND totalCount + 1 <= maxCount;
```

> 返回 1 表示预占成功，返回 0 表示空间不存在或严格额度不足。后续上传失败时需要释放预占额度。

### 软额度：当前项目的真实业务口径

当前项目不是严格额度预占，而是刻意采用类似网盘的软上限策略：

```text
上传前尚未达到上限
→ 允许本次上传跨过上限
→ 跨过后禁止继续上传
→ 引导用户升级空间
```

因此当前判断已有 `totalSize >= maxSize` 后阻止下一次上传，符合产品意图，不应描述成实现缺陷。严格条件更新 SQL 是另一种“绝不超额”的产品方案，不能未经需求确认就替换。

需要准确说明边界：如果产品文案承诺只允许“超一点点”，还应限制单文件最大尺寸，否则最后一次上传理论上可能让用量超过上限很多；并发上传也可能让多个请求同时越过软上限。是否允许这种幅度，应由产品规则明确。

### 今日易错点

- `FOR UPDATE` 的核心是锁住最新记录，不只是“读取后再修改”。
- 不要拿着行锁执行长时间外部调用。
- 技术上能做严格原子扣减，不代表业务上必须禁止所有超额。

### 继续追问

1. 软上限下如何控制最大超额幅度？
2. 预占额度方案失败后如何幂等释放？

## 第 9 题：图库分析慢 SQL 如何排查？

### 原题

下面的分类统计突然变慢，如何从前端定位到 SQL 并优化？

```sql
SELECT category, COUNT(*)
FROM picture
WHERE spaceId = ?
  AND isDelete = 0
GROUP BY category;
```

### 推荐答题结构

定位层级 → 获取慢 SQL → 看执行计划 → 修改索引或 SQL → 相同数据验证 → 缓存与预聚合。

### 标准答案

> 先在浏览器 Network 确认接口总耗时，再通过 Nginx、Controller、Service、Mapper 的日志或链路追踪拆分 Java、Redis、外部调用与 SQL 耗时，避免把接口慢直接等同于 SQL 慢。随后使用 MySQL 慢查询日志取得真实 SQL 与参数。
>
> 使用 `EXPLAIN` 重点查看 `type`、`possible_keys`、`key`、`key_len`、`rows`、`filtered` 和 `Extra`，关注全表扫描、`Using temporary` 与 `Using filesort`。这个查询可以评估 `(spaceId, isDelete, category)` 联合索引，使前两列完成等值过滤，并利用 `category` 进行分组扫描。
>
> 有索引仍可能不走，原因包括结果占比过高、索引列使用函数、隐式类型转换、前导模糊匹配、破坏最左前缀、部分 `OR` 分支无索引、表太小或统计信息不准。修改后必须在相同数据量与参数下重新测量。
>
> 数据继续增长时，优先考虑短期缓存、避免 N+1、异步统计和按空间/日期/分类维护预聚合表，再根据指标考虑读副本或分析数据库。分库分表不是默认答案，跨分片 `GROUP BY` 还可能增加聚合合并成本。

### 今日易错点

- 浏览器只能证明接口整体耗时，仍需继续定位 Java 与 SQL。
- 索引字段顺序不能只背“区分度高放左边”，要结合过滤、排序和分组。
- 数据量大不等于立刻分库分表。

### 继续追问

1. `Using index`、`Using temporary`、`Using filesort` 分别意味着什么？
2. 如何设计并维护分类统计预聚合表？

## 第 10 题：图库分析四个图表都“暂无数据”

### 原题

用户个人空间有图片，但四个分析图表都没有数据。请区分没有发请求、参数错误、权限拒绝、SQL 错误、前端未渲染和线上旧包。

### 推荐答题结构

页面状态 → Network → 请求参数 → 状态码与响应体 → 后端日志/SQL → 前端映射 → 部署版本证据。

### 标准答案

> 先确认图表组件是否挂载、当前用户是否 hydration 完成、页面是否处于加载或错误状态，并查看 Console。然后用 Network 检查分析请求是否发出、是否被取消、是否携带 Session，以及请求方法和 URL 是否正确。
>
> 核对 `spaceId`、`userId`、`queryPublic`、时间维度等参数，确保属于当前用户与当前空间。再根据响应分类：401 是未登录，403 是无权限，404 是空间不存在，200 加空数组表示后端成功但结果为空，200 加有效数据则优先检查前端。
>
> 后端侧核对 Controller 实际参数、登录用户、权限判断和 MyBatis SQL，并用相同参数直接查询数据库，检查 `spaceId`、`userId`、`isDelete` 和审核状态等条件。前端侧检查 Axios 解包层级、字段映射、空状态、Vue 响应式赋值、ECharts `setOption`、容器宽高和 Console 异常。
>
> 本地修复但线上仍异常时，再核对服务器提交 SHA、`git pull` 结果、构建退出码、镜像 ID、容器实际镜像、静态 chunk hash 和 Nginx 静态目录，不能只反复清浏览器缓存。

### 真实故障复盘

本项目曾出现当前用户信息尚未 hydration 就提前发出分析请求，导致用户或空间上下文不正确；修复后线上仍不变化，又发现服务器 `git pull` 失败及 Docker 构建命令拼写错误，实际仍使用旧代码或旧镜像。这是有价值的真实案例，但未知故障仍应逐层取证，不能直接套用历史根因。

### 今日易错点

- “暂无数据”可能是失败兜底文案，不能直接推断数据库为空。
- 先说排查路径，再说历史上最终发现了什么。
- 本地代码正确不代表服务器提交、镜像、容器和浏览器资源都已更新。

2. 如何证明浏览器拿到的是新构建的前端资源？

## 最终纠错题：后端返回有效数据但图表仍为空

### 原题

Network 中 HTTP 200，响应包含：

```json
{
  "code": 0,
  "data": [
    { "category": "风景", "count": 12 },
    { "category": "人物", "count": 5 }
  ]
}
```

页面仍显示“暂无数据”。可以排除什么？接下来查哪里？

### 标准答案

> 请求未发出、Session 缺失、后端权限拒绝、SQL 空结果和 HTTP 请求失败基本可以排除。接下来只追踪前端消费链路：检查 Axios 拦截器后的响应结构，避免页面多取或少取一层 `data`；检查后端的 `category/count` 是否转换为图表需要的 `name/value`；检查空状态是否在成功后复位，数据是否正确写入 Vue 的 `ref`；最后检查 DOM 挂载、ECharts 初始化、`setOption` 调用、容器宽高和 Console 异常。`resize` 只解决尺寸变化，不是所有空图表的通用修复。

## 今日重点纠错

1. `@Transactional` 只能回滚 MySQL，不能回滚 COS。
2. 旧 COS 文件必须在数据库切换引用且事务提交后再删除。
3. 原子性关心“做没做完整”，一致性关心“做完以后对不对”。
4. 快照读不一定读取 undo log，当前版本可见时可直接读取。
5. MVCC 优化快照读与写的并发，不单独解决写写冲突。
6. 慢查询先分层定位，分库分表不是默认答案。
7. 当前容量是软上限业务策略，不应用严格额度方案否定既定产品规则。
