## 第 3 题：如何防止成员被重复添加？

### 原题

如果 `space_user` 没有 `(spaceId, userId)` 联合唯一索引，只在代码中先查询、不存在再插入，高并发下可能发生什么？如何解决？

### 推荐答题结构

按“并发时序 → 数据库兜底 → 业务提示 → 事务边界”回答。

### 标准答案

> 高并发下，两个请求可能同时查询到成员不存在，然后都执行插入，最终产生重复成员。普通事务不能自动解决这个竞态，因为两个事务都可能在插入前读到“不存在”。  
> 我会在数据库中为 `(spaceId, userId)` 建立联合唯一索引，从数据层保证同一个用户不能重复加入同一空间。业务层仍可先查询，以便提前返回友好提示；数据库唯一约束负责最终兜底。如果并发下触发重复键异常，就捕获并转换为“成员已存在”的业务异常。添加成员若还伴随其他数据库修改，再使用事务保证这些操作一起成功或回滚。

### 今日易错点

- 误以为普通事务可以阻止两个请求同时“先查后插”。
- 只说“加锁”，没有说明是 JVM 锁、分布式锁还是数据库约束。
- `synchronized` 只能限制单个 JVM，多实例部署后不能作为最终一致性保证。

### 继续追问

1. 为什么事务不能代替唯一索引？
2. 捕获 `DuplicateKeyException` 后应该向前端返回什么？

> 记忆：事务保证一组操作的完整性，唯一索引保证数据不能重复。

## 第 4 题：图片详情请求如何往返？

### 原题

前端调用“查询图片详情”接口，请从浏览器开始，按顺序说明请求如何到达数据库，又如何返回前端。

### 推荐答题结构

分为四段：浏览器发请求、网关与 MVC 调度、业务与数据库、响应与异常。

### 标准答案

> 用户在 Vue 页面点击图片后，组件通过 Axios 发起 HTTP 请求，请求先到 Nginx，再被反向代理到 Spring Boot。进入应用后，请求先经过 Filter，然后由 `DispatcherServlet` 根据路由找到对应 Controller，在调用 Controller 前还会经过配置的 Interceptor。  
> Controller 解析图片 ID 等参数并调用 Service。Service 负责查询条件、资源存在性和访问权限等业务判断，再通过 Mapper 访问 MySQL。Mapper 返回 Entity 后，Service 执行业务处理并按需要组装 VO，Controller 最后包装为统一的 `BaseResponse`。Spring MVC 使用 Jackson 将响应序列化为 JSON，经 Nginx 返回 Axios，Vue 再更新页面。若过程中抛出异常，则由全局异常处理器转换为统一错误响应。

```text
用户 → Vue → Axios → Nginx → Filter → DispatcherServlet
→ Interceptor → Controller → Service → Mapper → MySQL
→ Mapper → Service → VO → Controller → BaseResponse
→ Jackson → Nginx → Axios → Vue
```

### 今日易错点

- 把 Nginx 放在 Vue、Axios 前面；实际上 Vue 和 Axios 运行在浏览器中。
- 漏掉 Mapper 与 MySQL 的往返。
- 图片详情可能只接收 `id` 请求参数，不一定使用 DTO。
- 漏掉全局异常处理分支。

### 继续追问

1. Filter、Interceptor 和 AOP 的执行位置有什么区别？
2. `DispatcherServlet` 的职责是什么？

## 第 5 题：为什么需要 Service 层？

### 原题

Controller 也能直接调用 Mapper，为什么仍需要 Service？结合图片详情说明 Controller、Service、Mapper 的职责。

### 推荐答题结构

先说三层边界，再说复用、测试、事务和未来调用方，最后落到图片详情流程。

### 标准答案

> Controller 负责 HTTP 层适配，包括接收和校验请求参数、获取当前登录用户、调用 Service 以及包装统一响应。Service 负责业务规则，例如判断图片是否存在、当前用户是否有权查看、是否需要更新统计，以及组装适合前端的数据。Mapper 只负责数据库访问，根据查询条件执行 SQL 并返回实体。  
> 如果 Controller 直接调用 Mapper，权限、事务和业务规则会散落在多个接口中，难以复用和测试。当同一业务需要被 WebSocket、定时任务或其他接口调用时，还可能复制逻辑。查询图片详情时，Controller 接收 ID 和用户上下文，Service 完成查询与授权，Mapper 读取 MySQL，Service 组装 VO，Controller 包装 `BaseResponse` 返回。

### 今日易错点

- “Service 只在逻辑复杂时才需要”不准确，Service 更重要的意义是定义可复用的业务边界。
- Controller 可以做参数与协议适配，但不应承载资源权限等业务规则。

## 第 6 题：DTO、Entity、VO 有什么区别？

### 原题

解释 DTO、Entity、VO。为什么查询图片详情时不直接把 `Picture` Entity 原样返回前端？至少给出两个风险。

### 推荐答题结构

使用“DTO 管输入、Entity 管存储、VO 管输出”，再补充安全、耦合和组合数据。

### 标准答案

> DTO 是数据传输对象，常用于承接客户端提交的数据，并限制客户端允许传入的字段；Entity 是持久化实体，通常与数据库表结构对应；VO 是视图对象，用于返回符合前端展示需求的数据。  
> 图片详情不直接返回 `Picture` Entity，一是防止内部状态、审核信息或逻辑删除字段意外泄露；二是避免接口格式与数据库表结构强耦合；三是避免返回前端不需要的字段。此外，详情页可能还需要上传用户、所属空间和当前用户权限等组合信息，这些应通过 VO 统一组装。

### 今日易错点

- Entity 不是“没有修改过的实体”，而是面向持久化和数据库映射的对象。
- DTO 不只用于前端请求，本质是跨边界传输数据的结构。

1. 为什么接收编辑请求时也不应直接使用 Entity？

## 第 7 题：如何为图片列表设计联合索引？

### 原题

```sql
SELECT *
FROM picture
WHERE spaceId = ?
  AND isDelete = 0
ORDER BY createTime DESC
LIMIT 20;
```

如何设计联合索引？为什么按这个顺序？它怎样帮助查询？

### 推荐答题结构

先给索引，再依次解释等值条件、排序、`LIMIT`、回表和查询模式。

### 标准答案

> 我会建立 `(spaceId, isDelete, createTime)` 联合索引。`spaceId` 和 `isDelete` 都是等值条件，可以先定位指定空间中未删除的数据范围；`createTime` 放在后面，使该范围内的数据按创建时间有序，从而减少 `ORDER BY` 的额外排序，并结合 `LIMIT 20` 提前结束扫描。  
> 由于查询使用 `SELECT *`，索引不包含图片表全部字段，所以通常仍需根据主键回到聚簇索引读取完整记录，不能称为覆盖索引。它的主要收益是缩小扫描范围、利用索引顺序和减少排序成本。

```sql
CREATE INDEX idx_space_delete_create
ON picture(spaceId, isDelete, createTime);
```

### 今日易错点

- 把 `isDelete = 0` 说成查询已删除图片。
- 误以为查询条件中的三列都在索引里，`SELECT *` 就能覆盖索引。
- 只按字段区分度机械排序，没有结合等值过滤和排序需求。

### 继续追问

1. 如果只建立 `(spaceId, createTime)`，会有什么差异？
2. 如何用 `EXPLAIN` 判断是否发生 filesort 和回表？

## 第 8 题：InnoDB 为什么使用 B+Tree？

### 原题

为什么使用 B+Tree，而不使用普通二叉搜索树或 Hash 表？从磁盘 I/O、树高、范围查询和排序能力回答。

### 推荐答题结构

按“磁盘页 → 多叉低树高 → 叶子有序链表 → 与二叉树/Hash 对比”回答。

### 标准答案

> InnoDB 使用 B+Tree，首先因为它是多叉树。非叶子节点主要保存索引键和子节点指针，一个磁盘页能容纳大量分支，因此相同数据量下树高通常很低，查询需要的磁盘 I/O 次数较少。普通二叉搜索树每个节点只有两个分支，树更高；不平衡时还可能退化。  
> B+Tree 的索引记录集中在叶子节点，叶子节点按键值有序并相互连接，因此既支持等值查询，也适合范围查询、排序和顺序扫描。Hash 表虽然平均等值查询很快，但不保存全局顺序，无法高效支持范围查询、`ORDER BY` 和最左前缀匹配。

### 今日易错点

- “前几层只放索引”不够专业，应说“非叶子节点保存索引键和子节点指针”。
- 需要补充叶子节点有序连接，这是范围扫描的重要原因。

### 继续追问

1. 聚簇索引和二级索引的叶子节点分别保存什么？
2. 为什么主键过大会增加二级索引占用？

## 第 9 题：`HashMap.put` 如何执行？

### 原题

说明 `HashMap.put(key, value)` 的大致过程，包括定位桶、冲突处理、树化、扩容，以及为什么重写 `equals()` 时通常也要重写 `hashCode()`。

### 推荐答题结构

按“计算 hash → 定位桶 → 比较或插入 → 树化 → 扩容 → equals/hashCode 契约”回答。

### 标准答案

> `put` 时，HashMap 先取得 Key 的 `hashCode()`，再进行扰动计算，让高位也参与桶位置计算，然后通过 `(n - 1) & hash` 定位数组桶。桶为空时直接插入；桶中已有元素时，先比较 hash，再通过引用相等或 `equals()` 判断是否为相同 Key，相同则覆盖 Value，不同则追加到链表或红黑树。  
> Java 8 中，链表长度达到树化阈值 8 且数组容量至少为 64 时，链表才会转换为红黑树；容量较小时通常优先扩容。元素数量超过 `capacity × loadFactor` 后会扩容，默认负载因子通常为 0.75，容量通常扩大为两倍。  
> `equals()` 相等的对象必须具有相同的 `hashCode()`。如果只重写 `equals()`，逻辑上相等的 Key 可能被定位到不同桶，导致查询不到或出现重复 Key。

### 今日易错点

- 顺序应是先取得 `hashCode()`，再进行扰动，不是扰动后才得到 hashCode。
- 桶位置通常使用 `(n - 1) & hash`，不是普通除法取余。
- 链表达到 8 并不必然树化，还要考虑数组容量是否至少为 64。

### 继续追问

1. 为什么 HashMap 容量通常保持为 2 的幂？
2. HashMap 为什么不是线程安全的？

## 第 10 题：`ArrayList` 还是 `LinkedList`？

### 原题

图片搜索结果需要频繁按下标读取，偶尔在末尾添加，几乎不在中间插入。选择 `ArrayList` 还是 `LinkedList`？说明底层结构、复杂度、中间插入和 CPU 缓存局部性。

### 推荐答题结构

先根据访问模式作结论，再比较随机访问、末尾追加、中间插入、内存和缓存局部性。

### 标准答案

> 我会选择 `ArrayList`。它底层使用动态数组，按下标随机访问是 `O(1)`；`LinkedList` 是双向链表，按下标访问需要从头部或尾部逐个寻找，复杂度是 `O(n)`。这个场景主要是频繁读取和末尾追加，而 ArrayList 末尾添加的均摊复杂度也是 `O(1)`。  
> LinkedList 只有在已经取得目标节点引用时，插入节点本身才是 `O(1)`；如果先按下标寻找插入位置，整体仍是 `O(n)`，因此中间插入不一定更快。ArrayList 的元素引用连续存储，额外内存更少，并具有更好的 CPU 缓存局部性；LinkedList 每个节点还要保存前后指针，节点通常分散在堆中，遍历时缓存命中率较低。

### 今日易错点

- CPU 会把访问地址附近的数据一并载入缓存；连续数组更容易命中，分散链表需要不断追踪指针。
- ArrayList 偶尔扩容需要复制，但末尾添加的均摊复杂度仍为 `O(1)`。

### 继续追问

1. ArrayList 扩容的大致过程是什么？
2. CopyOnWriteArrayList 适合什么场景？

> 项目使用腾讯 COS 存储图片文件，使用 Sa-Token 完成登录认证并结合空间权限规则实现资源授权；使用 WebSocket 和 Redis 支持团队协同编辑，使用 Caffeine 与 Redis 构建多级缓存，同时接入通义千问 Agent 和 MCP 图片生成工具。  
> 我主要负责数据库表结构设计、技术方案选型、核心业务逻辑实现、权限方案落地和前后端接口对齐。项目中比较有代表性的难点是多类型空间下的资源权限控制。同一个图片操作需要综合判断平台用户角色、空间类型、团队成员角色和图片归属。我将查看、编辑、删除等能力抽象为权限码，再根据当前用户与资源上下文统一判断，避免权限逻辑散落，也防止只靠前端隐藏按钮造成越权。

不要逐字背诵，只记住：

```text
平台定位 → 三类空间 → 技术与业务对应 → 我的职责 → 权限难点
```

## 今日四个重点纠错项

1. **事务不等于并发唯一性。** 先查后插存在竞态，最终由数据库联合唯一索引兜底。
2. **请求从浏览器发出后才到 Nginx。** Vue、Axios 在浏览器内部，不能放到 Nginx 后面。
3. **`SELECT *` 通常不是覆盖索引。** 联合索引没有全部业务字段，最终仍可能回表。
4. **不要主动选择讲不清的难点。** 先把权限难点讲扎实，再逐步补 WebSocket、Lua 和 Pub/Sub。
