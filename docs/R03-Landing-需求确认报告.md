## 3. 当前具体问题

1. **定位仍停留在 AI 云图库。** 标题、描述和三张特色卡只谈智能管理；没有数字伙伴、长期关系或图片如何参与成长。
2. **高重量标题压过图片。** 900 字重、最大 6rem、85vh Hero，首屏没有真实图片；图片要滚过特色区后才出现。
3. **搜索成为默认第一动作。** 初访者还未理解产品就被要求输入查询，也不清楚搜索的是公共图库还是个人空间。
4. **AI 过度强调且承诺缺少依据。** “智能语义搜索、毫秒级响应、精准定位每一张图”不能从当前 Gallery 链路得到支持；R03 不用这些说法。
5. **容量说法与代码冲突。** “无限容量”与 SPACE_LEVEL_INFO 的数量/容量配额矛盾；“多副本冗余”未在所读前端证据中得到验证，不写作首页保证。
6. **展示排版被写成编辑能力。** 首页只有静态 mosaic，不能据此承诺存在“马赛克布局编辑器”。
7. **旧风格仍很明确。** 搜索框 2px 黑边、focus 的 6px 硬偏移阴影；feature-card 的 2px 黑边与 hover 8px 硬投影；红黄蓝黑四色条；黑底尾段。这些和 R01 的图片优先、单强调、柔和层次不符。
8. **换红色不足以解决定位。** 最近局部改为 #f04438 是旧 Hero 的可读性迭代，不是 R03 的新品牌色决策；R03 原型回到 R01 语义令牌。
9. **热门标签没有继续放在 Hero 的理由。** 六个静态词增加噪声，还被称为“热门”。推荐移除 Landing 上这组标签，图库真实标签筛选保留。
10. **注册 CTA 忽略用户状态。** 已登录用户仍被邀请注册；“开始使用 / 下一代”等泛化说法也无法解释实际下一步。
11. **“精选合集”容易产生错觉。** 本地示例图不是用户相册、实时合集或真实公共内容推荐；后续应标示展示素材，避免做成可点击但没有目的地的假卡片。
12. **旧响应式规则并非 R01 字面量。** 旧页使用 767 等断点；后续只在 Landing 局部迁移到 480 / 768 / 1024，不借机改全站。

## 4. 旧定位与新定位

| 维度 | 旧首页表达 | 本轮设计目标 |
| --- | --- | --- |
| 产品主语 | AI、搜索速度、存储能力 | 用户的图片空间 |
| 日常价值 | 上传与查图的工具集合 | 图片有归属，个人与团队可持续整理 |
| 差异 | “更智能”的泛化承诺 | 用户可主动用图片培养长期存在的数字伙伴 |
| 伙伴角色 | 完全缺席 | 空间内的长期实体，有成长、状态和记忆 |
| 用户控制 | 搜索、注册 | 管理图片；选择是否喂养、确认记忆、开启主动提议 |
| AI 位置 | 首页品牌中心 | 能力实现方式及配置条件，不作为首屏口号 |

不是把 MySpace 中已有“AI 助手”拿来改名当伙伴。图片管理和伙伴是有关联但有各自用途的能力；管理图片不要求使用伙伴。

## 5. 唯一核心心智

**有数字伙伴的图片空间。**

先明确“图片空间”，用户才能知道日常用途；加入“数字伙伴”，用户才能理解它与普通图库的区别。两者形成一个整体印象，而不是把很多功能并列到首屏。

“长期存在”表示伙伴状态、成长与记忆可持续保存和再次查看，不承诺模型一直在线、永久保存或自主处理所有图片。

## 6. 初访十几秒内应该理解什么

- 这是可以上传、浏览、查找和整理图片的地方。
- 图片属于个人或团队空间。
- 数字伙伴与图片有关：用户可选择图片进行喂养，并在以后查看成长、相处。
- 现在该点注册、登录还是进入空间；未开放能力有可见说明。

首屏只承担“定位 + 图像证据 + 下一步”。情绪轴、技能列表、记忆管理和创作步骤不堆到 Hero。预计阅读时间是设计目标，尚未经过真实初访用户测试。

## 7. 能力证据与文案白名单

| 能力 | 本轮读取到的证据 | 可用说法 / 必须保留的边界 |
| --- | --- | --- |
| 图库 | GalleryView 的 searchText/category/tags 等控件 | 按名称或简介搜索、分类与标签筛选；不宣称语义理解或速度 |
| 空间 | MySpaceView、SPACE_TYPE、SPACE_LEVEL_INFO | 个人空间、创建/加入团队、容量与归属；不承诺无限 |
| 喂养 | CompanionView 选择器与 feed actions | 从自己的私有空间选一张图喂养；不画成已支持任意拖拽/批量喂养 |
| 图片保留 | CompanionView 的现有说明 | 喂养不移动、改名或删除原图片；不能等同于“不外发图片” |
| 成长 / 状态 | LIFE_STAGE、MOOD_AXES、RELATIONSHIP_AXES、TRAIT_AXES、home panels | 有成长、情绪、关系、性格状态；不写假数值、假个性和饥饿值 |
| 记忆 | MemoryPanel 的候选记忆与确认/纠正操作 | 真实图片理解后可能形成候选；不承诺每次喂养都记住内容 |
| 聊天 / 主动提案 | ChatPanel 挂载、ProposalPanel 的开关与契约 | 可以聊天；主动提议默认关闭，由用户允许；不宣称自动替用户执行 |
| 故事 | StoryPanel 的选图、大纲、草稿、确认保存 | 图片故事是可说明的具体创作流程，依赖服务/模型可用性 |
| 表情 / 融合 | EmojiPanel、FusionPanel 的未开放说明 | 不作可用卖点；名称存在或技能可成长不等于功能开放 |
| 伙伴可见性 | features.js | DEV 或 VITE_COMPANION_ENABLED=true 才启用；默认生产关闭 |

这是一份基于前端与既有合同表达的设计核实，不替代后端功能验收。涉及费用、图片外发、保存期限等未验证事项，首页不作新增承诺。

## 8. CTA 与可用性矩阵

| 状态 | Hero / 页尾主要 CTA | 次要 CTA | 伙伴 Section |
| --- | --- | --- | --- |
| 访客、伙伴未开放（默认生产） | 注册 → /register | 登录 → /login；图库入口始终可达 | 概念介绍 + “伙伴功能暂未开放”；不出现可用伙伴跳转 |
| 已登录、伙伴未开放 | 进入空间 → /space/my | 图库 → /gallery | 同上；无注册或“开始使用” |
| 访客、伙伴已开放 | 注册 → /register | 登录 → /login | 登录后查看伙伴 → /login?redirect=/companion |
| 已登录、伙伴已开放 | 进入空间 → /space/my | 图库 → /gallery | 进入伙伴 → /companion |

主要 CTA 不直接“唤醒”或喂养；Landing 不推断是否已创建伙伴，也不为判断按钮请求 home API。进入伙伴页后由现有流程处理首次唤醒。

首页/导航读取现有认证结果；加载中先保留中性“图库”入口及稳定按钮占位，不先显示注册再跳成空间。认证失败不推断访客。后续实现只读取现有 store，不修改其认证规则。

原型默认“访客 + 未开放”，顶部控制栏可切四种组合，明确只是设计预览。关闭态仍保留概念，并在 Hero 和伙伴段附近提示暂未开放；不放预订、等待名单或虚假开放日期。

## 9. 方案 A — 先认识空间

1. **Hero**：左文右图；简短定位与 CTA，山谷大图占视觉主体，旁边出现较小的概念栖居位。
2. **核心表达**：先建立图片空间，再自然引出伙伴。
3. **图片能力**：首个内容 Section 三张图，配浏览、名称/简介搜索与分类标签说明。
4. **空间能力**：随后个人/团队两栏，用照片和短说明区分归属，不做后台卡片截图。
5. **伙伴**：第三段较完整的 Habitat 与解释。
6. **喂养 / 记忆 / 成长**：伙伴段三条具体过程，带真实理解与候选确认条件。
7. **创作**：伙伴段末一句图片故事及确认保存说明；表情/融合不作卖点。
8. **搜索**：输入框从 Hero 下移到图片区尾，标签写“图库搜索”，实际目标沿用 /gallery?q=。
9. **CTA**：按 §8，Hero/尾段注册或进入空间，次要登录或图库。
10. **Footer 前**：“先建一个自己的图片空间” / “回到你的图片空间”，接实际 CTA。
11. **易懂原因**：先解释熟悉的图片管理，再介绍差异；空间功能容易被看到。
12. **风险**：伙伴正文较晚，用户可能认为只是图库附属功能；小占位形态不能承担主要解释。

实际候选文案：

- Hero：**你的图片空间，也有伙伴的位置。**
- 副标题：上传、搜索和整理图片，分开管理个人与团队空间。图片还可以用于培养一个长期相处的数字伙伴。
- 主要 CTA：注册 / 进入空间。
- 图片标题：把想留的图片整理好。
- 空间标题：自己的图片，与团队的图片。
- 伙伴标题：用图片培养一个数字伙伴。

## 10. 方案 B — 图片与伙伴同处一室（已选定）

1. **Hero**：短标题和描述/CTA 并列在上；下方一整块照片画布，右边是空间内嵌的静态栖居位。主图面积显著大于形态区域。
2. **核心表达**：图片与长期伙伴同属于这个空间，第一屏就相遇。
3. **图片能力**：Hero 先看到真实照片；后段公共图库入口说明浏览和查找。
4. **空间能力**：在关系段后，个人/团队文字与一张大图并列，说明管理归属与已有权限。
5. **伙伴**：Hero 有位置，紧随的第一段解释相处方式；不是聊天启动按钮。
6. **喂养 / 记忆 / 成长**：照片旁三条短步骤，解释选图、成长/候选记忆、以后再查看和聊天。
7. **创作**：关系段末尾小段说明图片故事，不设 AI 创作功能墙。
8. **搜索**：Landing 不再放输入框；保留导航“图库”和图片区“图库搜索 →”，进入现有 Gallery 完成搜索。
9. **CTA**：按 §8；Hero 一个视觉主按钮，伙伴入口在对应段，不抢注册/进入空间。
10. **Footer 前**：回到图片空间的实际 CTA；不用全黑收尾大广告。
11. **易懂原因**：标题把管理与培养说清，照片提供图片产品证据，内嵌栖居位提供关系证据，下一段马上解释。
12. **风险**：概念轮廓可能被误读为最终角色；必须标注。生产关闭态必须同时出现可用性说明，不能只展示愿景。

实际候选文案：

- Hero：**管理图片，也用图片培养伙伴。**
- 副标题：这里可以上传、搜索和整理图片，管理个人与团队空间。数字伙伴有自己的成长记录，你可以用图片喂养它，也可以回来和它聊聊。
- 主要 CTA：注册 / 进入空间。
- 伙伴标题：选一张图片，开始一次相处。
- 空间标题：一个人整理，也可以和团队一起。
- 图片标题：先看看图片。
- 关闭态补充：伙伴功能暂未开放。你可以先使用图片和空间功能。

## 11. 方案 C — 从一张图到一次成长

1. **Hero**：居中短定位；下方“单张图 / 空间图片组 / 栖居轮廓”形成可阅读三步画面。
2. **核心表达**：展示一张图从保存、归属到参与伙伴成长的使用过程。
3. **图片能力**：第 01 段上传与查找，用单张大图支撑。
4. **空间能力**：第 02 段明确个人/团队，补充现有喂养选择器来自私有空间。
5. **伙伴**：第 03 段展示栖居位和长期状态解释。
6. **喂养 / 记忆 / 成长**：构成主要叙事；明确所有步骤是示意，不是在原型里执行。
7. **创作**：第三段最后可提图片故事，不列模型能力矩阵。
8. **搜索**：第 01 图片段放“去图库搜索 →”；不设 Hero 输入框。
9. **CTA**：按 §8；三步不可做成要求用户必须全部完成的任务清单。
10. **Footer 前**：创建/回到图片空间，强调图片管理可以独立使用。
11. **易懂原因**：每一步都有具体对象与动作，减少抽象品牌词。
12. **风险**：像新手教程；“从一张图开始”会比 B 更强调喂养，必须避免“上传就自动喂养”的误读。

实际候选文案：

- Hero：**从一张图片开始，认识你的数字伙伴。**
- 副标题：先把图片放进自己的空间，再选择一张喂养伙伴。图片可以继续整理，伙伴的成长也会留下记录。
- 主要 CTA：注册 / 进入空间。
- 图片标题：先留下，再找到。
- 空间标题：给图片一个清楚的位置。
- 伙伴标题：喂养之后，继续了解它。

## 12. 三套信息架构对照

| 维度 | A | B | C |
| --- | --- | --- | --- |
| 第一眼 | 产品介绍 + 大图 | 共处的图片画布 | 使用流程 |
| Section 顺序 | 图片 → 空间 → 伙伴 | 关系/伙伴 → 空间 → 浏览图片 | 上传/查找 → 空间 → 成长 |
| 伙伴位置 | Hero 一角、后段详细 | Hero 内嵌、下一段立即解释 | 三步的终点、后续展开 |
| 搜索 | 下移的简短输入框 | 图库入口 | 第 01 段入口 |
| 更适合 | 先认识图片管理 | 建立 2.0 核心印象 | 解释关系和步骤 |
| 最大代价 | 差异可能太晚出现 | 需要控制概念与开放状态 | 容易像教程或必做任务 |

三套均使用同一套令牌、无衬线字体和本地照片，不用颜色差异替代信息架构差异。

## 13. 图片如何成为主体

- 复用 `li-picture-cloud-frontend/public/images/mosaic/` 下 nature、travel、city、architecture、still-life 等已存在照片。无远程下载、无新增图像库。
- B 的 Hero 约四分之三画布宽度给照片，其余给栖居位；视觉重点不依赖满屏标题或光球。
- 照片直落在纸底上，适度 R01 圆角；不每张图片外再套带标题按钮的卡片。
- 正文不遮住图片；说明放在图外。使用 img、alt、固定比例，防止加载位移；首屏 eager，后续 lazy。
- 原型展示的是本地样片，不称实时精选、真实团队、用户作品或伙伴最喜欢的图片；旁边的标题只是说明设计关系。
- 现有素材的授权出处未在本轮核实：已有文件可用于内部探索，正式上线前仍要核对授权或替换为项目自有素材。若整目录被单独拷走，必须同时携带相对引用的样式/图片。
- 不增加图片筛选、详情弹层、分页或 Gallery 数据请求，R04 体验不在本轮复制。

## 14. Companion 如何出现而不锁死 Avatar

用一枚无眼睛、无肢体细节的柔和轮廓占位，与一条地面线构成 Habitat。占位颜色固定使用 accent-soft；没有从图片取色，不关联情绪。

轮廓下可见“概念示意 · 非正式角色”；这里不是当前生命阶段的真实渲染。没有姓名、等级、情绪值、假对白、饥饿、最喜欢或具体记忆样本。

栖居位在内容布局里，不固定右下角，不点击后弹客服聊天框。本轮没有拟定 Sprite、表情、状态机或拖拽喂养协议。正式 Avatar 留给 R05；Landing 后续需要保留可替换的视觉槽位。

## 15. 搜索与标签决定

推荐 B：Hero 先解释产品，搜索入口去现有 Gallery。它仍是一跳可达的实用功能，并非删除。

A 提供保留轻输入框的对照：放在图片区尾，明确搜名称/简介，沿用 /gallery?q=。C 在第一步骤给入口。原型里只展示目标 URL，不请求接口。

旧“热门”固定词不保留；确有浏览价值的图片分类由 Gallery 的真实 metadata 控件承担。R03 不新增趋势词接口，不更换搜索规则。

## 16. 视觉、Motion 与响应式

- 直接引用现有 tokens.css / base.css / motion.css，不拷贝后再维护另一套颜色。
- UI 使用 lp-bg/surface/text/accent/border；正文不使用过浅 tertiary。标题字重 600，Display 最高沿用 R01 4rem，无网络字体，默认 sans。
- 图片画布可使用 wide 宽度；正文限制阅读长度，流式区域按空间需要布局。所有规则隔离在探索目录，不创建全局统一 max-width。
- 普通 hover 采用 fast 160ms、颜色变化；无 hover 位移。
- 原型默认静态，无滚动入场依赖，无光晕/浮动动画。未来如选定低频呼吸，只可单一概念元素复用 ambient 3200ms，并在 reduce、屏外与后台关闭；本轮不为此增加脚本。
- 统一断点为 480 / 768 / 1024，@media 使用字面量；不因技能示例采用别的断点或 React Native 技术栈。
- Desktop：A 左文右图；B 上方文案/操作、下方横向共享画布；C 三栏步骤与章节。
- Tablet：缩短间距，保留分区，不缩小文字强塞内容。
- Mobile：A 文案后接大图/栖居位；B 文案/CTA → 主图 → 小图与栖居位并排；C 改三条图文步骤。阅读顺序与 DOM 相同。
- 顶部预览工具栏是设计工具，不属于产品导航，移动端可折行。
- 控件 ≥44px、可见 focus-visible、跳到内容、清晰 alt 与 input label；reduce 下保持内容完整可读。
- 不追求首屏内塞下移动端全部元素；Hero 文案立即说清伙伴，照片与形态可以在下一屏自然出现。
