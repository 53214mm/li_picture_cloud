## 🔴 安全漏洞 (Critical — 7 个) ✅ 全部已修复

### 1. SSRF — ResourceDownloadTool ✅

**位置**：`AI/tools/ResourceDownloadTool.java:17`

**问题**：URL 无任何校验，可访问内网地址 `localhost`、`169.254.169.254`（云元数据）。`fileName` 参数无路径遍历防护，可写 `../../` 到任意系统位置。

```java
// 当前代码：
HttpUtil.downloadFile(url, new File(filePath));  // url 和 filePath 都未校验
```

**建议修复**：
- URL 校验协议白名单（仅 http/https），DNS 解析后过滤私有 IP
- fileName 校验，拒绝含 `..`、`/`、`\` 的路径

---

### 2. SSRF — WebScrapingTool

**位置**：`AI/tools/WebScrapingTool.java:16`

**问题**：URL 无任何校验，Jsoup 直接连接，可抓取内网服务。

```java
// 当前代码：
Document doc = Jsoup.connect(url).get();  // url 未校验
```

**建议修复**：同 #1，增加 URL 白名单校验 + DNS 私有 IP 过滤

---

### 3. 路径遍历 — FileOperationTool

**位置**：`AI/tools/FileOperationTool.java:16, 27`

**问题**：`fileName` 直接拼接到沙箱路径，未过滤 `../`，可突破沙箱读写任意文件。

```java
// 当前代码：
String filePath = FILE_DIR + "/" + fileName;  // fileName 可能是 "../../../etc/passwd"
```

**建议修复**：校验 `fileName` 不含 `..`、`/`、`\`，使用 `Paths.get().normalize()` + 前缀校验

---

### 4. JSON 注入 — SearchTool

**位置**：`AI/tools/SearchTool.java:25`

**问题**：`query` 直接拼入 JSON 字符串，含 `"` 或 `\` 会破坏 JSON 结构。

```java
// 当前代码（有注入风险）：
"\"content\":\"" + query + "\""  // query 中的 " 未转义
```

**建议修复**：使用 `JSONObject` / `ObjectMapper` 构造 JSON，而非字符串拼接

### 5. CSRF Origin 校验可绕过

**位置**：`controller/AIController.java:35`

**问题**：`origin.endsWith(host)` 匹配不精确。如 `host=example.com`，Origin 为 `http://attackerexample.com` 也能通过。

```java
// 当前代码：
if (host == null || !origin.endsWith(host)) {  // 可绕过
```

**建议修复**：解析 Origin 的 host 部分，与 `Host` 头做精确比较；或使用 Spring Security 的 CSRF 保护

## 🟠 Bug / 运行时缺陷 (High — 9 个)

### 8. MCP 工具 inputSchema 全部硬编码为 `{}`

**位置**：`AI/config/RefreshableMcpToolProvider.java:113`

**问题**：所有 MCP 工具的 `ToolDefinition.inputSchema` 都被设为 `"{}"`，LLM 不知道参数名和类型，只能"盲猜"。这是导致 MCP 工具（generate_image、get_task_status 等）调用失败率高的根因之一。

```java
// 当前代码：
return ToolDefinition.builder()
    .name(toolName)
    .description(toolDescription)
    .inputSchema("{}")  // ★ 应该从 MCP tool.inputSchema() 获取真实 schema
    .build();
```

**建议修复**：从 `McpSchema.Tool.inputSchema()` 获取 JSON Schema 字符串传入

---

### 9. Kryo 序列化 Spring AI Message 不可靠

**位置**：`AI/chatMemory/RedisBasedChatMemory.java:87, 97`

**问题**：Spring AI 的 `Message` 实现类（如 `AssistantMessage`）可能含 Lambda、不可序列化字段。Kryo 在 `setRegistrationRequired(false)` 下不能保证正确序列化/反序列化。反序列化用 `ArrayList.class` 泛型丢失，可能导致类型错误。

**建议修复**：改用 Jackson JSON 序列化（依赖 Spring AI Message 的 Jackson 注解），或使用 Spring AI 自带的 JDBC/Cassandra ChatMemory 实现

---

### 10. autoSaveToSpace URL 提取逻辑脆弱

**位置**：`AI/config/RefreshableMcpToolProvider.java:159-164`

**问题**：用 `indexOf("http")` + 空格/换行/`}` 截断 URL，某些 CDN URL 含 `}` 会截断错误，URL 含空格也会出问题。

```java
// 当前代码（脆弱）：
int end = text.indexOf(" ", start);
if (end < 0) end = text.indexOf("\n", start);
if (end < 0) end = text.indexOf("}", start);  // URL 中可能有 }
```

**建议修复**：用正则 `https?://[^\s\n}]+` 提取 URL

---

### 11. BaseAgent SSE 回调注册位置错误

**位置**：`AI/agent/BaseAgent.java:162-176`

**问题**：`emitter.onTimeout()` 和 `emitter.onCompletion()` 写在 `CompletableFuture.runAsync()` 的 lambda 内部。`runAsync` 立即返回，回调注册在线程池任务中——如果任务执行很快，回调可能在 emitter 返回之后才注册，导致回调不生效。

```java
// 当前代码（有竞态）：
CompletableFuture.runAsync(() -> {
    // ... 业务逻辑 ...
    emitter.onTimeout(() -> { ... });      // ★ 应该移到 runAsync 外部
    emitter.onCompletion(() -> { ... });    // ★ 应该移到 runAsync 外部
});
return emitter;
```

**建议修复**：将 `onTimeout`/`onCompletion`/`onError` 移到 `runAsync` 外部注册

---

### 12. BaseAgent state 竞态条件

**位置**：`AI/agent/BaseAgent.java:149-174`

**问题**：`runAsync` 内部线程修改 `state`，外部 `onTimeout`/`onCompletion` 也修改 `state`，无同步机制。

**建议修复**：使用 `AtomicReference<AgentState>` 或 `volatile` + 只在单线程修改

### 13. MyLoggerAdvisor 流式场景 NPE

```java
// 当前代码：
log.info("ai-response: {}", chatClientResponse.chatResponse().getResult().getOutput().getText());
```

**建议修复**：增加 null 检查；或在聚合后的最终响应中输出完整文本

### 14. AIController SSE send 异常处理不完整

### 17. Agent 体系与 PicCloudApp 双轨并行

**位置**：`AI/agent/` vs `AI/app/`

**问题**：项目存在两套独立的 AI 调用体系：
- **Agent 体系**：PicAgent → ToolCallAgent → ReActAgent → BaseAgent（ReAct 循环，手动 think→act）
- **PicCloudApp 体系**：直接使用 Spring AI `ChatClient`（依赖 Spring AI 内置的 tool calling 循环）

当前 AIController 仅使用 PicCloudApp，整个 Agent 体系（6 个文件）可能是死代码。两套体系存在大量重复（系统提示词、工具注入逻辑）。

**建议修复**：确认 Agent 体系是否需要，若不需要则删除；若需要则统一为一个体系

### 26. ChatMemory add() 全量读写开销

**位置**：`AI/chatMemory/RedisBasedChatMemory.java:52-57`

**问题**：每次 `add()` 先全量 GET 反序列化 → 追加 → 全量序列化 SET。对话历史长时网络 IO 和 CPU 开销大。

```java
public void add(String conversationId, List<Message> messages) {
    List<Message> current = getOrCreateConversation(conversationId); // 全量 GET
    current.addAll(messages);
    saveConversation(conversationId, current);  // 全量 SET
}
```

**建议修复**：使用 Redis List 的 `RPUSH` 追加，配合 `LRANGE` 获取最近 N 条

## 🔵 性能问题 (Performance — 3 个)

### 27. 每次 MCP 工具调用都新建连接

**位置**：`AI/config/RefreshableMcpToolProvider.java:119-127`

**问题**：`FreshSessionMcpCallback.call()` 每次调用都新建 MCP SSE 连接 + `client.initialize()`（~500ms）。如果 AI 单轮对话调用 3 个 MCP 工具（如 generate_image → get_task_status → 再次 generate），延迟累积 1.5s+。

**建议修复**：考虑短时连接池或 session 复用（keep-alive），或在调用间隙保活

---

### 28. MCP 工具列表首次加载冷启动

**位置**：`AI/config/RefreshableMcpToolProvider.java:56-92`

**问题**：工具列表缓存在第一次请求时才加载，首次用户需等待 MCP 连接 + 列举工具的完整耗时。

**建议修复**：增加 `@PostConstruct` 预热或应用启动时的异步加载

---

### 29. 对话历史全量序列化

**位置**：`AI/chatMemory/RedisBasedChatMemory.java:79-83`

**问题**：每次对话都对完整历史做 Kryo 序列化写回 Redis，历史消息多时（如 50+ 轮对话）CPU 和网络开销显著。详见 #26。

## 🟢 缺失与不完整 (Missing — 6 个)

### 30. 无 AI 接口速率限制

**位置**：`controller/AIController.java`

**问题**：没有对 `/ai/chat/stream` 做频率限制，恶意用户可短时间内发起大量请求，导致通义千问 API 费用暴涨。

**建议修复**：增加基于用户 ID 的速率限制（如每分钟 10 次），可用 Redis 计数器或 Spring AOP 实现

---

### 31. 无用户输入长度限制

**位置**：`controller/AIController.java:26`

**问题**：`message` 参数无长度校验，用户可发送数万字文本，消耗大量 token 且可能超出模型 context window。

**建议修复**：限制 message ≤ 2000 字符

---

### 32. 无对话历史长度管理

**位置**：`AI/chatMemory/RedisBasedChatMemory.java`

**问题**：对话历史无限追加，超长对话会超出模型 context window（如 qwen-max 的 32K），导致截断或错误。

**建议修复**：限制保留最近 N 轮对话（如 20 轮），或基于 token 数裁剪

---

### 33. AIController 缺少显式权限注解

**位置**：`controller/AIController.java:25`

**问题**：目前靠 `getLoginUserEntity()` 抛异常来保证登录状态，没有显式的 `@AuthCheck` 注解。

**建议修复**：添加 `@AuthCheck` 注解

---

### 34. SSE 使用 GET 方式，长消息受限

**位置**：前端 `AiAgentPanel.vue:96-97`

**问题**：使用 GET + query string 发送消息，长文本会超过 URL 长度限制（浏览器约 2000 字符）。

```javascript
const url = '/api/ai/chat/stream?message=' + encodeURIComponent(msg) + '&chatId=' + chatId
```

**建议修复**：改为 POST + EventSource polyfill（或改用 fetch + ReadableStream）

---

### 35. EventSource 断开无自动重连

**位置**：前端 `AiAgentPanel.vue:109`

**问题**：SSE 连接断开后 `EventSource` 虽有内置重连，但 `es.onerror` 直接关闭了连接且标记 loading 结束，用户必须手动重发。

**建议修复**：增加重连计数，网络异常时自动重连（限制最大重试次数）

### 37. AiAgentPanel localStorage key 隔离不足

**位置**：前端 `AiAgentPanel.vue:51-53`

**问题**：`userId` 默认为空字符串，未登录或 userId 为空时，多个用户（或同一浏览器不同标签页）可能共享同一存储 key，导致消息串扰。

**建议修复**：userId 为空时禁用 localStorage 持久化，或使用 sessionStorage
