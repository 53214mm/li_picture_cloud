# 疑难杂症

> 记录 AI 模块开发中遇到的非直觉问题和解决方案

---

## 1. AI 不停轮询 MCP get_task_status

**现象**：让 AI 生成图片后，AI 每隔几秒就调一次 `get_task_status`，产生大量无效 MCP 连接和 token 消耗。

**根因**：

1. **系统提示词教 LLM 轮询**：`PicCloudApp.java` 中写有 "每隔一分钟通过 get_task_status 查询异步生成任务的结果"
2. **MCP 返回文本也教 LLM 轮询**：`generate_image` 的返回值中包含 "请自动调用 get_task_status 查询结果，直到完成"
3. **Spring AI ChatClient 无 maxSteps 限制**：LLM 可以在工具调用循环中无限调用工具
4. **LLM 不懂真正的等待**：系统提示词说 "每隔一分钟" 但 LLM 无法 sleep，它每次循环都立即调用

**解决方案**：

在 `RefreshableMcpToolProvider` 的 `FreshSessionMcpCallback.call()` 中拦截生成类工具（`generate_image` / `generate_video`），在 **Java 层做轮询**：

- 调用 MCP 生成工具 → 获取 taskId → 先等 50s → 指数退避轮询（2s→4s→8s→16s→30s...）→ 最大 240s
- 每次轮询**创建新 MCP 连接**（不尝试复用——MCP SSE 有空闲超时）
- 完成后返回最终结果，LLM 只看到 1 次工具调用
- 用 `stripPollingInstruction()` 过滤掉 MCP 返回中的 "请自动调用 get_task_status" 诱导文本

**关键代码位置**：
- `RefreshableMcpToolProvider.java` — `pollUntilComplete()`、`callMcpGetTaskStatus()`、`stripPollingInstruction()`
- `PicCloudApp.java` — 系统提示词改为 "工具会自动等待生成完成并返回结果"

## 2. taskId 提取失败——中文格式 "任务序列号"

**现象**：`generate_image` 返回了 taskId，但日志显示 "生成工具同步返回结果（无 taskId）"，轮询逻辑被跳过。

**根因**：MCP 返回的是中文格式 `任务序列号: 2079168410440175616`，而 `extractTaskId()` 只匹配 JSON `"taskId":"xxx"` 格式。

**解决方案**：改为多正则依次尝试匹配：

```java
private static final Pattern[] TASK_ID_PATTERNS = {
    Pattern.compile("任务(?:序列号|ID|编号)[：:]\\s*(\\d+)"),  // 中文格式
    Pattern.compile("\"(?:taskId|task_id|id)\"\\s*:\\s*\"([^\"]+)\""),  // JSON格式
    Pattern.compile("\\b(\\d{15,20})\\b")  // 纯数字ID兜底
};
```

## 3. get_task_status 参数名错误

**现象**：轮询 `get_task_status` 时所有请求都返回 `serial_no 不能为空`。

**根因**：mxai MCP 服务端期望的参数名是 `serial_no`（对应 "任务序列号"），而代码传的是 `taskId`。

**解决方案**：`Map.of("taskId", taskId)` → `Map.of("serial_no", taskId)`

## 4. MCP SSE 连接空闲超时，无法复用

**现象**：尝试在同一个 MCP 连接上复用轮询，但 50s 初始等待期间连接断开（`EOFException`），后续轮询全部报 `Invalid session ID`。

**根因**：MCP SSE 连接有约 30s 的空闲超时。50s 等待期间没有流量，连接被服务端关闭。

**解决方案**：放弃复用同一连接。每次 `get_task_status` 轮询都创建全新 MCP 连接（`callMcpGetTaskStatus()`），用完即关。500ms 建连开销 vs 50s+ 等待——可忽略。

## 5. UserContextHolder 在 reactor 子线程为 null

**现象**：`autoSaveToSpace` 中 `UserContextHolder.get()` 返回 null，图片无法自动保存到用户空间。但 SSE 主线程中 set 了 user。

**根因**：

1. `PicCloudApp.doChatStream()` 在 SSE 处理线程调用 `UserContextHolder.set(user)`
2. Spring AI `ChatClient` 内部的工具调用（`ToolCallback.call()`）运行在 reactor `boundedElastic` 线程
3. `Hooks.enableAutomaticContextPropagation()` 需要 `io.micrometer:context-propagation` 依赖才能生效——**我们的 pom.xml 中没有这个依赖**，`Hooks` 调用是空操作
4. `ThreadLocal` 无法跨线程池传播

**失败路径**：

| 尝试 | 结果 |
|------|------|
| `InheritableThreadLocal` | ❌ 对线程池无效（线程复用，非 fork）|
| `ConcurrentHashMap<ThreadId, User>` | ❌ 不同线程 ID 不同 |
| `ContextRegistry.registerThreadLocalAccessor()` | ❌ 缺少 context-propagation 依赖 |
| 在 PicCloudApp 静态块中先加载 UserContextHolder | ❌ 同上 |

**最终方案**：在 `PicCloudApp.doChatStream()` 中，用 **Java 闭包直接捕获 user**，包装每个 MCP ToolCallback：

```java
// 包装每个 MCP 回调，在 call() 执行前注入用户上下文
for (int i = 0; i < mcpCallbacks.length; i++) {
    mcpCallbacks[i] = new UserContextToolCallback(mcpCallbacks[i], currentUser);
}

// record 实现
private record UserContextToolCallback(ToolCallback delegate, User user) implements ToolCallback {
    public String call(String toolInput) {
        UserContextHolder.set(user);
        try { return delegate.call(toolInput); }
        finally { UserContextHolder.clear(); }
    }
}
```

闭包中的 `user` 引用在创建时绑定，无论 `call()` 在哪个线程执行都能访问。

## 6. Redis ChatMemory Jackson 序列化问题

**现象**：日志报 `Cannot construct instance of Message` / `InvalidTypeIdException` / `MismatchedInputException`。

**根因**：Spring AI 的 `Message` 是接口，其实现类（`UserMessage`、`AssistantMessage` 等）没有无参构造器和 `@JsonCreator`，Jackson 无法反序列化。

**尝试过的方案**：

| 方案 | 结果 |
|------|------|
| Kryo 序列化（原始方案） | ❌ Message 实现类含 Lambda 字段，Kryo 不注册类时不可靠 |
| Jackson + `registerSubtypes` | ❌ 反序列化不知道用哪个子类 |
| Jackson + `activateDefaultTyping` | ❌ `BasicPolymorphicTypeValidator` 阻断了 ArrayList 等容器类型 |

**当前状态**：反序列化失败时会 catch 异常并返回空列表（对话重新开始），对功能无影响，仅有 WARN 日志。旧 Redis 数据会在 TTL 过期后自然清除。

**完全修复方向**（如需要）：使用 Spring AI 内置的 `JdbcChatMemory`，或为 Message 类型编写自定义 Jackson 序列化器/反序列化器。

## 7. AI 生成图片超过 2MB 限制

**现象**：图片生成成功但保存到空间时报 `文件大小不能超过 2M`。

**根因**：`FileManager.validPicture()` 和 `UrlPictureUpload.validPicture()` 硬编码了 2MB 限制。AI 生成的图片通常较大（5-10MB）。

**解决方案**：全局上调上传限制 2MB → 10MB：

| 文件 | 改动 |
|------|------|
| `FileManager.java` | `2 * ONE_M` → `10 * ONE_M` |
| `FilePictureUpload.java` | `2 * ONE_M` → `10 * ONE_M` |
| `UrlPictureUpload.java` | `TWO_MB` → `TEN_MB` |
| `application.yaml` | `max-file-size: 10MB` → `50MB` |

## 8. 50s 等待期间前端零反馈

**现象**：AI 生成图片时，`pollUntilComplete()` 阻塞 50s+，期间无任何 SSE 事件，前端只显示三个加载点。

**解决方案**：在 `AIController.chatStream()` 中，订阅 Flux 之前先通过 emitter 发送一条提示消息：
```java
emitter.send(SseEmitter.event().data("正在处理您的请求，图片生成可能需要 1-2 分钟...\n\n"));
```
用户会立即看到这条提示，知道 AI 正在工作中。

## 9. Markdown 图片无法渲染——显示裂图或残片

**现象**：AI 返回 `![alt](https://...png)` 格式的图片，前端要么显示裂图图标，要么显示 `" alt="` 等 HTML 残片。

**根因**：`renderMd()` 中的裸 URL 正则先于 `marked.parse()` 执行，把 markdown 图片语法 `![alt](url)` 里的 URL 替换成了 `<img>` 标签，破坏了 markdown 结构。

**解决方案**：改为三遍处理流程：

```
Step 1: 提取 ![alt](url) → 占位符 __IMG_0__ 保护
Step 2: 裸 URL → <img> 标签
Step 3: 占位符 → <img> 标签（带 alt + src）
Step 4: marked.parse() 处理剩余 markdown
```

**关键代码**：`AiAgentPanel.vue` — `renderMd()` 函数

## 10. 图片过大撑爆聊天框

**现象**：AI 生成的图片尺寸很大，撑满整个聊天面板。

**解决方案**：
- `.bubble-ai` 加宽：`max-width: 85%` → `95%`
- 图片限高：`max-height: 400px; object-fit: contain; cursor: pointer`
- 加 `no-referrer` meta 标签绕过 CDN 防盗链

---

## 11. 以图生图需要上传参考图片 + 提示词

**现象**："以图生图" 按钮只填入文字前缀，用户需要手动粘贴图片 URL，体验差。

**解决方案**：
- 点击 "以图生图" 弹出内联表单
- 支持两种输入参考图的方式：**本地文件上传**（自动上传到平台拿到 URL）或 **粘贴 URL**
- 另有风格描述输入框
- 提交后自动构造完整消息：`"请用这张参考图生成一张相似风格的图片。参考图URL: xxx，描述: xxx"`

## 经验总结

1. **不要教 LLM 去轮询**：LLM 会把 "每隔X秒查询" 理解为 "每次工具调用循环都查一次"
2. **MCP SSE 连接不能长空闲**：~30s 超时，长时间等待场景要每次新建连接
3. **跨线程传递上下文优先用闭包**：比 ThreadLocal + ContextRegistry 简单可靠，不依赖额外依赖
4. **优先看 API 实际返回值格式**：参数名、字段名可能与文档/预期不同（`taskId` vs `serial_no`，中文 `任务序列号` 格式）
5. **第三方 API 返回值可能包含诱导性指令**：MCP 返回中嵌入了 "请自动调用 get_task_status"，需要过滤
6. **Markdown 渲染要注意处理顺序**：裸 URL 和 markdown 语法可能冲突，应先用占位符隔离
7. **长阻塞操作需要给用户即时反馈**：SSE 订阅前先发一条提示消息
8. **DOMPurify 不要允许 `onerror` 等事件属性**：有 XSS 风险，用 CSS 兜底
